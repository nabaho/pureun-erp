# 2026-09-08 · 「왜 자꾸 이권우가 항상 올라오나」 — 딥링크에 갇힌 창

- 대표 제보: 「기업정보함에 왜 자꾸 이권우가 항상 올라오나 문제 있는지 검토해라」
  (화면 주소: `pu-cards.html?q=010-7797-7572&v=ebf570f6`)
- 답: **자료도 판독도 멀쩡하다. 「주소」가 문제였다.** 명함이 자꾸 올라온 것이 아니라,
  그 탭이 **검색 한 건에 갇혀** 열 때마다 그 한 사람만 보여 준 것이다.

## 어떻게 갇혔나 — 네 곳이 겹쳤다

| | |
|---|---|
| ① | 사진첩의 「기업정보함에서 이 명함 보기 →」(`openFiledCard`)가 `pu-cards.html?q=010-…` 로 열었다. `?q=` 에 **전화번호**를 담고 `sso=` 가 없는 곳은 사진첩뿐이라 여기서 온 것이 분명하다 |
| ② | 기업정보함은 `?q=` 를 읽어 검색만 걸고 **주소에서 지우지 않았다**(`pu-cards.html` 딥링크 자리, `history.replaceState` 없음) |
| ③ | 새 판이 올라올 때마다 `js/pu-version.js:86` 이 `new URL(location.href)` 에 `v` 만 얹어 새로고침했다 — **쿼리를 그대로 들고 간다.** 대표 주소의 `v=ebf570f6`(그때 main 의 커밋)이 그 흔적이다 |
| ④ | 포털에서 기업정보함 타일을 눌러도 `enter.html` 의 `portalAppUrlMatches` 가 **origin·pathname 만** 견주어 「이미 그 화면」으로 보고 `focus()` 만 했다 — 주소가 안 바뀌니 그대로였다 |

→ **F5 로도 안 풀린다**(주소에 적혀 있으니 다시 읽힌다). 새 판이 올 때마다 되살아난다.
포털 타일로도 못 벗어난다. 유일한 탈출구는 주소창을 손으로 고치는 것이었다.

## 고친 것

**A. `pu-cards.html` — 딥링크는 «한 번» 쓰고 주소에서 지운다**

검색을 건 **뒤** `history.replaceState` 로 `q` 만 뺀다. 바로 위 `shared=1` 이 이미 같은
일을 하고 있었다(한 번 쓰고 지운다) — 같은 결로 맞춘 것이다.

- ⚠ **`q` 하나만** 뺀다. 통째로 지우면 `?view=mail` 로 열린 **메일 창**이 새로고침될 때
  명함 화면으로 바뀐다(같은 파일이 두 앱이다).
- ⚠ **화면은 그대로 둔다** — 지우는 것은 주소뿐이다. 결과가 눈앞에서 사라지면
  「눌렀는데 안 나왔다」가 된다.
- ⚠ **지우기는 검색을 건 뒤에** 온다. 먼저 지우면 검색어를 잃는다.

**B. `enter.html` — 창을 다시 쓸 때 «뜻이 있는» 쿼리까지 견준다**

`portalAppUrlKey()` 가 `v`·`sso` 를 뺀 쿼리를 차례 맞춰 만들고, `portalAppUrlMatches`
가 그것까지 견준다.

- ⚠ 쿼리를 **통째로 견주면 안 된다.** 타일은 늘 `v=<10분 버킷>`을 붙이므로 10분마다
  달라져, 보던 자리를 잃고 새로고침된다 — **`pathname` 만 견주던 까닭이 그것이다.**
- 덕분에 `?view=mail`(메일)과 `pu-cards.html`(명함)이 **다른 화면**으로 갈린다.
  같은 파일이라 예전에는 못 가렸다.
- 이 B 는 `?q=` 뿐 아니라 **어떤 쿼리에 갇혀도** 타일로 빠져나오게 하는 일반 안전장치다.

## 아니었던 것 (재어 보고 지운 의심)

- 명함이 중복으로 쌓이지 않았다 — 검색 결과가 **1개**다.
- 판독기가 같은 번호를 지어내지 않았다 — `010-7797-7572` 은 앱 코드에 값으로
  박혀 있지 않다(주석·검사 붙임자료에만 있다).
- 중복 판정이 엉뚱한 명함을 집지 않았다 — `dedupKey` 는 휴대폰 숫자이고,
  `findByKey` 가 찾아간 명함의 번호를 **다시 맞춰 본다**(옛 열쇠를 그대로 믿지 않는다).
- 회사 이음매 되짚기(`coCompanySweep`)는 `read.coCheck` 표로 **한 번만** 돈다.
