# 푸른통합 온톨로지 — 1단계 전수진단과 공통 사전

작성: 2026-09-02

## 결정

온톨로지는 푸른ERP의 부가기능이 아니라 푸른통합시스템 전체의 공통 의미 계층이다.
기존 Firebase·IndexedDB·로컬 자료는 계속 정본이며, 온톨로지는 언제든 다시 만들 수
있는 읽기 전용 관계 후보로 시작한다.

## 등록된 프로그램

포털의 13개 프로그램을 모두 `js/pu-ontology.js`에 등록했다.

- 푸른이알피
- 정부사업일정
- 업무관리
- 경력관리
- 푸른 메일
- 기업정보함
- 사진첩
- 기금관리
- 취업규칙 관리
- 문서관리
- 급여관리
- 급여데이터함
- 홈페이지 관리

각 프로그램은 자신이 소유하는 저장 뿌리(`primaryRoots`)와 다른 프로그램에서 읽는
공유 뿌리(`sharedRoots`)를 구분한다. 공유한다고 소유권이나 쓰기 권한이 생기는 것은 아니다.

## 공통 개체

`Organization`, `Person`, `Employment`, `Contract`, `Case`, `Project`, `Task`,
`ScheduleEvent`, `FinancialTransaction`, `Invoice`, `Document`, `MediaAsset`,
`Message`, `PayrollRecord`, `Policy`, `Submission`을 v1의 정식 개체어로 사용한다.

## 공통 관계

`belongsToOrganization`, `contractedWith`, `concerns`, `projectFor`, `assignedTo`,
`assists`, `derivedFrom`, `paidFor`, `invoicedTo`, `scheduledFor`, `evidencedBy`,
`attachedTo`, `ownedBy`, `transferredTo`, `fulfills`, `supersedes`를 v1의 정식 관계어로 사용한다.

## 1단계 진단 범위

환경설정 → 데이터·로그 → 온톨로지에서 다음을 검사한다.

1. 개체 ID 누락 및 중복
2. 중복 업체명·사업자번호
3. 존재하지 않는 `companyId`
4. 업체는 찾았지만 `companyId`가 비어 있는 업무
5. 확정할 수 없는 업체 연결
6. 존재하지 않는 주담당·부담당 사번
7. 재무자료의 끊어진 `sourceKind`·`sourceId`
8. 확실한 관계의 읽기 전용 관계 후보 생성

진단 결과는 화면 상태와 내려받은 JSON에만 존재한다. `dbSet`, Firebase `set/update/remove`,
자동 교정은 호출하지 않는다.

## 권한 원칙

통합 관계망이 원본 권한을 우회하면 안 된다. 이후 관계를 서버에 저장할 때는 일반업무,
인사, 재무, 개인자료의 경로를 분리하고 각 관계에 원본 출처와 권한 등급을 기록한다.
권한을 확인할 수 없는 관계는 생성하지 않는 쪽으로 실패한다.

## 다음 순서

1. 실제 진단 결과를 검토하고 용어·관계 후보를 확정한다.
2. 프로그램별 읽기 어댑터를 붙여 공통 진단 범위를 확장한다.
3. 확정 관계만 `ontology/v1` 파생 색인으로 생성한다.
4. 업체 360° 화면을 만든다.
5. 검증센터와 AI 질의를 연결한다.

어느 단계에서도 온톨로지 때문에 기존 원본을 자동 삭제하거나 통째로 다시 쓰지 않는다.
