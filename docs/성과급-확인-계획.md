# 매달 성과급 확인 기능 — 계획

작성 2026-08-01 · 상태 **계획 확정, 구현 전**

매달 초 각자 자기 성과급 내역을 직접 확인하고, 누가 언제 확인했는지 기록으로 남긴다.
폰에서도 된다.

---

## 왜 '발행' 단계가 필요한가

성과급 원본은 `finance_income` 에 있고, 각 입금 건 안에
`perfShares[] = {sid, name, role, pct, amount}` 로 분배가 박혀 있다.

이 노드의 규칙은 **재무 권한자만 읽기/쓰기**다.

```
"finance_income": {
  ".read":  "root.child('uid_roles').child(auth.uid).child('fin').val() == true",
  ".write": "root.child('uid_roles').child(auth.uid).child('fin').val() == true"
}
```

→ **직원 본인은 자기 성과급을 못 읽는다.** 규칙을 풀면 남의 것까지 다 보이므로 풀면 안 된다.

그래서 재무 권한자가 그 달치를 **사람별로 추려 확인용 사본을 발행**하고,
직원은 사본만 읽는다. 원본은 안 건드린다.
덤으로 "확인 대상이 확정된 시점"이 분명해진다.

## 정해진 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 안내 강도 | 하루 첫 로그인 팝업 1회 + 상단 빨간 띠 상시 | 매번 막으면 월초에 일을 못 한다 |
| 확인 화면 | **업무관리(work.html) 안에 '성과급' 메뉴 추가** | 아래 "확인 화면을 어디에 둘까" 참고 |
| 대상 월 기준 | **입금 확정된 달** | 지금 성과관리가 쓰는 기준과 같다. 급여 지급월 기준이면 한 달 늦게 확인하게 된다 |

발행·현황판은 pu-erp 성과관리 안에 둔다(대표가 PC 에서 하는 일).

### 확인 화면을 어디에 둘까 — 한 번 바뀐 결정

처음에는 별도 파일 `pu-perf.html` 로 잡았다. 이유는 **pu-erp 가 3.6MB** 라 폰에서
체크 몇 개 하려고 받을 수 없다는 것이었다.

그런데 확인 화면을 **업무관리 안에** 두면 그 이유가 사라진다.

- work.html 은 **358KB** 이고, 직원이 **어차피 매일 여는 화면**이다 → 추가 부담 0
- 안내와 실제 확인이 같은 화면에 있다 → "다른 프로그램으로 가라"는 단계가 없어진다.
  가라는 안내는 항상 사람을 잃는다
- 성과급이 붙은 원천(사건·컨설팅·기금)이 곧 업무관리의 업무다. 맥락이 맞다
- 새 파일을 안 만든다 → 만들 것이 4개에서 3개로 줄어든다
- 폰 앱은 work.html 에 manifest 를 붙이면 된다(명함첩과 같은 방식).
  업무관리를 홈화면에 두는 건 어차피 쓸모가 있다

**`pu-perf.html` 은 만들지 않는다.**

#### 업무관리에 둘 때 반드시 지킬 것

1. **본인 고정** — work.html 에는 `setView(sid,name)` 으로 *다른 사람 업무를 열람*하는
   기능이 있다(`S.vsid`). 성과급 화면은 **반드시 로그인 본인 `S.me.sid`** 에 묶고,
   열람 대상 `S.vsid` 를 절대 따라가면 안 된다.
   규칙(`uid` 대조)이 한 번 더 막으므로 코드가 틀려도 남의 것은 안 열린다 — 이중 잠금.
2. **금액 가림** — 업무관리는 하루 종일 켜 두는 화면이라 어깨너머로 보인다.
   금액은 처음에 `●●●` 로 두고 누르면 보이게 한다.
3. 팀 전체·업무량 화면에는 성과급이 **절대 섞이지 않게** 한다.

## 데이터 자리

**`data/perf_confirm`** — `data/finance_income` 과 나란히.
(최상위가 아니라 `data` 아래다. 규칙 안의 경로도 `root.child('data').child('perf_confirm')`)

```
data/perf_confirm/
  2026-08/                         대상 월 (입금 확정월)
    p/
      <sid>/
        uid                        ← 발행 때 심는다. 규칙이 이걸로 본인을 가린다
        name  total  itemCount
        openedAt  openedBy
        items/
          <fiId>/                  finance_income 레코드 id — 추적용
            date source sourceId coName kind role pct amount
            stamp                  ← 금액·비율을 뭉친 지문. 바뀌면 체크가 풀린다
            ok  okAt  okBy
            reply/  text at by state       ← 대표 답변. 직원은 못 쓴다
        done  doneAt  doneBy  deviceHint
        objection/
          byItem/
            <fiId>/  text  at     ← 직원이 건별로 남기는 이의
        reopen/     at by reason   ← 대표가 완료를 푼 기록
```

**월 단위 `meta` 는 두지 않는다.** 거기에 전사 합계를 넣으면 전원이 읽게 된다.
업무관리는 자기 칸이 있는지만 보면 되므로 meta 가 필요 없다.

### 이의는 왜 `objection/byItem/` 이고 답변은 왜 `items/<fiId>/reply` 인가

**규칙을 다시 게시하지 않으려고 갈라 놓은 것이 아니라, 갈라야 맞아서 갈랐다.**

- 게시된 규칙에서 직원은 `objection` **아래 전체**를 쓸 수 있다.
  그래서 `objection/byItem/<fiId>/…` 는 규칙을 안 고쳐도 바로 된다
- 대표 답변을 같은 `objection` 아래 두면 **직원이 자기가 받은 답변을 고칠 수 있다.**
  그래서 답변은 직원 쓰기 규칙이 없는 `items/<fiId>/reply` 에 둔다.
  대표는 `perf_confirm` 최상위 `.write`(fin) 로 거기까지 쓸 수 있다

→ **규칙 재게시 불필요.**

### 금액이 바뀌면 체크가 풀린다

발행할 때 항목마다 `stamp` 를 같이 적는다 — `amount|pct|role` 을 이어 붙인 문자열.

재발행 때 같은 `fiId` 의 `stamp` 가 달라졌으면
그 항목의 `ok`·`okAt`·`okBy` 를 지우고 `stamp` 를 새로 적는다.
사람의 `done` 도 함께 푼다(그 사람은 다시 확인해야 한다).

이유 — 이의를 받아들여 입금을 고치면 금액이 바뀐다.
그때 옛 체크를 그대로 두면 **"확인했다"는 기록이 지금 금액과 다른 것을 가리킨다.**
기록이 의미를 잃는다.

`stamp` 가 같으면 손대지 않는다. 그래서 단순 재발행은 안전하다.

### 권한 규칙 — **게시 완료본이 `docs/firebase-rules-현재적용본.json` 에 들어 있다**

`data` 아래 `finance_income` 바로 앞에 47줄이 들어갔다. 기존 규칙은 한 줄도 안 지웠다.

핵심 세 가지:

- **읽기** — `$sid` 칸은 `data.child('uid').val() === auth.uid` 인 사람과 재무권한자만.
  `p` 묶음과 `$ym` 묶음에는 읽기 권한을 주지 않았다 → **남의 것을 훑을 수 없다**
- **쓰기** — `$sid` 칸에 통짜 `.write` 를 주지 않았다.
  본인이 쓸 수 있는 건 `items/$fid/ok·okAt·okBy` · `done` · `doneAt` · `doneBy` ·
  `deviceHint` · `objection` **뿐**. `amount` · `total` · `name` 에는 규칙이 없으므로
  **금액은 못 고친다**
- **되돌리기** — `done` 은 재무권한자도 쓸 수 있다(대표가 완료를 풀어 준다).
  `ok` 와 `objection` 은 본인만

`.validate` 로 `ok`·`done` 은 참/거짓만, 시각 문자열은 40자, 이의 사유는 500자로 제한했다.

uid 는 발행할 때 `data/user_accounts` 의 매핑을 보고 심는다.
uid 가 비어 있으면(계정 미연결) 그 사람 것은 **아무도 못 읽으므로**,
발행 미리보기에서 **uid 없는 사람을 먼저 경고**해야 한다.

점검 스크립트: `rules-perf-check.js` (20가지 — 남의 것 못 훑는지, 금액 쓰기 규칙이
없는지, 기존 항목이 안 빠졌는지)

## 화면 셋

### 1. 발행 (pu-erp 성과관리 `hr/perf` — `PerfManagement`)
- `[이달 확인 발행]` — 그 달 확정 입금의 `perfShares` 를 sid 로 묶는다
- 미리보기: 사람 / 건수 / 합계, uid 없는 사람 경고, 이미 발행됐으면 차이만 표시
- 재발행은 덮어쓰지 않고 **새 항목만 추가**한다 (이미 체크한 걸 날리면 안 된다)
- `perfExclude` · `isPersonalIncome` 건은 제외 (지금 성과관리와 같은 기준)

### 2. 본인 확인 — 업무관리 안 '성과급' 메뉴 (work.html)
work.html 은 vanilla JS 다. React 아님.

- 메뉴 추가 지점: `route()` 의 `['my','team','stats','kb','ho','archive']` 배열과
  `crumbs` 객체에 `perf` 를 넣고 `renderPerf()` 를 붙인다. 좌측 nav 에 `nav-perf` 항목 추가
- 읽는 곳: `fbDb.ref('data/perf_confirm/'+ym+'/p/'+S.me.sid)` — **`S.vsid` 아님, `S.me.sid`**
- 줄을 누르면 **계산 근거가 펼쳐진다** — 입금일 · 입금액 · 부가세 뺀 금액 · 내 비율 · 결과.
  이걸 봐야 맞는지 틀린지 판단할 수 있다. 근거 없이 체크만 시키면 확인이 아니라 서명일 뿐이다
- 펼친 자리에서 바로 **이의**를 남긴다 → `objection/byItem/<fiId>/{text, at}`
- 금액은 처음에 `●●●`, 누르면 보임
- 대표 답변(`items/<fiId>/reply`)이 있으면 그 줄 아래에 표시.
  **따로 알리지 않는다** — 성과급 화면에 들어와야 보인다
- 완료하면 본인은 못 푼다. 대표만 풀 수 있고 푼 것도 기록
- 폰: `viewport` 는 이미 있다. `@media` 가 3개뿐이라 이 화면만 세로로 쌓이게 만든다

#### 줄의 상태는 셋
`미처리` / `확인함(ok)` / `이의(objection.byItem 에 글이 있음)`

**`확인 완료` 는 모든 줄이 `확인함` 또는 `이의` 여야 눌린다.**
애매하게 두고 넘어갈 수 없게 한다.

### 3. 안내 (같은 work.html)
- `data/perf_confirm/<이번달>/p/<내sid>` 가 있는데 `done` 이 아니면
- 하루 첫 로그인 팝업 1회(`localStorage` 로 날짜 기억) + 상단 빨간 띠 상시
- 누르면 **같은 화면 안** '성과급' 메뉴로 이동 (`go('perf')`). 다른 프로그램으로 안 보낸다
- 팝업은 `showModal(html)` / `closeM()` 을 그대로 쓴다
- **대표 답변이 와도 띠를 다시 띄우지 않는다** (대표님 결정). 조용히 화면에만 남긴다

### 4. 현황판 (pu-erp 성과관리)
- `완료 5명 · 이의 처리중 2명 · 미확인 1명` — **이의가 열려 있는 사람은 완료로 세지 않는다**
- 미확인자 목록
- **이의 목록** — 사람 · 날짜 · 업체 · 금액 · 사유 · 접수일
  - `[입금 건 보기]` → `sessionStorage['global_search_focus'] = {title: 업체명, ts: Date.now()}`
    직후 `window.navigateTo('fin/income')`.
    다른 화면이 이미 쓰는 방식(`useGlobalSearchFocus`)이라 새로 만들 것이 없다
  - `[원천 보기]` → 같은 방식으로 `sourceKind` 에 따라
    `biz/case` · `biz/consulting` · `biz/fund` · `biz/other` 로
  - `[답변하고 처리]` → `items/<fiId>/reply/{text, at, by, state:'done'}`
- 미확인자에게 알림 보내기(추후)

### 2단계에서 만든 것 — work.html (vanilla JS)

좌측 메뉴 `⭐ 내 성과급`(`nav-perf`), 라우팅 `perf`, 안 끝난 달 수를 배지로.

| 이름 | 하는 일 |
|---|---|
| `pcMySid()` | **`S.me.sid` 만 돌려준다.** 성과급 코드 어디서도 sid 를 밖에서 안 받는다 |
| `pcMonths(n)` · `pcLoad()` | 달 목록을 훑을 권한이 없어(남의 것까지 보임) **최근 넉 달을 하나씩 두드린다.** 막히면 조용히 넘긴다 |
| `pcRowState(p,fid)` | `todo` / `ok` / `obj`. **물린 이의(`withdrawnAt`)는 이의로 안 친다** |
| `pcCounts` · `pcAllHandled` | 모든 줄이 `ok` 또는 `obj` 여야 `확인 완료` 가 눌린다 |

| `renderPerf` · `pcMonthHTML` · `pcRowHTML` | 카드 세로 배치 — 폰에서 그대로 쓴다 |

동작 요점 — 줄을 누르면 **계산 근거**(입금일·입금액·부가세 뺀 금액·비율·결과)가 펼쳐지고
거기서 `✓ 맞습니다` / `⚠ 다릅니다`. **이의를 남기면 그 줄의 확인이 자동으로 풀린다**(둘은 같이 설 수 없다).
물릴 때는 `withdrawnAt` 만 찍고 **사유는 안 지운다**. 금액은 기본 `●●●`.
마감이 지나면 빨갛게 알리되 **막지 않는다**.

검증: `pcw-test.js` 37 · 실 DOM 하네스 48(본인고정 6 + 화면·확인 12 + 이의 16 + 완료·마감 14)
· 360px 폭 8 · `node --check`.

1단계 끝나면 대표 혼자 8월분으로 시험해 볼 수 있다.
2단계까지 끝났으니, 발행하면 직원이 실제로 확인할 수 있다.
다만 **아직 안내(띠·팝업)가 없어서** 직원이 메뉴를 눌러야 보인다.

```

```

막지 않는다. 확인은 계속 할 수 있다.
대신 현황판에 **늦은 사람으로 표시**되고 업무관리 띠가 그대로 남는다.
막아 버리면 확인을 못 받게 되어 목적이 뒤집힌다.

### 이의 철회
`objection/byItem/<fiId>/withdrawnAt` 에 시각을 찍는다. **`text` 는 지우지 않는다.**
현황판에 회색 `철회됨 8/16` 으로 남아 대표가 "이의가 있었다가 물렸다"를 안다.
게시된 규칙에서 직원은 `objection` 아래 전체를 쓸 수 있으므로 **재게시 불필요.**
`pcfCount()` 는 철회된 이의를 '열린 이의'로 세지 않는다.

pu-erp 성과관리 `직원별` 탭에 `⭐ 이달 확인 발행` 단추와 발행 창이 들어갔다.

만든 것 (모두 `PerfManagement` 바로 위, 블록 7):

| 이름 | 하는 일 |
|---|---|
| `pcfStamp(x)` | `금액\|비율\|역할` 지문 |
| `pcfPickItems(perf)` | `matched`·`personal` 중 **0원 아닌 것만** |
| `pcfBuildRows(empPerfs, users, uidBySid)` | 사람별로 묶기. 담을 게 없으면 빠짐 |
| `pcfDiff(rows, prev)` | 이미 나간 것과 견주기 (`new`/`update`/`same`, 추가·풀림·유지·빠짐) |
| `pcfMergeOne` · `pcfMergeAll` | 서버에 쓸 것. 확인·이의·답변을 살리고 지문 바뀐 것만 푼다 |
| `pcfLoadUidMap()` | `uid_roles` 를 뒤집어 사번→계정 (계정 여럿이면 `updatedAt` 최근 것) |
| `pcfLoadMonth(ym)` · `pcfWrite(ym, upd)` | 읽기·쓰기. 쓰기는 `update` 라 남의 칸을 안 건드린다 |
| `pcfCount(prev)` | 완료·이의열림·미확인. **이의 열린 사람은 완료로 안 셈** |
| `pcfDefaultDue(nowIso)` | 발행일 +7일 |
| `PerfPublishModal` | 발행 창 |

기존 `calcEmpPerf(sid, incomeList)` 를 그대로 쓴다 → **성과관리 화면과 발행본이 어긋날 수 없다.**
