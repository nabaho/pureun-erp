# 매달 성과급 확인 기능 — 계획

작성 2026-08-01 · 상태 **계획 확정, 구현 전**

매달 초 각자 자기 성과급 내역을 직접 확인하고, 누가 언제 확인했는지 기록으로 남긴다.
폰에서도 된다.

---

## 왜 '발행' 단계가 필요한가

성과급 원본은 `finance_income` 에 있고, 각 입금 건 안에
`perfShares[] = {sid, name, role, pct, amount}` 로 분배가 박혀 있다.

이 노드의 규칙은 **재무 권한자만 읽기/쓰기**다.

```
"finance_income": {
  ".read":  "root.child('uid_roles').child(auth.uid).child('fin').val() == true",
  ".write": "root.child('uid_roles').child(auth.uid).child('fin').val() == true"
}
```

→ **직원 본인은 자기 성과급을 못 읽는다.** 규칙을 풀면 남의 것까지 다 보이므로 풀면 안 된다.

그래서 재무 권한자가 그 달치를 **사람별로 추려 확인용 사본을 발행**하고,
직원은 사본만 읽는다. 원본은 안 건드린다.
덤으로 "확인 대상이 확정된 시점"이 분명해진다.

---

## 정해진 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 안내 강도 | 하루 첫 로그인 팝업 1회 + 상단 빨간 띠 상시 | 매번 막으면 월초에 일을 못 한다 |
| 확인 화면 | **별도 작은 파일** (`pu-perf.html`) | pu-erp 는 3.6MB — 폰에서 체크 5개 하려고 받을 수 없다. 명함첩·촬영기가 이미 이 방식(manifest+SW)이라 홈화면 추가 가능 |
| 대상 월 기준 | **입금 확정된 달** | 지금 성과관리가 쓰는 기준과 같다. 급여 지급월 기준이면 한 달 늦게 확인하게 된다 |

발행·현황판은 pu-erp 성과관리 안에 둔다(대표가 PC 에서 하는 일).

## 데이터 자리

새 최상위 노드 `perf_confirm` — `finance_income` 과 나란히.

```
perf_confirm/
  2026-08/                         대상 월 (입금 확정월)
    meta/  openedAt openedBy closedAt totalPeople totalAmount
    p/
      <sid>/
        uid                        ← 발행 때 심는다. 규칙이 이걸로 본인을 가린다
        name  total  itemCount
        items/
          <fiId>/                  finance_income 레코드 id — 추적용
            date source coName role pct amount
            ok  okAt  okBy
        done  doneAt  doneBy  deviceHint
        objection/  text  at
        reopen/     at by reason   ← 대표가 완료를 푼 기록
```

### 권한 규칙 (게시 필요)

```json
"perf_confirm": {
  ".read": "root.child('uid_roles').child(auth.uid).child('fin').val() == true",
  "$ym": {
    "meta": { ".read": "auth != null && auth.token.firebase.sign_in_provider === 'password'" },
    "p": {
      "$sid": {
        ".read":  "data.child('uid').val() === auth.uid || root.child('uid_roles').child(auth.uid).child('fin').val() == true",
        ".write": "root.child('uid_roles').child(auth.uid).child('fin').val() == true",
        "items": { "$fid": {
          "ok":   { ".write": "root.child('perf_confirm').child($ym).child('p').child($sid).child('uid').val() === auth.uid" },
          "okAt": { ".write": "root.child('perf_confirm').child($ym).child('p').child($sid).child('uid').val() === auth.uid" },
          "okBy": { ".write": "root.child('perf_confirm').child($ym).child('p').child($sid).child('uid').val() === auth.uid" }
        }},
        "done":   { ".write": "root.child('perf_confirm').child($ym).child('p').child($sid).child('uid').val() === auth.uid || root.child('uid_roles').child(auth.uid).child('fin').val() == true" },
        "doneAt": { ".write": "root.child('perf_confirm').child($ym).child('p').child($sid).child('uid').val() === auth.uid || root.child('uid_roles').child(auth.uid).child('fin').val() == true" },
        "doneBy": { ".write": "root.child('perf_confirm').child($ym).child('p').child($sid).child('uid').val() === auth.uid || root.child('uid_roles').child(auth.uid).child('fin').val() == true" },
        "objection": { ".write": "root.child('perf_confirm').child($ym).child('p').child($sid).child('uid').val() === auth.uid" }
      }
    }
  }
}
```

핵심 — **본인은 `ok` / `done` / `objection` 만 쓸 수 있고 금액은 못 고친다.**
uid 는 발행할 때 `data/user_accounts` 의 매핑을 보고 심는다.
uid 가 비어 있으면(계정 미연결) 그 사람 것은 아무도 못 읽으므로,
발행 미리보기에서 **uid 없는 사람을 먼저 경고**해야 한다.

## 화면 넷

### 1. 발행 (pu-erp 성과관리)
- `[이달 확인 발행]` — 그 달 확정 입금의 `perfShares` 를 sid 로 묶는다
- 미리보기: 사람 / 건수 / 합계, uid 없는 사람 경고, 이미 발행됐으면 차이만 표시
- 재발행은 덮어쓰지 않고 **새 항목만 추가**한다 (이미 체크한 걸 날리면 안 된다)
- `perfExclude` · `isPersonalIncome` 건은 제외 (지금 성과관리와 같은 기준)

### 2. 본인 확인 (`pu-perf.html`, 새 파일)
- 자기 것만. 항목마다 체크, 전부 체크해야 `확인 완료` 활성
- `다른 것 같습니다` → 사유 남기면 대표에게 표시
- 완료하면 본인은 못 푼다. 대표만 풀 수 있고 푼 것도 기록
- 폰 우선 레이아웃 + manifest + service worker (명함첩 방식 그대로)

### 3. 업무관리 안내 (work.html)
- `perf_confirm/<이번달>/p/<내sid>/done` 을 보고 안 됐으면
- 하루 첫 로그인 팝업 1회(`localStorage` 로 날짜 기억) + 상단 빨간 띠 상시
- 띠·팝업에서 `pu-perf.html` 로 바로 이동
- work.html 은 `finance_income` 을 못 읽으므로 **금액은 안 보여 주고** 건수만 안내

### 4. 현황판 (pu-erp 성과관리)
- 발행 대비 완료 인원, 미확인자 목록, 이의 신청 목록
- 미확인자에게 알림 보내기(추후)

## 순서

| 단계 | 무엇 | 위험 |
|---|---|---|
| 1 | 데이터 자리 + 권한 규칙 + 발행 화면 | 직원 화면 안 건드림. **없음** |
| 2 | `pu-perf.html` 본인 확인 화면 | 새 파일이라 기존에 영향 없음 |
| 3 | work.html 안내 (팝업 + 띠) | 전 직원이 보는 화면 — 여기가 유일한 고비 |
| 4 | 현황판 + 폰 홈화면 안내문 | 낮음 |

1단계 끝나면 대표 혼자 8월분으로 시험해 볼 수 있다.

### 대표가 직접 해야 하는 것
- **1단계 전** Firebase 콘솔에서 위 `perf_confirm` 규칙 게시 (기존 규칙에 블록 추가)
- 2단계 후 폰에서 홈화면 추가

---

## 아직 안 정한 것

- 이의 신청이 들어오면 어떻게 처리하나 (입금관리에서 고치고 재발행? 그 항목만 정정?)
- 대상자 범위 — 성과급 있는 사람만인가, 0원인 사람도 "0원 확인"을 시키나
- 퇴사자 미정산 성과급(이미 있는 기능)과의 관계
- 확인 마감일을 두나 (예: 매월 10일)
