## 4. 현행 구조의 한계 (변경 이유)

- 첨부 원본은 IndexedDB `kcareer_files`에 **base64로 저장**(`saveFileUnified`, kcareer.html:1412).
  base64는 원본의 약 1.33배 → 3.75 GB면 **약 5 GB**. 브라우저 저장 한도·메모리로 불가.
- `getAllFilesFromIDB()`(kcareer.html:1449)와 `getStorageFilesAsync()`(:1490)가
  **모든 파일의 base64를 한 번에 메모리로 적재**한다. 이 규모에서 확실히 멈춘다.
- 메타데이터는 localStorage → `fbScheduleAuto` → RTDB `kcareer/`. **원본은 클라우드에 없다**
  → 지금도 다른 기기에서는 첨부 원본이 열리지 않는다.
- `ocrDrop`(:3510)은 파일 1개씩 순차 API 호출. 3,979개 전량 OCR은 시간·비용 모두 비현실적.

## 6. 데이터 모델

### 6.1 신규 스토어 `submission` (제출서류)

localStorage `kc_submission` → RTDB `kcareer/submission`

```js
{
  id: 'SB0001',
  year: '2019',                                  // 경로 20NN년 또는 파일명
  org: '경제진흥원',                              // 건 폴더명에서 추출
  title: '2019경제진흥원컨설턴트',                 // 건 폴더명 원문
  caseDir: '7. 컨설턴트,위원신청등/2019년/2019경제진흥원컨설턴트',
  files: [{ name, relPath, size, mtime, ext }],  // 건 안 파일 목록
  fileCount: 7,
  src: 'fs',
  scanId: 'S20260731-1',                         // 되돌리기 단위
  savedAt: '2026-07-31T...'
}
```

`CAREER_CFG`에 `submission` 항목을 추가한다(cols: ID·연도·기관·건 이름·서류수·관리).
검색 필드(`qFields`)는 `['org','title','caseDir']`.

### 6.2 기존 스토어(`wiccok`·`cert`·`certdoc`) 확장 필드

```js
src: 'fs',                                       // 'idb'(기존 base64) / 'fs'(로컬 참조)
relPath: '1. 위촉장/2015 질병판정위원회 위원 위촉장 (2015.05.07).pdf',
fileSize: 431104, fileMtime: '2015-05-07T...',
scanId: 'S20260731-1'
```

기존 레코드는 `src` 없음 = `'idb'`로 간주한다. **기존 데이터는 변경하지 않는다.**

### 6.3 원본 존재 판정

`fileExists(id)`(:1430)는 base64 기준이므로 `src:'fs'`를 모른다. 판정 함수를 하나 둔다.

```js
function hasOriginal(r){ return r && r.src==='fs' ? !!r.relPath : fileExists(r.id); }
```

`_dupRow`(:3348) 등 `fileExists`를 쓰는 표시부는 `hasOriginal`로 교체한다.

### 6.4 폴더 접근권한 보관

- IndexedDB `kcareer_fs` / objectStore `handles` / key `'rootDir'`에
  `FileSystemDirectoryHandle`을 저장한다(구조화 복제 가능).
- 재방문 시 `queryPermission({mode:'read'})` → `'granted'`면 그대로,
  `'prompt'`면 사용자 클릭(제스처) 후 `requestPermission()`.
- 권한이 없으면 목록·검색·증명서 발급은 정상 동작하고 **원본 열기만** 막힌다.

### 6.5 원본 열람

```
relPath 분해 → root에서 getDirectoryHandle 체인 → getFileHandle
→ getFile() → URL.createObjectURL → 새 탭
```

OneDrive 클라우드 전용 파일은 **이 시점에만** 내려온다. 스캔 단계에서는 이름·크기만 읽으므로
3.75 GB가 내려오지 않는다.

## 7. 자동 판정 규칙

### 7.1 읽지 않는 파일

```
^(\.~lock\.|~\$)   엑셀·한글 임시·잠금 파일
4NZFL.DOCX         OneDrive 부산물 (0바이트, 모든 폴더에 존재)
```

### 7.2 이름 정리 (core)

확장자를 뗀 이름에서 아래를 제거하고 끝의 공백·`_`·`-`를 다듬는다.

```
\(\s*20\d{2}[.\-]\d{1,2}[.\-]\d{1,2}\s*\)    (2015.05.07) 형태의 발급일
\s*\(\d+\)\s*$                                (1), (2) 형태의 사본 연번
```

### 7.3 3단계 판정 — "이름 끝을 본다"

```js
원본확장자 = /\.(pdf|jpg|jpeg|png|hwp|hwpx)$/i
결과물끝   = /(위촉장|위촉계약서|재위촉|위촉서|표창장|표창|포상|상장|자격증|수료증|이수증|협약서|경력증명서|실적증명서|참여확인서|수행확인서)$/
결과물어디든 = /위촉장|위촉계약|재위촉|표창|포상|상장|자격증|수료증|이수증|협약서|경력증명|실적증명|참여확인|수행확인/
부정어 = /동의서|신청서|제출|공고|양식|서식|명단|시나리오|좌석|추천\s*계획|모집|목록|초안|회의록|회의자료|교재|자료집|매뉴얼/
```

| 판정 | 조건 | 처리 | 실측 건수 |
|---|---|---|---|
| 🟢 확실 | 원본확장자 && core가 결과물끝 && !부정어 | 기존 목록에 자동 승격 | **239** |
| 🟡 애매 | 🟢 아니고 결과물어디든 && !부정어 | 보류 목록 — 사람이 체크한 것만 승격 | **220** |
| ⚪ 제출서류 | 나머지 | `submission`에만 등록 | **3,520** |

**"이름 끝"을 보는 이유** — 실제 파일명에 이런 것들이 섞여 있다.

| 파일명 | 판정 | 이유 |
|---|---|---|
| `2015 질병판정위원회 위원 위촉장.pdf` | 🟢 | 끝이 위촉장 |
| `위촉장 목록.xlsx` | ⚪ | 목록표 |
| `위촉식 시나리오.hwp` | ⚪ | 행사 진행표 |
| `제1기 노동권익보호관 위촉 대상자 명단.hwp` | ⚪ | 명단 |
| `위촉 동의서.hwp` | ⚪ | 본인이 제출한 서류 |

> ⚠ **부정어에 `회의`를 넣지 말 것.** 처음 규칙에 넣었더니 `천안북부상공회의소 위촉장`,
> `충남북부상공회의소 자문위원 위촉장` 등 진짜 위촉장 3건이 "상공**회의**소"에 걸려
> 잘못 제외되었다. `회의록`·`회의자료`로 좁혀야 한다.
> 현재 규칙에서 부정어로 보류되는 것은 `신청서 및 실적증명서.pdf` 1건이며 이는 올바른 보류다.

### 7.5 연도·기관 채우기

**연도** (우선순위)
1. 파일명의 `20\d{2}`
2. 경로의 `(20\d{2})년` 폴더 — 7번은 대부분 여기서 나온다
3. 파일 수정일의 연도 + **확인필요 플래그**

**기관**
1. 파일명에서 추출
2. 없으면 건 폴더명에서 앞쪽 연도·숫자를 떼고 사용 (`2019경제진흥원컨설턴트` → `경제진흥원컨설턴트`)

## 9. 중복 처리

- **1차(스캔 중)**: `name + size`가 같으면 사본으로 보고 1건만 등록, 나머지는 미리보기에
  "사본 N건"으로 표시. 실측 예: `공인노무사자격증.pdf` 2건, `4. 협약서.hwp` 2건.
- **2차(등록 후)**: 기존 중복관리 화면을 그대로 쓴다. `650fd14`에서 만든 2단계 판정
  (완전일치 = 중복 / 시기만 다름 = 유사)과 `dup_dismiss` 제외 목록을 재사용한다. 신규 개발 없음.

## 10. 오류 처리

| 상황 | 동작 |
|---|---|
| 폴더 권한 없음/거부 | 목록·검색·증명서 정상. 원본 열기만 "폴더 연결 필요" 안내 |
| 파일 이동·개명·삭제 | 원본 열기 실패 → "원본을 못 찾음 — 다시 스캔하세요". **레코드는 유지** |
| 다른 PC | 그 PC에서 폴더 1회 연결 |
| 폰 | 목록·검색·증명서 가능. 원본 열기 불가 안내 |
| 스캔 중 예외 | 해당 파일만 건너뛰고 실패 목록에 남김. 전체 중단하지 않음 |

**앱은 이 폴더의 파일을 이동·개명·삭제하지 않는다. 읽기 전용이다.**

OCR은 자동 실행하지 않는다. 개별 건에서 기존 `reOcrForm`(:2922)을 누를 때만 동작하며,
`src:'fs'` 레코드도 읽을 수 있도록 원본 취득 경로를 `hasOriginal`/로컬 열람 함수에 연결한다.

3. **기존 데이터 보호**: 기존 레코드·기존 base64 첨부는 읽기만 한다. 신규 필드만 추가한다.

## 13. 가정

- 사용 브라우저는 Chrome 또는 Edge 데스크톱이다(File System Access API 필요).
  앱은 https(`nabaho.github.io`)로 서비스되므로 보안 컨텍스트 요건은 충족한다.
- 지원하지 않는 브라우저에서는 "폴더 연결" 버튼을 숨기고 기존 첨부 방식만 노출한다.
- 서류 폴더의 최상위 구조(`1. 위촉장` ~ `9. 기타전문가`, 7번의 연도 폴더)는 유지된다.
