# 급여데이터함 설계서

2026-08-13 확정 · 대표 결정 기준 · 새 앱 `pu-paydata.html`

> **한 줄 요약**
> 급여 아웃소싱에 쓰는 근로자·임금 자료를 **사업장별로** 모으고, 거기서 읽어낸 **값을 급여관리에 바로 넘기는** 별도 앱. 사진첩과 부품은 공유하고 함은 분리한다.

---

## 1. 왜 별도 함이 필요한가

지금 급여자료는 **갈 곳이 없다.**

- 사진첩은 급여서류로 판독되면 `🚫 보관 안 함 — 지워 주세요`로 막는다 (2026-08-06 보유기준 결정). 사진첩의 보유기준은 1년/5년이라 급여자료의 법정 3년과 맞지 않고, 권한도 「내 것 / 전체」 두 단계뿐이다.
- 급여관리(`payroll-os.html`)의 「수신함」은 **파일명·메일 제목만** 기록한다. 실제 자료는 어디에도 담기지 않고, 사람이 파일명을 손으로 붙여넣어야 도착 표시가 된다.
- 그래서 급여자료가 사진첩으로 흘러들고, 사진첩은 그것을 지우라고 한다.

한 함에 두면 **보관 기간·볼 수 있는 사람·파일 종류**가 셋 다 달라 한쪽 기준이 다른 쪽을 망친다. 그래서 나눈다.

### 두 함의 경계 (대표 결정 2026-08-13)

| | 푸른사진첩 | 급여데이터함 |
|---|---|---|
| 무엇 | **기업 자체** 정보 — 담당자, 계약정보, 현장사진 | **근로자·임금** 자료 — 근로계약서, 근태, 급여자료 |
| 정리 축 | 종류별 (분류 탭) | **사업장별** (사업장 서랍) |
| 연결되는 앱 | 컨설팅·명함첩·업체관리 | **급여관리(급여 아웃소싱)** |
| 보유기간 | 증빙 5년 · 나머지 1년 | **일괄 3년** (법정) |

## 2. 담는 것

대표 결정 2026-08-13 — 아래 전부 담는다.

| # | 종류 | 탭 이름 | 월과의 관계 |
|---|---|---|---|
| 1 | 근로계약서 등 사업장마다 계속 두는 서류 | 근로계약서 | 월 무관 — 항상 보인다 |
| 2 | 고객사가 보내오는 근태 원자료 (출근부·출역표·시간) | 근태 | 귀속월별 |
| 3 | 고객사가 보내오는 급여대장·노임대장 | 급여대장 | 귀속월별 |
| 4 | 우리가 만들어 내보내는 것 (명세서·이체목록·신고서) | 우리 산출물 | 귀속월별 |
| 5 | 수기작성 서류, 캡쳐, 아직 종류를 못 가린 것 | 기타 | 귀속월별 |

**주민등록번호는 담지 않는다.** 급여관리가 이미 그 원칙으로 돌고 있다(성명 매칭). 판독 중 주민번호가 읽히면 값 층에 넣지 않는다.

## 3. 두 층으로 나눈다 — 원본과 값

이 앱의 핵심이다. **근태표 사진 한 장은 자료지만, 급여 계산에 쓰이는 것은 거기서 읽어낸 값이다.**

| | 원본 층 | 값 층 |
|---|---|---|
| 무엇 | 사진·캡쳐·엑셀·PDF 그 자체 | 근로자명, 근무일수, 시간, 금액 |
| 어디에 | 파일 창고 (Storage) | 실시간DB (표) |
| 왜 있어야 하나 | **근거.** 나중에 다투면 이것을 내놓는다 | 급여 프로그램에 넣을 재료 |
| 보유 | 3년 | 3년 (원본을 지워도 값은 남는다 — 그래서 같이 3년) |

### 값 한 줄의 모양

```
사업장ID · 사업장명 · 귀속월 · 근로자 · 항목 · 값 · 출처(원본번호) · 넣은 사람 · 확인여부
```

**값 한 줄마다 원본 번호가 반드시 붙는다.** 급여관리에서 어떤 숫자를 눌렀을 때
「이 값은 8/12 홍길동이 올린 근태표 3쪽에서 나왔습니다」가 뜨고 원본이 열려야 한다.
이것이 없으면 몇 달 뒤 「이 수당 어디서 나온 것이냐」에 답할 수 없다.

**캡쳐 한 장에 근로자 열 명이 섞여 있으면 값은 열 줄이 된다.** 사진 한 장 = 값 한 줄이 아니다.

### 값이 채워지는 방식

기계가 먼저 읽고, **계산이 맞아떨어지는 것만 자동으로 들어간다.** 합계가 안 맞거나 못 읽은 칸은
노란 표시로 남아 사람이 채운다. (판독 층 `js/pu-doc-read.js`를 그대로 쓴다 — 2026-08-08 결정
「기계 검증 통과분만 자동 입력」과 같은 원칙. 전부 사람 확인으로 되돌리지 않는다.)

### 같은 자료를 두 번 올렸을 때

사업장·귀속월·근로자·항목이 겹치면 **「이미 있습니다 — 덮을까요」**를 묻는다.
묻지 않으면 근무일수가 두 배가 된다. **캡쳐는 실제로 두 번 올라온다.**

## 4. 누가 무엇을 할 수 있는가 (대표 결정 2026-08-13)

권한 경계가 **사람**이므로 담기는 자리도 사람별이다. 화면에서 가리는 것은 보호가 아니다 —
서버 규칙이 막는다. 사진첩이 이미 이 구조다.

| 대상 | 보기 | 수정·저장 |
|---|---|---|
| 내 자리 | ○ | ○ |
| 남의 자리 | ○ (이름을 골랐을 때만) | ✗ — 단추가 안 그려지고, 눌러도 서버가 거절 |
| 맡은 자리 (휴가 대리) | ○ | ○ (기간 안에서만) |

**사업장은 자료 한 건마다 붙는 이름표**다. 그래서 내 자리 안에서 사업장별로 묶어 보여줄 수 있다.

### 남의 것은 이름을 골라야 열린다

한 번에 전체가 보이는 화면을 **만들지 않는다.** 기술적으로도 그렇게 된다 — 사람별 자리는
위에서 통째로 긁을 수 없고, 누구 자리인지 지정해야 열린다.

두 군데에 「이름 고르기」가 붙는다.

1. **사업장 서랍 안** — 「이 업체 자료를 가진 다른 담당자: 홍길동 12장」 줄. 눌러야 열린다.
2. **위쪽 담당자 고르개** — 직원 명단에서 한 사람을 고른다. 들어간 동안 화면에
   「홍길동 자리 — 보기만」이 계속 떠 있다.

### 열람에는 사유를 적는다 (대표 결정 2026-08-13)

범위는 **전 직원**이지만, 남의 자리를 열 때 **「왜 보는가」를 한 줄 적어야** 열린다.
적은 사유는 열람 기록에 남는다.

```
언제 · 누가 · 누구 자리를 · 왜 봤는가
```

급여자료라 이것은 있어야 한다. 점검을 받을 때 내놓을 것이 필요하다.

### 휴가 대리 — 기간을 정해 넘긴다

내 자리 설정에 **「자리 맡기기」**를 둔다: *누구에게 · 언제부터 언제까지*.

- 맡은 사람은 그 기간에만 내 자리를 **수정·저장**할 수 있다.
- **기간이 지나면 저절로 닫힌다.** 돌아와서 회수를 잊어도 열려 있지 않다.
  → 사람이 거둬야 닫히는 권한은 반드시 열린 채로 남는다. 이것이 이 설계의 핵심이다.
- 맡긴 동안 내 화면에는 「홍길동이 맡고 있음 (8/20까지)」, 맡은 사람 화면에는 「맡은 자리 1곳」.
- 대리인이 고친 자료에는 **누가 고쳤는지** 남는다. 내 자리에 있는 자료라도 손댄 사람이 표시된다.
- 기간 중에도 바로 거둘 수 있다.
- **원본과 값에 같이 걸린다.** 원본만 맡기고 값은 못 고치면 대리를 맡긴 의미가 없다.

## 5. 화면

### 첫 화면 — 사업장 목록

**업체관리(`companies`) 명단을 기준으로 한다** (대표 결정 2026-08-13).
업체마다 고유번호(`companyId`)가 있어 다른 앱과 연결된다. 데이터함이 세 번째 명단을
만들지 않는다.

업체 한 줄에 보이는 것: 업체명 · 이번 달 자료 도착 여부 · 담긴 장수 · 값 확인 필요 건수.

**장수와 확인 필요 건수는 「내 자리 기준」이다.** 도착 여부만 7장의 얇은 칸에서 읽어
전체를 반영한다 — 남이 담은 자료의 장수까지 첫 화면에 세면 4장의 권한 경계가 새어 나간다.

급여관리 설정 카드에만 있고 업체관리에 없는 사업장은 **「명단에 없음」으로 따로 모아** 보여준다.
숨기지 않는다 — 숨으면 그 업체가 빠진 줄도 모른다.

### 미정 대기 칸 — 들어온 것이 먼저 놓이는 곳

**들어오는 자료가 곧장 사업장 서랍으로 갈 수 없는 경우가 세 가지 있다.**

1. **메일 자동수신** — 서버가 담는다. 서버는 사람이 아니므로 「누구 자리」가 없다.
2. **사진첩에서 보낸 한 장** — 사진첩은 사업장·귀속월을 받지 않는다. 어느 서랍인지 모른다.
3. **현장에서 급하게 찍은 것** — 사업장을 고를 겨를이 없다.

그래서 서랍 앞에 **미정 대기 칸**을 둔다. 일단 받고, 사업장·귀속월을 채우면 서랍으로 내려간다.

- 파일명·판독 글자에서 짐작해 **미리 채워 두고** 사람이 고친다. 빈칸으로 두면 아무도 안 채운다.
- 첫 화면 맨 위에 「미정 5건」이 늘 보인다. 서랍 안에 있으면 안 보이므로 잊힌다.
- **3일 넘게 묵으면 표시가 뜬다.** 대기 칸은 잠깐 머무는 곳이지 쌓아 두는 곳이 아니다.
- 대기 칸도 **사람별 자리**다. 메일 자동수신으로 들어온 것만 예외로 **공용 대기 칸**에 놓이고,
  누구든 집어서 자기 자리로 내려보낼 수 있다 — 집은 사람이 기록에 남는다.

### 사업장 서랍

위: **월 고르개** + **탭**(근로계약서 · 근태 · 급여대장 · 우리 산출물 · 기타)
아래: 사진첩과 같은 **격자**. 장수가 0인 탭도 남긴다.

근로계약서 탭은 월과 상관없이 항상 다 보인다 — 계약서는 월별 자료가 아니다.

서랍 안에 **값 표**로 넘어가는 줄을 둔다: 「이 달 값 12줄 · 확인 필요 3줄」.

### 값 표 화면

사업장·귀속월 기준 표. 확인 필요한 줄은 노란 표시. 값을 누르면 **출처 원본**이 열린다.

### 자리 맡기기 화면

내 설정 안. 맡길 사람·기간을 고르고, 지금 맡고 있는/맡긴 상태가 보인다.

## 6. 들어오는 길 네 개

| 길 | 상태 | 비고 |
|---|---|---|
| 폰으로 찍어서 바로 | 사진첩 부품 재사용 | 연속촬영 그대로 |
| PC에서 파일 올리기 | 새로 만든다 | 엑셀·PDF 포함 |
| 카톡·갤러리에서 공유 | 사진첩 방식 재사용 | ⚠ **안드로이드 전용** (애플이 막아 둠). 앱으로 설치돼 있어야 공유 목록에 뜬다 |
| 메일로 온 것 자동 수신 | **뒷 단계** | 아래 참고 |

**네 길 모두 미정 대기 칸을 지날 수 있다.** 사업장·귀속월을 아는 채로 올렸으면 곧장 서랍으로,
모르면 대기 칸으로 간다(5장). 「곧장 서랍뿐」으로 만들면 사진첩에서 보낸 한 장과 서버가
받은 메일은 들어올 곳이 없다.

### 메일 자동수신은 성격이 다르다

지금 서버(`functions/`)는 메일을 **보내기만** 한다(`sendMaterialMail`·`sendScheduledMail`,
다음메일 SMTP). **받는 기능은 없다.** 받으려면 서버가 메일함을 주기적으로 들여다보고
첨부를 꺼내 담는 새 기능이 필요하다.

그래서 **I단계로 미룬다.** 그 전에는 메일로 온 첨부를 PC에서 끌어다 올린다.
(급여 처리는 이 한 가지가 없어도 돈다 — 없다고 앱 전체가 멈추게 만들지 않는다.)

## 7. 급여 아웃소싱과 연결

### 도착 사실만 따로 얇게 쓴다

급여관리 「수신함」은 **전체 사업장 도착 현황을 한 화면에서** 봐야 한다. 그런데 사람별
자리를 다 열어야 알 수 있다면 4장의 권한 설계와 부딪힌다.

그래서 **「도착했다」는 사실만** 별도 칸에 쓴다 — 업체·귀속월·종류·장수·마지막 시각뿐.
**자료 본문도 값도 들어가지 않는다.** 수신함은 이 칸만 읽고, 실제 자료를 보려면
여전히 그 사람 자리로 들어가야 한다.

수신함의 판정(`정상`/`도착`/`미도착`/`지연`)과 독촉 문구 복사는 그대로 살아 있고,
**손으로 파일명 붙여넣기가 없어진다.**

### 값 넘기기

사업장 서랍에 **「이 달 값 급여관리로 넘기기」** 단추. 넘기면 급여관리 「급여 처리」가
재료가 들어간 상태로 시작한다. 지금은 엑셀을 다시 만들어 올려야 하는데 그 단계가 없어진다.

**넘긴 뒤에 값을 고치면** 급여관리에 「자료가 바뀌었습니다 — 다시 받을까요」가 뜬다.
조용히 덮으면 이미 확정한 명세서와 어긋난다.

### 넘기면 권한 띠가 끊긴다 — 넘긴 기록을 남긴다 (대표 결정 2026-08-13)

급여관리는 `payroll_os` 칸을 **통째로 한 번에** 읽는다(앱 구조가 그렇고, 접근 거부 안내에
「재무/급여·관리자 권한」이 적혀 있다). 사람별로 나뉘어 있지 않다.

그래서 데이터함에서는 남의 자료를 보려면 사유를 적어야 하는데, **같은 값이 급여관리로
넘어가면 급여관리에 들어갈 수 있는 사람은 사유 없이 다 본다.** 일반 직원은 급여관리에
못 들어가니 밖으로 새지는 않지만, **재무·급여 담당자에게는 사유 적기가 우회된다.**

**대표 결정: 사유는 받지 않고 「넘긴 기록」만 남긴다.** 넣는 것이 그 사람들의 일이므로
매번 사유를 적게 하면 일이 안 된다. 대신 언제·누가·어느 사업장·어느 귀속월·몇 줄을
넘겼는지 남긴다 — 새는 문이 발자취 없이 보이지 않게만 하지 않는다.

이 우회를 **계획서에 적어 둔 채로** 진행한다. 적어 두지 않으면 나중에 「데이터함은 사유를
받는다」만 기억하고 실제로는 안 받는 길이 있다는 것을 잊는다.

## 8. 사진첩과의 경계 처리

사진첩에서 급여서류로 읽히면 지금은 「지워 주세요」가 뜬다. 이것을
**「데이터함으로 보내기」**로 바꾼다. 한 장씩 사람이 눌러 넘긴다.

**보낸 자료는 「보낸 사람 자리」의 미정 대기 칸으로 간다.** 사진첩은 사업장·귀속월을 받지
않으므로 어느 서랍인지 알 수 없고, 남의 자리에 넣을 수도 없다(4장). 보낸 사람이 사업장을
채워 서랍으로 내려보낸다. 사진첩 원본은 휴지통으로 가서 30일 안에 되살릴 수 있다.

**그동안 쌓인 것을 한꺼번에 옮기는 이사는 하지 않는다** (대표 결정 2026-08-13).
급여자료는 데이터함에서 직접 받는다.

반대로 말하면 안 된다.

## 10. 담기는 자리 (기술)

### 실시간DB — 루트 `paydata`

| 경로 | 무엇 |
|---|---|
| `paydata/u/{uid}/items/{yyyymm}/{id}` | 자료 정보 — 사업장ID·사업장명·종류·귀속월·파일이름·창고경로·올린때·올린사람·손댄사람 |
| `paydata/u/{uid}/items/keep/{id}` | 월 무관 자료(근로계약서 등) |
| `paydata/u/{uid}/pending/{id}` | 미정 대기 칸 — 사업장·귀속월이 아직 없는 것 |
| `paydata/pending_shared/{id}` | 공용 대기 칸 — 서버가 메일로 받은 것. 집으면 자기 자리로 내려간다 |
| `paydata/u/{uid}/thumbs/{yyyymm}/{id}` | 격자용 작은 미리보기 주소 — 본문과 가른다 |
| `paydata/u/{uid}/values/{yyyymm}/{rowId}` | 값 한 줄 — 3장의 표 |
| `paydata/u/{uid}/deputy/{deputyUid}` | 자리 맡기기 — `{from, to, by}` |
| `paydata/u/{uid}/trash/...` | 휴지통 30일 |
| `paydata/owners/{uid}` | 이름 고르개용 얇은 명단 — 이름·담당 업체 수·최근 활동. **자료는 넣지 않는다** |
| `paydata/arrivals/{companyId}/{yyyymm}` | 도착 사실만 (7장) |
| `paydata/access_log/{id}` | 열람 기록 — 언제·누가·누구 자리·사유 |
| `paydata/handoff_log/{id}` | 넘긴 기록 — 언제·누가·어느 사업장·귀속월·몇 줄 (7장) |

**정보와 본문을 반드시 가른다.** 목록만 읽을 때 파일까지 내려받으면 앱이 느려진다
(명함첩이 실시간DB 1.7GB로 무료 한도를 넘길 뻔한 2026-08-09 사고와 같은 원인).

**쓰기는 반드시 다중 경로 update 한 번으로 한다.** 상위 노드를 통째로 `set` 하면 남의
자료가 지워진다(2026-07 실데이터 사고). 자료를 담을 때 자료 정보 · 미리보기 · 도착 칸을
**한 번에 함께** 쓴다 — 따로 쓰면 한쪽만 들어가고 도착 표시가 어긋난다.

### 파일 창고 — 루트 `pu_paydata`

`pu_paydata/{올린사람uid}/{yyyymm}/{id}.{확장자}`

⚠ **창고 규칙은 실시간DB를 볼 수 없다.** (Storage 규칙은 Firestore만 참조 가능)
그래서 대리인이 「주인 자리」 창고 경로에 직접 쓰게 만들 수 없다. 대신:

- 파일은 **항상 올린 사람 창고 자리**에 놓인다.
- 「누구 자리 소속인가」는 **실시간DB 정보**가 정한다. 대리인이 올린 파일도 DB상 주인 자리에 매인다.
- 지우기는 **DB 정보를 휴지통으로 옮기는 것**으로 한다. 창고 파일 실삭제는 30일 뒤 정리.
- **한계**: 창고 읽기는 로그인한 직원 전체로 열린다. 앱을 거치지 않고 주소를 직접 아는
  경우 열람 기록이 남지 않는다. 서명 주소(signed URL)로 막을 수 있으나 서버 작업이 커서
  1차 범위에서 뺀다. **이 한계를 대표님께 알린 상태로 진행한다.**

### 창고 주소를 하나로 못 박아야 한다 — 0단계

지금 앱마다 다르다. **셋이 다 살아 있을 수는 없다.**

| 앱 | 지금 설정된 창고 |
|---|---|
| 사진첩·기금·컨설팅·업무관리 | `pureun-erp.firebasestorage.app` |
| 명함첩 | `pureun-erp-photos` |
| 급여관리 | `pureun-erp.appspot.com` |

**0단계에서 콘솔로 어느 것이 실재하는지 확인하고 하나로 못 박는다.** 데이터함은 그것을 쓴다.

### 재사용하는 공용 부품

| 부품 | 쓰는 곳 |
|---|---|
| `js/pu-photo-queue.js` | 올리기 대기줄 — 신호 약해도 자료를 잃지 않는다 |
| `js/pu-doc-read.js` | 서류 판독 → 값 뽑기 |
| `js/pu-appbar.js` | 앱 사이 이동 (★ APPS 배열에 한 줄 추가 필수 — 빠뜨리면 오갈 수 없는 섬이 된다) |
| `js/pu-resilience.js` · `pu-health.js` · `pu-version.js` · `pu-backup.js` | 포털 공통 |
| 사진첩 촬영 화면 | 연속촬영 그대로 |

새로 만드는 저장 층: `js/pu-paydata-store.js` (`pu-photo-store.js`와 같은 원리 —
화면은 저장 방식을 모른다).

## 11. 만드는 순서

| 단계 | 무엇 | 누가 |
|---|---|---|
| **0** | 창고 주소 확인 → 실시간DB·창고 규칙 게시 | **대표님** (붙여넣을 내용은 내가 만든다) |
| **A** | 목업 승인 — 사업장 목록 / 서랍 / 값 표 / 자리 맡기기 | 대표님 확인 |
| **B** | 껍데기 · 포털 타일 · 사업장 목록 (읽기만, 저장 없음) | |
| **C** | 원본 담기 — 폰 촬영 · PC 올리기 · **미정 대기 칸** · 격자 · 탭 · 월 고르개 · 휴지통 | |
| **D** | 권한 — 이름 고르기 · 사유 입력 · 열람 기록 · 자리 맡기기 | |
| **E** | 값 층 — 판독 → 값 표 → 중복 경고 → 출처 되짚기 | |
| **F** | 급여관리 연동 — 도착 칸 · 값 넘기기 · 바뀜 알림 | |
| **G** | 사진첩 「데이터함으로 보내기」 단추 | |
| **H** | 카톡·갤러리 공유 받기 (안드로이드) | |
| **I** | 메일 자동수신 (서버 새 기능) | 뒷 단계 |

**0단계 없이는 C단계 첫 저장에서 반드시 막힌다.** 규칙은 콘솔이 진짜이고, 저장소 파일로
배포하면 사진첩·성과확인이 막힌 적이 있다 — 콘솔에 넣는 방식만 쓴다.

**A단계 목업 승인 없이 화면을 짓지 않는다.**

## 13. 범위 밖 (하지 않는다)

- **사진첩에 쌓인 급여서류 일괄 이사** — 대표 결정 2026-08-13. 한 장씩 보내는 길만 둔다.
- **자동 삭제** — 어디에도 만들지 않는다. 사람 확인 필수.
- **주민등록번호 저장** — 담지 않는다.
- **급여 계산 자체** — 급여관리 소관. 데이터함은 재료까지만.
- **서명 주소(signed URL)로 창고 읽기 잠그기** — 1차 범위 밖. 10장의 한계로 기록해 둔다.
- **사업장 명단을 데이터함에서 새로 만들기** — 업체관리 명단만 쓴다.

## 14. 위험과 주의

| 위험 | 어떻게 다루나 |
|---|---|
| 급여자료를 전 직원이 이름 골라 열람 가능 | 사유 입력 + 열람 기록으로 보완 (대표 결정). 개인정보 처리방침 반영 여부는 별도 판단 |
| 창고 직접 접근은 열람 기록이 안 남는다 | 10장에 한계로 명시. 서명 주소는 뒷 단계 |
| 급여관리로 넘어간 값은 사유 없이 열린다 | 넘긴 기록으로 발자취를 남긴다(7장, 대표 결정). 급여관리 자체가 재무·급여·관리자만 들어가므로 밖으로는 새지 않는다 |
| 미정 대기 칸이 쌓아 두는 곳이 된다 | 첫 화면 맨 위에 건수를 늘 띄우고 3일 넘으면 표시. 서랍 안에 숨기지 않는다 |
| 여러 세션이 같은 작업트리를 공유한다 | 커밋은 **경로를 지정**해서 한다. `git add .`만 하면 남의 파일이 섞인다 |
| 원격 main이 자주 앞서 있다 | push 전 반드시 `git pull --rebase origin main` |
| 규칙을 저장소 파일로 배포 | 하지 않는다. 콘솔이 진짜다 |
| 실시간DB 용량 | 정보와 본문을 갈랐고 본문은 창고로 간다. 격자 미리보기도 창고에 둔다 |

## 15. 결정 기록 (2026-08-13 대표 결정)

1. 담을 자료 — 고객사 원자료 · 우리 산출물 · 근로계약서 등 보존서류 · 폰 촬영 급여서류 · 수기 서류 **전부**
2. 들어오는 길 — 폰 촬영 · PC 올리기 · 메일 자동수신 · 카톡 공유 **네 개 다** (메일은 뒷 단계)
3. 정리 방식 — 사업장별 서랍, 안은 격자 + 탭 걸러보기
4. 사업장 명단 — **업체관리 기준** (고유번호로 연결)
5. 저장 — 파일 창고 (버킷 사용 가능, 주소는 0단계에서 통일)
6. 보유기간 — **3년** (법정 기준 그대로), 자동 삭제 없음
7. 권한 — 내 자리 전권 / 남의 자리 보기만 / **이름을 골라야** 열림 / **전 직원 가능하되 사유 입력**
8. 휴가 대리 — 기간을 정해 넘기고 **기간이 지나면 저절로 닫힌다**
9. 사진첩 — 「데이터함으로 보내기」 단추만. 일괄 이사 없음
10. 원본과 값을 **두 층으로** 나누고, 값에는 출처 원본번호를 반드시 붙인다
11. 값 자동 입력은 **기계 검증 통과분만**
12. 급여관리 연동 — 도착 사실만 얇게 + 값 넘기기 + 바뀜 알림
13. **미정 대기 칸을 둔다** — 사업장·귀속월을 모르는 채로 들어오는 길이 세 가지 있다.
    메일로 받은 것만 공용 대기 칸, 나머지는 사람별 대기 칸. 3일 넘으면 표시
14. **사진첩에서 보낸 것은 「보낸 사람 자리」의 대기 칸으로** 간다
15. **급여관리로 넘길 때는 사유를 받지 않고 「넘긴 기록」만 남긴다** — 넣는 것이 그 사람들의
    일이므로 매번 사유를 적게 하면 일이 안 된다. 우회가 있다는 사실을 계획서에 적어 둔 채로 간다
