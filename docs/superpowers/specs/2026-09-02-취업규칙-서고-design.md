# 취업규칙 서고 — 설계서

- 날짜: 2026-09-02
- 대표 지시: 「취업규칙이 계속 보관되면 파이어베이스에 자동으로 업로드되게 해달라. 그리고 푸른이알피에서 사업장 컨설팅 등으로 취업규칙을 개정한 경우 만약 기존에 규정개정이 끝난 자료의 경우 업로드 해서 별도로 보관 하고 싶은데 어떻게 해야되나」
- 대상: `rules.html`(규정관리) · 새 노드 `rules_mgmt/casebook` · Storage `pureun-erp-hrphotos`(기존 창고 재사용 — 새로 만들지 않는다)
- 분량: 10년치 폴더 통째로 — **수백 건**

## 0. 먼저 못 박아 둘 것 — 셋

**① 「자동 업로드」는 이미 있다. 작업이 없다.**

보관은 다섯 시점에서 저절로 걸리고, 그때마다 Firebase 로 올라간다.

| 시점 | 자리 |
|---|---|
| 파일 올린 직후 (검토 전이라도) | `rules.html:1740` |
| `▶ 취업규칙 검토` 직후 | `rules.html:2086` |
| **조문을 고칠 때마다** (4초 디바운스) | `rules.html:4476` |
| 작성기에서 넘어올 때 | `rules.html:5953` |
| 자동 로그아웃 직전 | `rules.html:6040` |

경로는 `autoSaveArchive()` → `doSaveArchive(silent)` → `putRecord()` → `FBDB.ref(path).set()`
(`rules.html:4051`), 원본 파일은 `putOrig()` → `rules_mgmt/orig/{id}`.
조건은 둘 — 로그인 상태여야 하고(미로그인 시 브라우저에만), **담당자 본인 기록만** 덮어쓴다(`rules.html:4036`).

> 대표가 이 기능을 몰랐던 것이므로, 서고 화면에 «보관은 자동입니다» 를 한 줄 적어 둔다.

**② 기존 보관함으로는 못 담는다. 이건 취향이 아니라 벽이다.**

지금은 원본을 실시간DB에 base64 로 넣고 **2MB 넘으면 텍스트만** 남긴다
(`rules.html:4346`, `MAX_ORIG_BYTES`). Firebase Storage 는 아예 쓰지 않는다
(`firebase.json` 에도 functions 만).

수백 건 × 서류 5종 × 1MB = **수 GB**. base64 는 33% 더 불어나고, 실시간DB 는
노드를 읽으면 **통째로** 내려온다. 담을 수 없다.

**③ 문안 은행은 이 일을 하지 않는다.**

`bankBuild()`(`rules.html:4875`)가 파일 여러 개를 한꺼번에 받기는 한다. 그러나 목적이
**조문 단위로 쪼개 문안을 재사용**하는 것(`chwieop/bank/*`)이고, 「사업장별 개정 완료본을
통째로 보관」과는 다르다. **다만 올릴 때 그쪽에도 함께 흘려보낸다**(§5-③).

## 1. 무엇을 담나 — 자료는 한 벌이 아니라 묶음

대표 확인: 사업장 하나당 손에 있는 것이 개정 전·후 두 벌, 신구대조표, 제출 서류 세트까지다.
그래서 레코드는 「파일 1개」가 아니라 **역할표가 붙은 서류 묶음**이어야 한다.

```
사업장 (사업자번호)
└─ 개정 회차 (2019 / 2022 / 2025 …)
   ├─ before   개정 전 원본        ├─ after    개정본 전문
   ├─ daejo    신구대조표          ├─ report   신고서
   ├─ opinion  의견청취서          └─ consent  동의서
   └─ etc      그 밖 (사람이 확인한 것만)
```

회차가 쌓이면 그대로 **그 사업장의 개정 이력**이 되고, 「지난번에 뭘 고쳤나」가
대조표에 이미 정리돼 있어 실적 증빙도 함께 해결된다.

## 2. 네 가지 용도, 저장소는 하나

대표가 용도 네 가지를 모두 골랐다. 다행히 네 개짜리 시스템이 아니다.

| 용도 | 무엇이 필요한가 | 어디서 오나 |
|---|---|---|
| 재개정 출발점 | `after` 전문 + 사업자번호 | §3 저장소 → §5-② |
| 실적·이력 증빙 | 목록 + 연도·담당 | §3 `index` 층 → §5-① |
| 다른 노무사 참고 사례집 | 조문 검색 + 열람 권한 | §3 `text`·색인 → §5-③ |
| 조문 문안 재사용 | 조문 단위 문안 | **이미 있음** — 문안 은행에 흘려보냄 |

앞 셋은 **저장 구조가 같다.** 다른 것은 보는 방식뿐이므로 «저장소 하나 + 화면 셋» 이다.

## 3. 저장 구조 — 무게별 네 층

본문 텍스트를 목록 노드에 같이 넣으면 안 된다. 취업규칙 전문은 100KB 넘고, 수백 건이면
수십 MB 인데 실시간DB 는 노드를 읽으면 통째로 내려온다. **서고 목록을 여는 순간
전문이 전부 딸려 온다.**

이미 이 저장소가 쓰는 방식이다 — `rules_mgmt/orig` 를 보관함에서 떼어 둔 것,
문안 은행이 "색인을 경로로 만들어 서버에서 필요한 조각만 읽는" 것과 같은 원리다.

```
① 목록 (가볍다 · 서고 화면이 이것만 읽는다)
   rules_mgmt/casebook/index/{siteKey}
     site, bizno, industry, size, revCount, lastYear, updatedAt

② 회차 상세 (사업장 하나를 열 때만)
   rules_mgmt/casebook/rev/{siteKey}/{revId}      revId = "2022" · 같은 해 둘이면 "2022-2"
     year, at(시행일), by(담당), note
     docs/{role}: { name, ext, size, path, artCount, sha }

③ 본문 텍스트 (그 서류를 펼칠 때만)
   rules_mgmt/casebook/text/{siteKey}/{revId}/{role}

④ 검색 색인 (경로 색인 — 문안 은행과 같은 방식)
   rules_mgmt/casebook/idx/k/{키워드}/{siteKey}__{revId} = 1

⑤ 원본 파일 — Firebase Storage
   casebook/{siteKey}/{revId}/{role}.{ext}
```

**`siteKey` 는 기존 규칙을 그대로 쓴다** — `"site_" + fbKey(사업자번호 || 사업장명)`.
`doSaveArchive`(`rules.html:4575`)가 쓰는 것과 같은 키라, 같은 사업장이면
**보관함 기록과 서고가 저절로 붙는다.** 「출발점으로 쓰기」에 연결 작업이 없다.

몇 가지 판단:

- **`sha`(파일 해시)를 넣는 까닭** — 수백 건을 여러 번에 나눠 올리게 된다. 같은 파일을
  또 올렸는지 이걸로 걸러야 중복이 안 쌓이고, 끊긴 뒤 이어 올리기가 안전해진다(§7).
- **`role` 을 파일이 아니라 «자리»로 둔 까닭** — 한 회차에 같은 역할이 둘일 일은 없고,
  「개정본이 있나」를 목록에서 바로 판단할 수 있다.
- **`industry`·`size` 를 목록 층에 둔 까닭** — 사례집의 주된 쓰임이 «비슷한 업종·규모
  찾기» 라, 이건 목록 단계에서 걸러져야 한다.
- **색인을 `after` 만 만드는 까닭** — `before` 까지 넣으면 옛 문구가 검색에 섞인다.
  문안 은행이 `⚠ 개정 전 문구 의심` 으로 이미 겪은 문제다.

**Storage 규칙 게시가 늦어질 때의 차선**: ⑤ 없이 ①②③④만 채운다. 검색·사례집·문안 은행·이력은
텍스트만으로 전부 되고 **원본 보기만 나중에** 붙는다. `path` 를 뒤에 채우는 형태라
구조를 바꿀 필요가 없다.

## 4. 일괄 분류 화면 — 이 물건의 심장

폴더를 통째로 떨어뜨리면 파일마다 셋을 가려야 한다: 어느 사업장 / 몇 년 / 무슨 서류.

| 무엇을 | 어떻게 | 이미 있는 것 |
|---|---|---|
| 서류종류 | 파일명 키워드 1순위, 본문 첫머리로 보강 | — |
| 사업장 | 파일명·**폴더 경로**(`webkitRelativePath`) → ERP 업체 대조로 사업자번호 | `detectSiteName` · `findErpCompany` · `erpNormName` |
| 연도 | 파일명 `20xx` → 본문 부칙 시행일 → 파일 수정일 | `bankYearOf` |
| 본문 추출 | HWP·HWPX·PDF | `hwp_extract.js` · rhwp WASM · pdf.js |
| 조문 쪼개기 | 문안 은행 적립 | `parseArticles` → `bankAccum` |

한 회차에 취업규칙이 둘인데 신·구 표시가 없으면 **부칙 시행일이 이른 쪽을 `before`**
로 본다. 그것도 못 가리면 사람에게 넘긴다.

### 원칙 — 못 가리면 추측하지 않는다

빈칸은 눈에 띄지만 **틀린 값을 확신해서 넣으면 아무도 못 찾는다.** 수백 건이면 더욱
그렇다. 애매한 건 `etc` 같은 자리로 조용히 밀어 넣지 않고 **「확인 필요」로 사람 앞에
올린다.**

> 이 원칙은 이번 검토에서 실제 사고로 확인했다 — `erpVatTextToFlag` 가 「부가세
> 불포함」을 «포함» 으로 정반대 판정해, 부가세 별도 계약이 포함으로 등록되면 청구액이
> 10% 적게 잡히는 상태였다(별건으로 고쳐 인계).

### 화면

```
📁 폴더를 떨어뜨리세요                          [ 342개 파일 읽음 ]

⚠ 확인 필요 17건 ─ 맨 위로 모은다
  파일명                        사업장        연도    종류
  취업규칙_최종.hwp             ?            2021    개정본     [고치기]
  20220310_규정.hwp             한빛산업     2022    ?          [고치기]

✓ 가려진 325건  ─ 접혀 있음 [펼치기]

  [ 이 폴더 전부 「한빛산업」으로 ]     325건 올리기 · 17건은 빼고
```

한 줄을 고치면 **같은 폴더의 나머지에 같은 사업장을 한 번에** 적용한다. 수백 건을
한 줄씩 고칠 수는 없다.

### 결정 1 — 파일명 키워드 (기본값. 사무소 규칙이 있으면 그게 정답)

기본 표는 아래로 두고, **`DOC_ROLE_HINTS` 한 곳에 모아** 사무소 이름 규칙에 맞게
고칠 수 있게 한다. 코드 여러 곳에 흩으면 다시는 못 고친다.

| 단서 | 자리 |
|---|---|
| `신구대조표` `대조표` `신구` | `daejo` |
| `신고서` | `report` |
| `의견청취` `의견서` `의견` | `opinion` |
| `동의서` `동의` | `consent` |
| `개정안` `개정` `최종` `(신)` | `after` |
| `현행` `기존` `구` `(구)` | `before` |

한 파일명에 둘 이상 걸리면 **표의 위쪽이 이긴다**(`daejo` 가 `개정` 보다 앞). 하나도
안 걸리면 `etc` 가 아니라 **「확인 필요」** 다.

### 결정 2 — 확인 필요분은 빼고 먼저 올린다

**17건 때문에 325건이 막히면 안 된다.** 가려진 것만 먼저 올리고, 확인 필요분은 화면에
남겨 나중에 처리한다. 다시 올릴 때 `sha` 로 이미 올라간 것은 건너뛰므로 안전하다.

## 5. 화면 셋

### ① 서고 목록 — 실적 증빙

`casebook/index/{siteKey}` **만** 읽는다. 사업장 · 회차 수 · 최근 연도 · 업종 · 규모 ·
담당. 연도·업종·규모·담당으로 걸러 보고, 그대로 `xlsx_gen.js` 로 내보내면 실적표가 된다.

### ② 사업장 이력 — 재개정 출발점

한 사업장의 회차를 시간순으로. 회차마다 **어떤 서류가 있는지 칩으로** 보여 준다
(`개정 전` `개정본` `대조표` `신고서` `의견` `동의`).

핵심 단추는 **「이 회차로 검토 시작」** — `after` 전문을 검토 화면에 실어
`▶ 취업규칙 검토` 로 이어간다. 임시저장 복원이 쓰는 `applyWorkObject`
(`rules.html:4479`)와 같은 길이다.

`siteKey` 가 보관함과 같으므로 **대시보드에 「지난 개정 3회」가 저절로 붙는다.**

### ③ 사례집 검색 — 새 화면을 만들지 않는다

`🔎 조문 검색`(`artsBuild`, `rules.html:5608`)이 이미 보관함 전체를 조문 단위로 훑고,
지금도 "※ N곳은 보관된 원문이 없어 검색되지 않습니다" 라고 스스로 한계를 밝힌다.
**서고가 그 빈칸을 채운다.**

다만 지금 방식으로는 수백 건에서 무너진다 — `artsBuild` 는 레코드당 Firebase 읽기
1회를 돌리고 전문 전체를 `ARTS` 에 쌓는다. 그래서 서고는 **경로 색인**(§3-④)으로
서버에서 필요한 조각만 읽고, **본문은 고른 것만** 가져온다.

문안 은행 적립은 `role=after` 만 `parseArticles` → `bankAccum` 으로 흘려보낸다.

## 6. 권한 — 여기서 보관함과 갈린다

| | 보관함 | **서고** |
|---|---|---|
| 읽기 | 내 것 + 남의 **완료본** | **직원 전체** |
| 쓰기 | 담당자만 | 올린 사람 또는 관리자 |

규칙 모양은 이미 있는 것을 그대로 쓴다 — `.read` 는 `done`·`archive`·`orig` 와 같은
비밀번호 로그인 조건, `.write` 는 `orig` 의 `ownerUid` 방식
(`docs/firebase-rules-전체-적용본.json:792` 의 `rules_mgmt` 블록, `archive` 는 879줄).

**⚠ 이건 의도된 차이다.** 보관함은 「담당자만 고치고 완료본만 남에게 보인다」인데
서고는 **남의 사업장도 다 보인다.** 사례집이 목적이니 맞지만, 올리는 화면에
**«서고에 올리면 직원 전체가 볼 수 있습니다» 를 적어야 한다.** 모르고 올렸다가
남이 보는 걸 나중에 알면 사고다.

## 7. 수백 건을 견디는 방법

### 중단은 예외가 아니라 기본값

- `sha` 로 **이미 올라간 파일은 건너뛴다**
- 브라우저를 닫았다가 **같은 폴더를 다시 떨어뜨리면 이어서** 올라간다
- 한 건 실패가 전체를 세우지 않는다 — 실패 목록에 남기고 계속, 끝에 **「실패 N건 다시 시도」**

### 쓰는 순서 — 고아를 만들지 않는다

```
① Storage 파일  →  ② text  →  ③ rev  →  ④ index/idx
   (무겁다)                              (가볍다)
```

무거운 것부터 쓴다. 중간에 끊기면 **파일은 있고 색인이 없는 고아 파일**이 남는다.
그래서 **`rev` 에 적힌 것만 목록에 보이게** 하고, 다시 올릴 때 `sha` 로 고아를 찾아
**색인만 다시 붙인다**(파일을 또 올리지 않는다).

이 원칙은 이미 코드에 있다 — `removeOrig` 주석이 "기록만 지우고 원본을 남기면
공용 저장소에 고아 데이터가 쌓인다" 고 적어 두었다.

### 나머지

- **파일 상한** — 하나당 50MB, 회차당 서류 수 상한. 넘으면 **그 파일만** 건너뛰고
  화면에 밝힌다. 조용히 빼면 안 된다.
- **되돌리기** — 잘못 올린 회차는 파일과 색인을 **함께** 지운다.
- **문안 은행 이중 적립 방지** — 같은 `sha` 를 두 번 적립하지 않는다.

## 8. 처음 판에서 뺄 것 (YAGNI)

- **업종·규모 자동 추출 안 함** — ERP 업체관리에서 가져오거나 빈칸. 파일에서 추측하면
  틀린 값이 수백 건 박힌다.
- **OCR 안 함** — 스캔 PDF 는 텍스트가 없으면 「원본만 보관」으로 두고 검색에서 뺀다.
  **그렇다고 화면에 적는다.**
- **회차 자동 병합 안 함** — 같은 연도 두 건은 `2022`, `2022-2` 로 두고 사람이 판단.
- **한글 편집기 임베드 안 함** — 별건 검토 결론: 편집 원본은 조문 모델이어야 하고
  한글은 출력 형식이다.

## 9. 검사 계획

화면과 얽히지 않게 **순수 함수로 뽑아** 실제로 돌린다(`vm` 또는 `module.exports`).
이 저장소의 `tests/` 관례를 따른다.

| 함수 | 무엇을 못 박나 |
|---|---|
| `roleOf(파일명, 본문머리)` | 키워드 우선순위 · 하나도 안 걸리면 «확인 필요»(=`null`) |
| `siteOf(경로, 파일명, ERP목록)` | 폴더명 단서 · ERP 못 찾으면 사업장명만 |
| `revIdOf(연도, 이미있는회차)` | `2022` → `2022-2` 충돌 회피 |
| `idxKeysOf(조문)` | `after` 만 · 색인 키워드 상한 |
| `uploadPlan(파일목록, 이미올린sha)` | 건너뛸 것 · 올릴 것 · 확인 필요 갈라내기 |

**골든셋**: 실제 파일명 20~30개를 `tests/fixtures/` 에 적어 두고 `roleOf`·`siteOf`·
`revIdOf` 를 통째로 견준다. 사무소 이름 규칙이 바뀌면 여기만 고친다.

## 12. 단계 — 한 판에 다 만들지 않는다

이 설계서는 한 사람이 한 번에 구현할 크기가 아니다. 아래 순서로 나눈다.
**각 단계가 끝나면 그것만으로도 쓸 수 있어야 한다.**

| 단계 | 무엇 | 끝나면 쓸 수 있는 것 |
|---|---|---|
| 1 | §3 저장 구조 + §9 순수 함수(`roleOf`·`siteOf`·`revIdOf`) + 골든셋 | 아직 화면 없음. 분류가 맞는지 검사로 확인 |
| 2 | §4 일괄 분류 화면 + §7 업로드(끊김·재개) | **10년치를 실제로 넣을 수 있다** |
| 3 | §5-① 서고 목록 + §5-② 사업장 이력 | 넣은 것을 보고, 재개정을 이어갈 수 있다 |
| 4 | §5-③ 사례집 검색(경로 색인) + 문안 은행 적립 | 사례집·문안 재사용 |

1단계를 검사로 못 박은 뒤 2단계로 가는 것이 중요하다. **분류가 틀린 채로 수백 건을
넣으면 되돌리는 값이 훨씬 크다.**
