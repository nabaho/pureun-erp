# 부분입금 · 마무리 확정 — 설계

- 날짜: 2026-08-16
- 요청: 대표님 — "정우신약 근로자의 일부가 미입금되었다. 관리자가 거래내역에 전체를 검토해서 입금자를 모두 합쳐 정리한 경우 합쳐서 정리된 내역을 입금확정에 모두 볼 수 있어야 한다. 실제 입금이 계속해서 적게 되는 경우 1달이 지난 경우 일부만 입금되어서 부분 확정해야 되는데 그 부분도 같이 반영하고, 그 다음 달 나머지가 입금되거나 추후 미수가 정리되었을 때 마무리 확정을 할 필요가 있을 것 같다."
- 목업: `docs/mockups/partial-close.html`
- 대상 파일: `pu-erp.html` (단일 파일, 빌드 없음, ES5)

---

## 1. 먼저 확인한 것 — 뼈대는 이미 있다

실제 코드를 읽어 확인했다. **새로 만들 필요가 없는 것이 셋이다.**

| 이미 되는 것 | 어디에 |
|---|---|
| 통장 여러 줄을 한 건에 합쳐 확정 | 거래내역 「⊞ 묶어서 처리」 (`spRows`) |
| 부분 확정 (일부만 받고 남기기) | `saveIncome(..., {partial:true})` · `splitPayments` 누적 |
| 다음 달 **남은 금액**으로 통장 뒤지기 | `erpExpectAmount(fee, taxType, paid)` — 이미 받은 만큼 뺀다 |
| 나머지가 채워지면 자동 완납 | `_after >= _totalExp - 1100` |

즉 정우신약 건은 588만을 부분확정해 두면, 다음 달 12만이 들어올 때
**약정 600만이 아니라 남은 12만으로** 통장을 뒤져 자동으로 붙는다.

⚠ 화면의 「120,000 모자람」은 **거짓말이 아니다.** 아직 아무것도 확정하지 않은 상태에서
통장 588만을 약정 600만에 대 본 결과다. 사실 그대로다.

### 「아직 안 받았나」는 한 곳에서만 판단한다

`erpUnpaidParts(it)` — 입금관리 「미입금 대기」와 거래내역 「후보」가 **둘 다** 이 함수를 본다
(2026-08-13 에 두 화면이 어긋나서 한 곳으로 모은 것). 이번 설계도 여기에만 손댄다.

## 2. 비어 있는 것 넷

### ① 부분입금 이력에 「적요」가 안 남는다 ← 가장 큰 구멍

지금 저장되는 것: `splitPayments: [{ id, date, amount, kind }]`
**누가 낸 돈인지가 없다.**

정우신약처럼 근로자 39명이 나눠 내는 건에서, 다음 달 마무리할 때
「588만이 누구누구 것이었지?」를 **통장을 다시 뒤져** 알아내야 한다. 사실상 불가능하다.

적는 곳이 셋이라 셋 다 고쳐야 한다:
- `saveIncome` (거래내역 확정) — `pu-erp.html`, `_sp.splitPayments = ...concat([...])`
- `doConfirm` (입금확정 창) — 사건 갈래 `_splitEntry`, 그 외 갈래 `_se`
- 종결관리 쪽 한 곳 (`prevSplits`/`splitEntry` 를 쓰는 자리)

### ② 입금확정 창이 합계 한 줄만 보여준다

지금: `◐ 기납입 5,880,000 · 잔액 120,000`
**언제 얼마씩 들어왔는지 목록이 없다.** 묶어서 처리한 줄도 합쳐진 뒤엔 안 보인다.

### ③ 「여기까지로 닫기」가 없다

`waived`(포기)는 **성공보수에만** 있다(`CloseCaseModal`). 착수금·계약금·잔금은 없다.
못 받기로 해도 **영원히 「미입금 대기」에 남는다.**

### ④ 미수금관리가 「정리된 미수」를 모르는 상태

`FinanceReceivable` 의 `_remain()` 은 받은 돈만 뺀다. 닫은 건을 뺄 근거가 없다.

## 3. 대표님이 정하신 것

| 물음 | 정하신 것 |
|---|---|
| 통장에 어떻게 찍히나 | **둘 다** — 근로자별 여러 줄인 건도, 모아서 한 줄인 건도 있다 |
| 남은 돈 마무리 방법 | **셋 다** — 추가 확정 · 여기까지로 닫기 · 약정액 줄이기 |
| 「마무리」 단추 자리 | **미입금 대기 목록에 바로** |
| 「닫기」 권한 | **관리자(ADMIN)까지** |

## 4. 설계

### 4-1. 들어온 돈에 적요를 남긴다

`splitPayments` 항목에 **`memo`** 를 더한다.

```js
{ id:'sp-…', date:'2026-07-02', amount:5880000, kind:'착수금',
  memo:'정우신약-39(+1명)' }        // ← 새로 더하는 칸
```

- **뒤로 호환된다** — 옛 기록은 `memo` 가 없고, 화면은 없으면 `-` 로 그린다.
- 적요의 출처: 거래내역은 통장 줄의 `memo || note`, 입금확정 창은 `confirmModal.bankRow.memo`.
  통장에서 열지 않고 손으로 확정한 건은 적요가 없다 — 그대로 비워 둔다(거짓으로 채우지 않는다).

⚠ **`kind` 는 그대로 둔다.** `erpPaidSoFar` 가 `sp.kind === kindLabel` 로 합계를 내므로
이름을 건드리면 지금까지 받은 돈이 통째로 0이 된다.

### 4-2. 입금확정 창에 「이 건에 들어온 돈」 표

```
📥 이 건에 들어온 돈                    약정 6,000,000
  날짜    적요                      금액       상태
  07-02  정우신약-39(+1명)      5,880,000   ✓ 확정됨
  08-16  박○○ 외 2명              120,000   ← 지금
  ─────────────────────────────────────────
  받은 6,000,000 · 남은 0                    완납 ✓
```

- 위쪽 줄들: `item.splitPayments` 중 이 종류(`kindLabel`)인 것
- 마지막 줄: 이번에 확정할 금액(`_cmPay`)과 통장 적요(`confirmModal.bankRow`)
- 합계 줄: `약정 · 받은 · 남은` — 남은 것이 0이면 초록 「완납」, 남으면 노랑 「일부입금」
- 한 줄뿐이어도 표로 그린다 — **다음에 줄이 늘어날 자리**이기 때문이다

지금의 `◐ 기납입 … · 잔액 …` 한 줄은 **이 표가 대신하므로 없앤다** (같은 것을 두 번 적지 않는다).

### 4-3. 「여기까지로 닫기」 — 저장 형태

항목(사건·컨설팅·기금·기타)에 **`unpaidClosed`** 를 둔다. 종류별로 따로 닫을 수 있어야 하므로 표(객체)다.

```js
it.unpaidClosed = {
  '착수금': { amount:120000, reason:'근로자 3명 끝내 미납 — 대표 협의로 정리',
              at:'2026-08-16T14:22:00.000Z', by:'P001', byName:'권형하' }
}
```

**읽는 곳은 한 함수로 모은다:**

```js
function erpClosedUnpaid(it, splitLabel){
  var m = (it && it.unpaidClosed) || {};
  var r = m[splitLabel];
  return (r && (parseInt(r.amount, 10) || 0) > 0) ? r : null;
}
```

**막는 곳 둘 (그 함수만 부른다):**
- `erpUnpaidParts` — `if(!done(…) && !erpClosedUnpaid(it, '착수금'))` 꼴로 네 종류에 건다
  → 입금관리 「미입금 대기」와 거래내역 「후보」가 **한꺼번에** 빠진다 (한 곳에서 판단하는 구조 덕)
- `FinanceReceivable._remain` — `if(erpClosedUnpaid(item, kindLabel)) return 0;`

⚠ **`xxxPaid` 플래그를 세우지 않는다.** 그걸 세우면 「다 받았다」가 되어 **받지도 않은 돈이 받은 것으로** 보인다.
닫힘은 「안 받기로 했다」이지 「받았다」가 아니다. 그래서 별도 칸을 둔다.

⚠ **매출·성과급은 건드리지 않는다.** 이 시스템은 실제 들어온 돈만 `finance_income` 에 적으므로
닫아도 매출은 588만 그대로다. 바뀌는 것은 「약정 600만 중 12만은 못 받기로 했다」는 **사실이 남는 것**뿐이다.

### 4-4. 「마무리」 단추 — 미입금 대기 목록에

- **일부라도 받은 건에만** 뜬다 (`p.paidSoFar > 0`). 한 푼도 안 받은 건에는 안 뜬다 — 아직 마무리할 것이 없다.
- 누르면 세 갈래 창:
  1. **나머지 N원을 확정한다** → 지금의 입금확정 창을 연다 (새로 안 만든다)
  2. **여기까지로 닫는다** → 까닭 입력 창 (관리자만 보인다)
  3. **약정액을 고친다** → 사건·계약 화면으로 보낸다 (**새로 안 만든다**)

⚠ 3번을 여기서 만들지 않는 까닭: 계약 금액은 세금계산서·부가세·성과 기준과 얽혀 있다.
여기서 숫자만 바꾸면 그것들이 어긋난다. 고치는 자리는 이미 있으므로 **그곳으로 보낸다.**

### 4-5. 닫기 창

- 약정 · 받은 돈 · **못 받기로 하는 돈**을 먼저 보여준다
- **까닭 필수** — 비면 단추가 막힌다
- 관리자(`isAdminByUser(CURRENT_USER)`)가 아니면 이 갈래 자체를 안 보여준다
- 저장 뒤 감사 로그에 남긴다

### 4-6. 정리된 미수 목록 + 되돌리기

`FinanceReceivable` 아래에 **「🏁 정리된 미수」** 칸을 더한다.

| 정리일 | 업체 | 항목 | 약정 | 받은 돈 | 못 받음 | 까닭 (누가·언제) | ↺ 되돌리기 |

⚠ **되돌릴 수 있어야 한다.** 잘못 닫으면 돈이 통째로 사라진 것처럼 보인다.
되돌리면 `unpaidClosed[종류]` 를 지우고, 그 건이 다시 미입금 대기로 돌아온다.

**월말 마감은 이번 범위 밖으로 둔다** — 마감 단계는 여섯 개가 서로 물려 있어
한 줄 더하는 일이 아니다. 정리된 미수는 미수금관리 화면에서 볼 수 있고, 그것으로 충분하다.
(대표님이 마감에서도 보이길 원하시면 그때 따로 한다.)

## 5. 안 만드는 것

- **통장 여러 줄을 자동으로 합쳐 찾기** — 「⊞ 묶어서 처리」가 이미 있다.
  자동으로 묶으면 **엉뚱한 돈이 붙어도 아무도 모른다.** 묶는 것은 사람이 보고 정할 일이다.
  (`erpBundlePlan` 이라는 죽은 함수가 있는데, 이번에도 쓰지 않는다. 지우지도 않는다 — 검사가 걸려 있다.)
- **약정액 고치는 화면** — 계약·사건 화면에 이미 있다
- **매출·성과급 셈 변경** — 부분확정하면 그 금액만큼만 성과급이 나뉘고 나머지가 들어오면 또 나뉜다. 지금도 그렇다.
- **`erpPaidSoFar` · `erpExpectAmount` 의 셈** — 이미 남은 금액으로 맞게 돌고 있다

## 6. 검사

`tests/partial-close.test.js` 새로 만든다. 함수를 소스에서 뽑아 **실제로 돌린다.**

**`erpClosedUnpaid`**
- 닫힌 종류를 찾아낸다 / 안 닫힌 종류는 null
- 금액 0이거나 칸이 없으면 null (빈 표에 걸려 잘못 닫히지 않는다)
- 종류가 여럿일 때 서로 섞이지 않는다 (착수금만 닫고 성공보수는 살아 있다)

**`erpUnpaidParts`**
- 닫은 종류가 목록에서 빠진다
- 닫지 않은 종류는 그대로 남는다
- **`xxxPaid` 플래그를 세우지 않는다** — 「받았다」와 「안 받기로 했다」는 다르다

**`splitPayments` 적요**
- 세 갈래(거래내역·입금확정창·종결관리) 모두 `memo` 를 적는다
- `kind` 는 그대로다 (건드리면 지금까지 받은 돈이 0이 된다)
- 적요가 없으면 빈 값 — 거짓으로 채우지 않는다

**화면**
- 「마무리」 단추는 일부라도 받은 건에만 뜬다
- 닫기 갈래는 관리자에게만 보인다
- 까닭이 비면 단추가 막힌다
- 미수금관리가 닫은 건을 안 센다
- 되돌리기가 있다

뮤테이션으로 각 규칙을 하나씩 망가뜨려 검사가 실제로 잡는지 확인한다.
⚠ **뮤테이션 전에 기준선이 초록인지 먼저 본다** — 늘 실패하는 검사가 하나 있으면 모든 변이가 잡힌 것처럼 보인다
(2026-08-16 에 실제로 겪었다).

⚠ 검사에 **높이·색·내부 변수 이름·글자수 거리**를 박지 않는다
(`CLAUDE.md` 「검사를 쓰는 규칙」, `tests/test-pin-guard.test.js`).

## 7. 이 설계가 막는 것

| 지금 | 뒤 |
|---|---|
| 588만이 누구 것이었는지 알 수 없다 | 적요가 함께 남는다 |
| 창에 합계 한 줄뿐 | 들어온 돈이 한 줄씩 보인다 |
| 못 받기로 해도 영원히 「미입금 대기」 | 까닭과 함께 닫고, 되돌릴 수 있다 |
| 미수금관리가 못 받기로 한 돈을 계속 센다 | 「정리된 미수」로 따로 보인다 |
