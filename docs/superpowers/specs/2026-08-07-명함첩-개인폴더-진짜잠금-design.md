# 명함첩 개인 폴더 — 화면 가림을 진짜 잠금으로

작성 2026-08-07 · 대상 `pu-cards.html` · Firebase 규칙

## 지금 무엇이 잘못돼 있나

명함첩의 자물쇠는 **화면에서 가리기만** 한다. 자료는 로그인한 직원 누구나 읽을 수 있다.

적용 중인 규칙(`docs/firebase-rules-현재적용본.json`)은 이렇다.

```json
"pucards": {
  ".read":  "auth != null && auth.token.email != null",
  ".write": "auth != null && auth.token.email != null"
}
```

| | 지금 상태 |
|---|---|
| 잠긴 폴더의 명함 | 자료는 누구나 읽힘. `canSeeGroup()` 이 화면에서만 가린다 |
| 잠금 비밀번호 `g.pw` | **같은 읽기 가능한 자리에 평문으로 저장** — 읽어서 그대로 입력하면 열린다 |
| 폴더 이름 | 공용 폴더 목록에 그대로 있다 |
| 다른 앱(푸른이알피) | **막힌다.** `inLockedGroup()` 이 공유 검색목록 `pucards/idx` 에서 빼고 있다 |

즉 실제로 지켜지는 것은 마지막 하나뿐이다.

뚫으려면 브라우저 개발자도구로 데이터베이스를 직접 조회해야 한다. 실수로 보게 되지는
않지만, **의도적으로 보려는 사람은 볼 수 있다.** 대표 요구("나 외에 아무도, 폴더도
안 보이게")를 지금 구조로는 만족할 수 없다.

## 목표

1. 잠긴 폴더의 명함과 **폴더 이름 자체**를 대표 외에는 서버가 주지 않게 한다.
2. 비밀번호를 저장하지 않는다.
3. 다른 앱·백업·검색이 지금처럼 동작한다.

## 정한 것 (대표 결정)

| 물음 | 결정 |
|---|---|
| 다른 기기에서도 봐야 하나 | **본다** — 클라우드에 두되 대표 계정만 읽게 |
| 비밀번호 | **유지** — 단 저장하지 않고 해시로 검사만 |
| 직원도 잠글 수 있나 | **아니오** — 대표만. 명함은 회사 자산이고, 직원이 잠그면 퇴사 후 찾을 수 없다 |
| 방식 | **경로 분리** — 내용 암호화(B안)는 비밀번호를 잊으면 영영 못 읽고 검색도 안 된다 |

같은 저장소의 푸른사진첩이 이미 `"$uid": {".read": "auth.uid === $uid"}` 로 사람별 분리를
하고 있다. 검증된 선례를 따른다.

---

## 1. 저장 구조

```
pucards/                       ← 공용 (그대로)
  items/  groups/  idx/  trash/

pucards_private/
  <대표 uid>/
    lock            = { salt, hash, iter }   ← 비밀번호 검사용. 비밀번호 자체는 없다
    groups/{gid}    = 폴더 기록 (name, locked:true, lockedAt)
    items/{id}      = 명함 전체
    photos/{id}     = 사진
    trash/{id}      = 지운 개인 명함 (공용 휴지통으로 나가면 안 된다)
```

폴더 기록까지 이 안에 둔다. 공용 `pucards/groups` 에 아무 흔적도 남기지 않아야
**폴더 이름도 개수도 보이지 않는다.**

### 규칙

```json
"pucards_private": {
  "$uid": {
    ".read":  "auth != null && auth.uid === $uid",
    ".write": "auth != null && auth.uid === $uid"
  }
}
```

`pucards_private` **자체에는 읽기 권한을 주지 않는다.** 주면 "누가 개인 폴더를 갖고
있는지" 목록이 드러난다. 자식만 열어 두면 목록 조회는 거부되고, 자기 것만 정확히
집어 읽을 수 있다.

## 2. 대표 판별

`uid_roles/<uid>/isAdmin` — 포털(`enter.html`)이 이미 쓰는 값이다. 새로 만들지 않는다.

- `isAdmin` 이 참인 사람에게만 🔒 잠금 단추와 `🔒 개인 폴더 열기` 단추를 보인다.
- 화면에서 숨기는 것은 편의일 뿐이다. 실제 차단은 규칙이 한다 — 남의 `uid` 경로는
  읽기도 쓰기도 거부된다.

**구현 첫 단계에서 대표 계정에 `isAdmin` 이 실제로 있는지 확인한다.** 없으면 진행을
멈추고 알린다.

## 3. 쓰는 흐름

### 잠글 때

```
폴더 ⋮ → 🔒 잠금 → 비밀번호 2번 입력(확인용)
   ↓ 통신 한 번
pucards_private/<uid>/groups/{gid}  ← 폴더 기록
pucards_private/<uid>/items/{…}     ← 그 폴더 명함 전부
pucards_private/<uid>/photos/{…}    ← 사진
pucards/groups/{gid}   = null       ← 공용에서 지움
pucards/items/{…}      = null
pucards/photos/{…}     = null       ← 사진도 공용 자리에서 지운다
pucards/idx/{…}        = null       ← 공유 검색목록에서 제외
```

명함이 한 장도 안 사라지게 **하나의 다중 경로 `update()`** 로 보낸다. 실패하면
아무것도 바뀌지 않는다.

사진을 옮기고 옛 자리를 지우는 것을 빠뜨리면 **명함은 숨어도 그 명함의 사진은 공용
자리에 그대로 남는다.** 명함 사진에는 이름·전화가 다 찍혀 있으므로 숨긴 의미가 없어진다.

### 열 때

왼쪽 아래에 대표에게만 `🔒 개인 폴더 열기` 단추를 둔다.

```
[🔒 개인 폴더 열기]
   ↓ pucards_private/<uid>/lock 만 먼저 읽어 비밀번호 검사
   ↓ 맞으면 그때 items·groups 구독 시작
폴더와 명함이 목록에 합쳐져 보임
   ↓ 새로고침·로그아웃
다시 잠김 (구독 해제)
```

**비밀번호를 맞히기 전에는 개인 자료를 불러오지 않는다.** 화면에서 가리는 것이 아니라
브라우저에 아예 없다.

열려 있는 동안 개인 명함은 공용 명함과 같은 목록에 섞여 보인다. 대표 눈에는 지금과
똑같다.

어느 창고에서 온 명함인지는 **화면에서만 쓰는 표시** `_priv:true` 로 가른다. 저장할 때는
떼고 보낸다 — 개인 창고에 있다는 사실 자체가 이미 개인이라는 뜻이라 기록에 남길 이유가 없고,
남기면 공용 자리로 되돌릴 때 지워야 할 것이 하나 늘 뿐이다.

### 개인 명함을 지울 때

휴지통 `pucards/trash` 는 **공용이다.** 개인 명함을 그냥 지우면 이름·전화가 담긴 기록이
공용 휴지통으로 나와 직원 누구나 읽게 된다 — 숨긴 것이 지우는 순간 드러나는 셈이다.

개인 명함은 `pucards_private/<uid>/trash/{id}` 로 보낸다. 되살리기도 그 자리에서 한다.

### 잠금 풀 때

비밀번호 확인 후 반대로 옮긴다. 공용 자리로 되돌리고 `idx` 에 다시 넣는다. 통신 한 번.

## 4. 비밀번호

저장하지 않는다. `crypto.subtle` 의 PBKDF2 로 뒤섞은 흔적만 남긴다.

```
pucards_private/<uid>/lock = {
  salt : 무작위 16바이트(base64),
  iter : 100000,
  hash : PBKDF2-SHA256(비밀번호, salt, iter) 의 base64
}
```

검사는 같은 방식으로 다시 계산해 견주기만 한다. 자료를 들여다봐도 비밀번호는 알 수 없다.

### 이 비밀번호가 막는 것과 못 막는 것 — 분명히 해 둔다

| 상황 | 결과 |
|---|---|
| 직원이 자기 계정으로 명함첩을 연다 | **자료가 아예 안 온다.** 서버가 거부 |
| 직원이 개발자도구로 경로를 직접 조회한다 | **거부된다.** 규칙이 막는다 |
| 대표가 로그인해 둔 화면을 누가 만진다 | **비밀번호에서 막힌다** |
| 대표 계정이 열린 상태에서 개발자도구를 다룰 줄 안다 | **막지 못한다.** 비밀번호 창을 건너뛰고 개인 창고를 읽을 수 있다 |

마지막 줄까지 막으려면 명함 내용 자체를 비밀번호로 암호화해야 하는데, 비밀번호를
잊으면 영영 못 읽고 검색도 안 된다. 대표가 그 맞바꿈을 원하지 않아 넣지 않는다.

**직원으로부터는 완전히 막힌다. 대표 계정을 쓰는 사람으로부터는 한 겹이다.**

## 5. 기존 개인폴더 이관

저절로 옮기지 않는다. 대표가 누를 때만 돈다.

```
환경설정 → 🔒 개인 폴더 → [개인 창고로 옮기기]
   "개인폴더 N장을 대표님 전용 창고로 옮깁니다"
   ↓ 통신 한 번 (잠글 때와 같은 경로)
```

옮긴 뒤에는 `🔒 개인 폴더 열기` 를 누르기 전까지 **대표 목록에서도 안 보인다.**
처음엔 낯설 수 있으므로 옮긴 직후 그 사실을 화면에 알린다.

## 6. 백업

지금 백업은 공용 명함만 담는다. 그대로 두면 **개인 명함이 조용히 빠진다** — 받았다고
믿는데 없는 것이 가장 위험하다.

- 개인 폴더를 **연 상태**에서 백업하면 함께 담는다.
- **잠긴 상태**면 백업 전에 알린다: *"개인 명함 N장은 빠집니다. 담으려면 먼저 여세요."*
- 개인 명함이 담긴 백업 파일에는 열쇠가 없다. 받을 때 그 사실을 한 줄 띄운다.
- 복원할 때 `_priv` 표시가 붙은 기록은 개인 창고로 되돌린다.

## 7. 다른 앱

**바뀌지 않는다.** 푸른이알피 등은 공유 검색목록 `pucards/idx` 만 본다. 잠긴 명함은
지금도 거기서 빠져 있고(`inLockedGroup`), 앞으로는 아예 다른 창고에 있어 더 확실하다.

## 8. 배포 순서

```
1. Firebase 규칙 배포   ← 대표가 콘솔에 붙여넣는다 (파일로 준비해 드린다)
2. 앱 배포
3. [개인 창고로 옮기기] 실행
```

규칙만 먼저 넣는 것은 아무 영향이 없다 — 아직 그 길을 쓰는 코드가 없다. 순서를 뒤집으면
앱이 새 창고에 쓰려다 「권한 없음」이 난다.

## 잘못될 수 있는 곳과 대비

| 위험 | 대비 |
|---|---|
| 이관 도중 실패해 명함이 사라짐 | 하나의 `update()` 로 원자적으로. 실패하면 아무것도 안 바뀐다 |
| 대표에게 `isAdmin` 이 없어 잠금이 안 됨 | 구현 첫 단계에서 확인하고, 없으면 멈추고 알린다 |
| 규칙보다 앱을 먼저 배포 | 배포 순서를 8절에 못 박았다 |
| 백업에서 개인 명함이 조용히 빠짐 | 잠긴 상태 백업 시 반드시 알린다 |
| 옮긴 뒤 대표가 "명함이 사라졌다"고 놀람 | 옮긴 직후, 그리고 목록이 빈 동안 안내 문구를 띄운다 |
| 잠금 해제 시 검색목록이 안 채워짐 | 해제도 잠글 때와 같은 한 번의 `update()` 에 `idx` 를 함께 쓴다 |
| 개인 명함이 공용 자리에 남아 이중 존재 | 옮기기·되돌리기 모두 새 자리 쓰기와 옛 자리 삭제를 같은 `update()` 에 넣는다 |
| 명함은 숨었는데 **사진이 공용 자리에 남음** | 사진도 함께 옮기고 `pucards/photos/{id}` 를 지운다. 검사에 넣는다 |
| 개인 명함을 지우자 **공용 휴지통으로 나옴** | 개인 명함은 `pucards_private/<uid>/trash` 로 보낸다. 검사에 넣는다 |

## 확인 방법

`pu-cards.html` 은 빌드 없는 단일 파일이므로 이 파일이 이미 쓰는 방식을 따른다.

1. **문법 검사** — 인라인 `<script>` 를 뽑아 `node --check`.
2. **순수 로직 검사** (`node --test`, `vm` 샌드박스) — 비밀번호 해시가 같은 입력에 같은 값을
   내고 틀린 비밀번호를 거르는지, 옮기기가 만드는 경로 목록이 정확한지(새 자리 쓰기와
   옛 자리 삭제가 짝을 이루는지).
3. **기능 검사** (로컬 서버 + 브라우저 자동화, 가짜 DB로 무엇을 쓰려 했는지만 받아 확인)
   - 잠글 때: 공용 자리 삭제 + 개인 자리 쓰기 + `idx` 삭제가 **한 번의 update** 에 들어가는지
   - 비밀번호 틀리면 구독이 시작되지 않는지
   - 잠금 해제가 공용 자리와 `idx` 를 정확히 되돌리는지
   - 개인 명함이 `pucards/idx` 에 절대 안 들어가는지
   - 사진이 `pucards/photos` 에서 지워지고 개인 창고로 옮겨지는지
   - 개인 명함을 지우면 공용 휴지통이 아니라 개인 휴지통으로 가는지
4. **규칙 검사** — Firebase 규칙 시뮬레이터로 남의 `uid` 경로 읽기가 거부되는지,
   `pucards_private` 목록 조회가 거부되는지 확인한다.

## 안 하기로 한 것

- **명함 내용 암호화** — 비밀번호를 잊으면 영영 못 읽고 검색도 안 된다.
- **직원별 개인 폴더** — 회사 명함을 직원이 숨길 수 있게 되고, 퇴사 후 찾을 수 없다.
- **대표만 전체를 볼 수 있는 예외 규칙** — 대표가 바뀔 때마다 규칙 파일을 손대야 한다.
- **기존 `g.pw` 평문 이전** — 옮기지 않고 버린다. 잠글 때 비밀번호를 새로 받는다.
