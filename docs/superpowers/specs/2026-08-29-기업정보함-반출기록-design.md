# 기업정보함 반출 기록 — 설계서

- 날짜: 2026-08-29
- 대표 지시: 「기업정보함에 데이터 다운받거나 할 정보를 가져가려고 할 경우 우선 보안 시스템 만들고 싶은데 어떻게 해야하나」
- 대상: `pu-cards.html` (푸른 기업정보함 — 명함 6,295 · 사업자 351 · 기업 상세 4,154)

---

## 0. 먼저 못 박아 둘 것 — 이것이 «벽»은 아니다

화면에 보이는 자료는 완전히 막을 수 없다. 화면 캡처·폰으로 찍기·개발자도구는
어떤 웹 프로그램도 못 막는다. 개발자도구를 열면 이 문지기도 건너뛸 수 있다.

**그러므로 이 시스템이 실제로 하는 일은 둘이다.**

1. **알려 주는 것** — 「이 내려받기는 기록됩니다」. 억지력의 거의 전부가 여기서 나온다.
2. **알아채는 것** — 퇴사를 앞둔 사람이 6,295건을 받아 가면 **그날** 대표가 안다.

**진짜 벽은 데이터베이스 규칙이다.** 그것은 2단계다(§7). 대표 결정으로
「흔적 먼저, 그다음 문 줄이기」 순서를 잡았다 — 기록을 2~3주 쌓아 «진짜 쓰는 문»을
확인한 뒤에 잠가야 업무가 안 멈춘다.

## 1. 지금 열려 있는 문 — 일곱

조사(2026-08-29)에서 확인한 것. **모두 직원 누구나 쓸 수 있고, 기록은 한 곳도 없다.**

| # | 문 | 함수 | 한 번에 나가는 양 |
|---|---|---|---|
| 1 | 📤 엑셀로 내보내기 | `exportXlsx()` | 명함/사업자 **전체** |
| 2 | 📇 주소록 CSV | `coMailCsv()` · `downloadCsvFile()` | 고른 회사 담당자 |
| 3 | 📇 연락처 저장 | `downloadVcf()` | 1건 |
| 4 | 📥 원본 사진 | `downloadPhoto()` | 1건 |
| 5 | 📋 정보 복사 | `copyCardInfo()` · 여러 건 복사 | 1건 ~ 여러 건 |
| 6 | 자료함 파일 | `downloadMaterial()` · `downloadMaterialOriginal()` | 파일 |
| 7 | 📧 메일 자료 보내기 | `openSendMaterials()` 계열 | 파일 |

기존 기록은 `pucards/sendLog/{cardId}` 하나뿐이다 — 메일을 «누구에게 보냈나»만 남고,
자료를 «가져갔나»는 아무 데도 안 남는다.

## 2. 고른 길 — 문지기를 «한 곳»에 둔다

일곱 문이 전부 함수 하나를 지난다.

```
내보내기 단추 → puExport(문, 건수, 무엇을) → ① 대량이면 사유 묻기 (취소 가능)
                                            ② 기록 남기기
                                            ③ 대량이면 대표 알림
                                            ④ true 를 돌려주면 그제서야 파일이 만들어진다
```

**왜 이 길인가.** 문마다 기록 한 줄씩 넣는 방법은 손이 덜 가지만 **여덟 번째 문에서
반드시 샌다.** 이 저장소가 이미 여러 번 겪은 무늬다 — 2026-08-29 하루에만
「거르개를 네 자리에 안 넣어 0건에 갇힌 일」, 「고르기만 다시 그리기를 한 길에서
빠뜨린 일」이 같은 꼴이었다. 자리가 하나여야 빠뜨릴 자리가 없다.

**서버가 내보내기를 만들어 주는 길**(우회 불가)은 화면이 RTDB 를 직접 읽는 지금 구조를
다시 짓는 일이라 몇 달짜리다. 기업정보함뿐 아니라 사진첩·급여데이터함도 같은 구조다.
지금 할 일이 아니다.

### 함수 모양

```js
/* 밖으로 나가는 모든 길은 여기를 지난다.
   true 를 돌려줄 때만 파일이 만들어진다 — 부르는 쪽은 반드시 결과를 본다. */
async function puExport(kind, n, what)
```

| 인자 | 뜻 | 보기 |
|---|---|---|
| `kind` | 어떤 문 | `'xlsx' | 'csv-addr' | 'vcf' | 'photo' | 'copy' | 'material' | 'mail-attach'` |
| `n` | 건수 | `6295` |
| `what` | 무엇을 (사람이 읽는 말) | `'명함 · 전체'` · `'주소록 · 2곳'` |

돌려주는 값: `true` = 진행, `false` = 사람이 사유 창에서 취소했다.

### 드러내 놓기 (대표 결정)

| 양 | 화면에 보이는 것 |
|---|---|
| 200건 미만 | 토스트 한 줄 — 「이 내려받기는 기록됩니다」 |
| 200건 이상 | 창 — 「6,295건을 내려받습니다. 어디에 쓰실 건가요?」 + 사유 한 줄 + [내려받기]/[취소] |

사유는 **비워도 진행된다**(막는 장치가 아니다). 다만 비면 기록에 `why:''` 로 남고,
대표 알림에 「사유 없음」으로 뜬다.

### ⚠ 복사(📋)만은 순서를 뒤집어야 한다

브라우저는 `navigator.clipboard.writeText()` 를 **사람이 누른 그 순간에만** 허용한다.
앞에서 `await`(기록 쓰기·창 띄우기)를 하면 그 「누른 순간」이 끊겨, 사파리·일부
크롬에서 **복사가 조용히 실패한다.**

그래서 복사만은 **먼저 복사하고, 기록은 그 뒤에 남긴다.**
복사는 늘 1건~여러 건이고 사유를 묻는 200건에 닿는 일이 거의 없으므로 순서를 뒤집어도
잃는 것이 없다. 200건이 넘는 복사라면 «복사한 뒤» 사유를 묻는다.
이 예외는 코드에도 같은 말로 적어 둔다 — 모르고 「통일」하면 복사가 죽는다.

## 3. 기록 — 무엇을 남기고, 무엇을 «안» 남기나

```
exportLog/{pushId} = {
  at:   1756000000000,   // 언제  (서버 시각 — §5 의 규칙이 강제한다)
  by:   '권형하',         // 누가  (이름 — 읽기 쉬우라고)
  uid:  'abc123…',        // 누가  (계정 — 이름은 바뀔 수 있다. 이쪽이 진짜다)
  kind: 'xlsx',           // 어떤 문
  what: '명함 · 전체',     // 무엇을
  n:    6295,             // 몇 건
  why:  '거래처 정리용'     // 사유 (200건 이상일 때만 묻는다)
}
```

### ⚠ 내용은 «안» 남긴다

명함 6,295건의 값을 기록에 담으면 **그 기록이 두 번째 유출원**이 된다.
「무엇을 몇 건」까지만 남긴다. 이름·전화·이메일은 한 글자도 안 들어간다.

---

## 4. 어디에 두나 — `pucards` «밖»에 둔다 ★

**파이어베이스 규칙에는 함정이 하나 있다: 부모가 준 읽기 권한은 자식이 못 뺏는다.**

`pucards` 에 이미 `.read` 가 걸려 있으면, 그 아래 `pucards/exportLog` 에
「관리자만」이라고 아무리 적어도 **직원이 그대로 읽는다.** 규칙은 아래로 흐르고,
자식은 그것을 좁힐 수 없다.

그래서 기록은 **맨 위 칸에 따로 둔다.**

```
exportLog/{pushId}     ← 반출 기록 (덧붙이기만 · 관리자만 읽음)
exportSeen/{uid}       ← 대표가 「확인」한 시각 (알림 배지를 끄는 데만 쓴다)
```

`pucards` 안에 두지 않는 것은 그 함정 하나 때문이다. **자리를 옮기지 말 것.**

### 왜 `exportSeen` 을 따로 두나

기록에 `seen:true` 를 적으면 «기록을 고치는» 것이 된다. 그러면 규칙에서 고치기를
열어 줘야 하고, 고칠 수 있는 기록은 지울 수도 있게 된다. 기록은 **끝까지 못 건드리게**
두고, 「어디까지 봤나」만 딴 칸에 적는다.

## 5. 규칙 — 지울 수 없는 기록 ★

> **자기 기록을 지울 수 있으면 기록은 아무 뜻이 없다.**

```json
"exportLog": {
  ".read": "auth != null && root.child('uid_roles').child(auth.uid).child('isAdmin').val() == true",
  "$id": {
    ".write": "auth != null && !data.exists() && newData.exists()",
    ".validate": "newData.hasChildren(['at','by','uid','kind','what','n'])
                  && newData.child('uid').val() === auth.uid
                  && newData.child('at').val() === now
                  && newData.child('n').isNumber()"
  }
},
"exportSeen": {
  "$uid": {
    ".read":  "auth != null && auth.uid === $uid",
    ".write": "auth != null && auth.uid === $uid && root.child('uid_roles').child(auth.uid).child('isAdmin').val() == true"
  }
}
```

| 규칙 조각 | 막는 것 |
|---|---|
| `!data.exists()` | **고치기·지우기.** 새로 만드는 것만 된다 |
| `uid === auth.uid` | **남의 이름으로 적기** |
| `at === now` | **날짜 속이기.** 앱은 `ServerValue.TIMESTAMP` 로 적어야 통과한다 |
| `.read` 관리자 | 직원이 남의 반출 기록을 들여다보는 것 |

⚠ 규칙은 **콘솔이 진짜다.** 저장소 파일로 배포하면 사진첩·성과확인이 막힌 적이 있다.
붙여넣을 글을 `docs/firebase-rules-반출기록-한칸만-넣기.txt` 로 따로 만들고,
**대표가 콘솔에 붙여넣는다.**

⚠ 규칙을 넣기 «전»에는 기록 쓰기가 조용히 실패한다. 그래서 앱은 실패를 삼키지 않고
「기록을 남기지 못했습니다 — 관리자에게 알려 주세요」를 띄운다(§6 마지막 줄).

## 6. 대표가 아는 길

포털(`enter.html`) **기업정보함 타일에 빨간 배지.**
지금 쓰는 「💰 입금 확인」(하나은행)과 **같은 방식·같은 코드 모양**을 따른다
(`portalHanaPaintBadge` → `.tile-alert`). 새로 짓지 않는다.

- 배지에 뜨는 수 = `exportLog` 에서 `at > exportSeen/{내 uid}` 이면서 `n >= 200` 인 건수
- 누르면 창 — 「누가 · 언제 · 어떤 문 · 무엇을 · 몇 건 · 왜」
- [확인] 을 누르면 `exportSeen/{uid} = now` → 배지가 사라진다
- 0건이면 배지를 **아예 안 만든다** (늘 켜진 등은 아무것도 알려 주지 못한다)

기업정보함 안에도 **「반출 기록」 화면**을 둔다(환경설정 안, 관리자만).
200건 미만까지 **전부** 보인다 — 300건씩 스무 번 나눠 가져가는 것은 배지로는 안 잡히고
이 목록에서만 보인다.

기록 쓰기가 실패하면 **파일을 만들지 않는다.** 「기록이 안 남는 내려받기」가 있으면
이 시스템 전체가 뜻을 잃는다.

## 7. 이번에 «안» 하는 것

| 안 하는 것 | 까닭 |
|---|---|
| 화면 캡처 막기 | 불가능하다 |
| 파일에 워터마크(받은 사람 이름 박기) | 뜻은 있으나 지금 목표가 아니다. 기록이 먼저다 |
| 문 잠그기(관리자만 내보내기) | **2단계.** 기록 2~3주 뒤, 「진짜 쓰는 문」을 보고 정한다 |
| `pucards` 자료 자체를 관리자만 읽게 | 별건으로 이미 «중단» 상태다(2026-08-29 대표 지시) |

### 보관 기간 — 2년 (대표 결정)

정책은 지금 못 박는다: **2년 지난 기록은 지운다.**
다만 **지우는 장치는 지금 만들지 않는다.**

- 오늘 만드는 첫 기록이 지워질 때는 **2028-08** 이다. 지금 만들면 2년 동안 아무 일도
  안 하는 코드가 된다.
- 더 중요한 까닭: **지울 수 있는 장치가 있다는 것 자체가 약점이다.** 기록의 값어치는
  「아무도 못 지운다」에서 나온다.
- 만들 때는 **서버(Cloud Functions 예약 작업)가 지운다.** 앱에는 지우는 단추를 두지
  않는다 — 규칙의 「지우기 금지」는 그대로 두고, 서버만 관리자 권한으로 지운다.
- 규칙 파일과 반출 기록 화면에 이 정책을 글로 적어 둔다(2028 년에 이 설계서를 다시
  찾지 않아도 되게).

## 8. 검사 — 이 설계가 «썩지 않게»

| 검사 | 무엇을 지키나 |
|---|---|
| ★ 문지기를 안 거친 내려받기가 없다 | `URL.createObjectURL` · `XLSX.writeFile` · `clipboard.writeText` 가 나오는 자리는 모두 `puExport(` 뒤에 온다. **여덟 번째 문이 생기면 여기서 걸린다** |
| ★ 기록에 «내용»이 안 들어간다 | 남기는 칸이 `at·by·uid·kind·what·n·why` 일곱뿐이다 |
| 기록은 서버 시각으로 적는다 | `ServerValue.TIMESTAMP` — 규칙의 `at === now` 와 짝이다 |
| 대량 기준이 한 곳에만 있다 | 200 이라는 수가 코드 여러 곳에 흩어지지 않는다 |
| 기록 쓰기가 실패하면 파일을 안 만든다 | 「기록 없는 내려받기」가 생기지 않는다 |
| 기록은 `pucards` 밖에 있다 | §4 의 함정 — 자리를 옮기면 직원이 다 읽게 된다 |

검사를 쓴 뒤 **고친 자리를 도로 막아 걸리는지 확인**하고 그 결과를 PR 에 적는다
(저장소 규칙 — 통과만 하고 아무것도 안 지키는 검사를 만들지 않는다).

## 9. 순서

**1단계 (지금)**
1. 문지기 `puExport()` 를 만든다
2. 일곱 문을 문지기 뒤로 옮긴다
3. 사유 창 (200건 이상)
4. 반출 기록 화면 (환경설정 안 · 관리자만)
5. 포털 타일 배지 (하나은행 방식 그대로)
6. 규칙 붙여넣기 글 → **대표가 콘솔에 넣는다**

**2단계 (2~3주 뒤)**
기록을 보고 「한 번도 안 쓴 문」부터 관리자 전용으로 돌린다.
그때가 되면 무엇이 업무에 꼭 필요한지 **짐작이 아니라 기록으로** 안다.
