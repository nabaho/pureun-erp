# 사진첩 — 서버 쪽 사진 이사 도구 설계서

2026-08-13 확정 · 대표 승인 · 관련: PR #192 (`js/pu-photo-store.js` 창고 이전, 클라이언트 쪽)

> **한 줄 요약**
> 총괄 관리자가 **다른 직원들**의 사진첩 사진을 실시간DB에서 파일 창고(Storage)로 옮길 수 있게, Admin SDK로 창고 규칙을 우회하는 Cloud Function을 만든다.

---

## 1. 왜 필요한가

PR #192 로 클라이언트 쪽 `PuPhotoStore.migrateToStorage()`가 이미 있다. 하지만 창고
보안 규칙(`docs/firebase-storage-사진첩-새창고(붙여넣기용).txt`)은 **본인 자리만** 쓰기를
허락한다 — 실시간DB의 `uid_roles/isAdmin`을 창고 규칙이 읽을 방법이 없어서다.

그 결과: 관리자가 자기 자신의 사진은 클라이언트 도구로 옮길 수 있지만, **다른 직원의**
사진을 옮기려 하면 창고 쓰기가 막혀 그 직원 몫만 실패로 잡힌다(사진을 잃지는 않는다 —
실시간DB에 그대로 남는다). 여러 직원 사진을 한꺼번에 옮기려면 Admin SDK로 규칙을
완전히 우회하는 **서버 쪽** 도구가 있어야 한다 — 이 문서가 그것을 다룬다.

---

## 2. 이번 결정 두 가지 (대표 승인)

| 질문 | 결정 |
|---|---|
| 어떻게 실행하나 | `pu-photos.html`에 총괄 관리자 전용 버튼 |
| 한 번에 얼마나 옮기나 | 한 번 호출에 조금씩(기본 30장) — 버튼을 여러 번 눌러 이어감 |

버튼 방식을 고른 이유: 개발자 도구 콘솔을 열게 하는 것보다 관리자가 진행 상황(옮김/
건너뜀/실패 수)을 화면에서 바로 볼 수 있다. 배치 방식을 고른 이유: 직원·사진이 많으면
한 번의 HTTPS 호출이 Cloud Functions 시간제한(기본 60~540초)에 걸릴 수 있다 — 작게
나누면 그 위험이 사실상 없어진다.

---

## 3. 트리거 — `pu-photos.html`

- 총괄 관리자(`PuPhotoStore`가 이미 아는 `isAdmin`)에게만 보이는 버튼
  **[전체 직원 사진 창고로 옮기기]**.
- 누르면 `confirm()` — 명함첩의 `pucardsMovePhotosToStorage`와 같은 패턴:
  "실시간DB에 있는 사진을 파일 창고로 옮깁니다. 옮긴 뒤엔 실시간DB에서는 지워집니다
  (창고에는 그대로 있습니다). 계속할까요?"
- 확인하면 서버 함수를 **자동으로 반복 호출**한다 — 매 호출 결과의 `done`이 `false`인
  동안 다음 호출을 이어서 보낸다. 화면에는 누적 옮김/건너뜀/실패 수를 보여준다.
- 호출 도중 사용자가 화면을 벗어나도 안전하다 — 이미 옮긴 사진은 실시간DB에
  `loc:'storage'`가 남아 있어(멱등성, 클라이언트 쪽과 동일), 버튼을 다시 누르면
  그 지점부터 이어간다. 명시적인 재개 커서를 주고받을 필요가 없다.
- 실패(권한 만료 등)는 토스트로 알리고 멈춘다 — 계속 눌러도 안 되면 사람이 봐야 한다.

## 4. 서버 함수 계약 — `functions/index.js`

```
exports.migratePhotosToStorage = functions.https.onRequest(async (req, res) => { ... });
```

- CORS: 기존 `PORTAL_ORIGIN`/`setAutomationCors` 그대로 재사용(새로 만들지 않는다).
- 인증: 기존 `requirePrimaryAdmin`과 같은 골격 — `Authorization: Bearer <idToken>` →
  `getAuth().verifyIdToken()` → `uid_roles/{uid}/isAdmin === true` 확인. 문구만
  "총괄관리자만 사진을 옮길 수 있습니다"로 바꿔 별도 함수로 둔다(기존 함수들도
  메시지별로 따로 두는 것이 이 저장소의 관례 — `requireStaff`와 `requirePrimaryAdmin`도
  통합돼 있지 않다).
- 요청: `POST { limit?: number }` — `limit` 생략 시 30.
- 응답: `{ ok: true, moved, skipped, failed, done }`
  - `done: true` — 더 옮길 사진이 없다(전체 완료).
  - `done: false` — 이번 호출에서 `limit`만큼(또는 그 전에 훑을 것을 다 훑었지만
    아직 못 끝냈을 때) 처리했고, 이어서 호출해야 한다.
  - 실패 항목이 있어도 `ok: true`로 응답한다(부분 실패는 정상 흐름의 일부다) — `failed`
    수로 알린다. 인증·입력 자체가 잘못됐을 때만 `ok:false` + 4xx.

## 5. 핵심 로직 — 새 파일 `functions/photos-migrate.js`

`functions/dev-automation.js`와 같은 철학: **firebase-admin에 직접 의존하지 않는 순수
함수**로 짠다. `db`(RTDB 접근 인터페이스)와 `bucket`(Storage 접근 인터페이스)을 인자로
받는다 — `js/pu-photo-store.js`의 `deps` 주입 패턴과 같은 이유(테스트가 가짜 객체로
동작을 검증할 수 있게).

### 주고받는 인터페이스 (얇게 — Admin SDK를 그대로 감싸지 않는다)

```js
// db: { listOwners(), listYear(uid, year), readItem(uid, year, id), writeMigrated(uid, year, id) }
// bucket: { upload(path, base64Body), exists(path) }
```

`index.js`의 HTTPS 핸들러가 실제 `getDatabase()`/`getStorage().bucket('pureun-erp-hrphotos')`를
이 모양으로 얇게 감싸 `photos-migrate.js`의 순수 함수에 넘긴다.

### 흐름 — `migrateBatch(db, bucket, limit)`

1. `db.listOwners()`로 전체 사람 목록.
2. 사람마다·연도마다(클라이언트 쪽 `candidateYears()`와 같은 순서 — 사람은
   `listOwners()`가 준 키 순서 그대로, 연도는 올해 → 과거 → `'unknown'`) 돌며,
   `loc !== 'storage'`인 항목을 만날 때마다:
   a. `db.readItem`으로 본문(base64 data URL)·미리보기를 읽는다. 본문이 없으면
      **건너뜀**(skipped++) — 실패로 세지 않는다(클라이언트 쪽과 동일 이유:
      "화면이 전혀 안 나오는 사진"은 옮길 것이 없다).
   b. base64 를 buffer 로 바꿔 `bucket.upload(fullPath, buf)` → 미리보기도 같은 방식.
   c. **되읽어 확인**: `bucket.exists(fullPath)` (메타데이터만 — 서버는 전체를 다시
      받을 필요가 없다, 이것이 클라이언트 쪽 `fetchFromBucket`과 다른 유일한 지점이고
      의도적이다). 확인 안 되면 예외 — 그 항목은 실패(failed++)로 잡고 실시간DB는
      그대로 둔다.
   d. 확인되면 `db.writeMigrated`로 `loc:'storage'` 표시 + 본문/미리보기 null을
      **한 번에** 쓴다(update 하나 — 부분 실패로 반쪽 상태가 남지 않게).
   e. `moved++`. `moved === limit`이면 그 자리에서 멈추고 `done:false`로 반환한다.
   f. 사람 하나를 다 훑어도(또는 처리 중 예외가 나도) 다음 사람으로 넘어간다 — 클라이언트
      쪽 `migrateOwnerToStorage`의 `.catch`와 같은 격리.
3. 전체를 다 훑고도 `limit`에 못 채웠으면 `done:true`로 반환한다.

### 지키는 안전장치 (클라이언트 쪽과 동일한 세 가지)

- **올리기 → 확인 → 지우기** 순서 — 확인 전엔 실시간DB 본문에 손대지 않는다.
- **한 장·한 사람 실패가 나머지를 막지 않는다.**
- **이미 옮긴 것(`loc==='storage'`)은 다시 손대지 않는다** — 멱등성, 재개 가능.

## 6. 검증

- `functions/photos-migrate.js`는 `require('../functions/photos-migrate.js')`로 직접
  불러 가짜 `db`/`bucket` 객체로 검사한다(`tests/dev-automation.test.js`와 같은 방식,
  Firebase 에뮬레이터 불필요).
- 검사 항목(클라이언트 쪽 이사 도구와 대응):
  - 올리기 → 확인 → 지우기 순서를 지킨다(먼저 지우면 안 된다).
  - `limit`에 닿으면 멈추고 `done:false`.
  - 더 옮길 것이 없으면 `done:true`.
  - 이미 옮긴 항목은 건너뛴다(재실행 안전).
  - 본문이 없는 항목은 실패가 아니라 건너뜀.
  - 확인 실패 시 실시간DB 본문을 지우지 않는다.
  - 한 사람 실패가 다른 사람을 막지 않는다.
- 이번 세션에서 해 온 것과 같은 방식으로, 위 각 안전장치를 실제로 망가뜨려 검사가
  잡는지 확인한다(뮤테이션 테스트).
- `pu-photos.html` 쪽 버튼 로직도 검사한다 — 관리자에게만 보이는지, `confirm()`을
  거치는지, `done:true`까지 자동으로 반복 호출하는지, 실패 시 멈추는지.

## 7. 이번 범위에 안 넣는 것 (YAGNI)

- 여러 관리자가 동시에 버튼을 누르는 경우의 동시성 제어 — 총괄 관리자는 현재 1~2명
  수준이라, 실무에서 동시에 누를 일이 사실상 없다. `loc==='storage'` 멱등 검사가
  최악의 경우(동시 실행)에도 같은 항목을 두 번 옮기는 것 이상의 사고는 막는다.
- 진행률 상한선 이전에 "전체 몇 장 남았는지" 미리 세어 보여주는 것 — 그 자체가 추가
  전체 훑기 비용이라 이번엔 뺀다. 버튼을 누른 횟수·누적 옮김 수로 충분히 진행을
  가늠할 수 있다.
- Cloud Scheduler 등 자동/정기 실행 — 이건 사람이 판단해 한 번 누르는 **일회성
  보정 도구**다. 자동으로 계속 도는 것은 필요해지면 그때 따로 결정한다.
