# 옛 명함에 박힌 썸네일을 밖으로 빼내기

작성 2026-08-16 · 대상 `pu-cards.html`

## 왜 필요한가

대표 지시 2026-08-16: *"정보함에 들어가면 화면이 정말 늦게 나온다. 매번 이런데 왜
이런거냥 데이터가 너무 많아서 그런것인가?"*

재 봤다(대표 기기, 콘솔):

```
명함 6,616장 · items 크기 4.92MB · 회사조립 64ms · 회사 4,138곳 · 페이지열기 548ms
thumb 2.48MB · companyAddr 0.12MB · id 0.10MB · email 0.09MB · mobile 0.09MB · …
```

**계산이 아니라 내려받기가 문제다.** 회사 4,138곳을 조립하는 데 64ms 밖에 안 걸린다.
느린 것은 기업정보함을 열 때마다 `pucards/items` 를 통째로 4.92MB 받기 때문이고,
**그 절반인 2.48MB 가 썸네일 하나**다. 나머지 아홉 칸을 다 합쳐도 0.7MB 가 안 된다.

## 이미 고쳐진 문제다 — 옛 자료만 남았다

이 파일은 이미 썸네일을 items 밖에 두기로 정해 놓았고(`pu-cards.html` 의
`Store.put`·`putThumb`·`getThumb`), 주석에도 이유가 적혀 있다:

> items 는 `.on('value')` 로 통째 구독한다. 썸네일(장당 약 20KB)이 그 안에 있으면
> 명함첩을 열 때마다 4,400장 전부를 받는다(약 90MB). 밖으로 빼서 **화면에 보이는 것만**
> 받는다.

`Store.put(it)` 은 저장할 때마다 `thumb`·`thumb2` 를 떼어 `{root}/thumbs/{id}` 로 보낸다.
**그 변경 뒤로 한 번도 저장된 적 없는 옛 명함들만** 아직 안에 품고 있다.

즉 새 구조를 만드는 일이 아니라 **남은 것을 정해진 자리로 옮기는** 일이다.

## 지금 구조 (그대로 쓴다)

| | 자리 | 함수 |
|---|---|---|
| 명함 본문 | `{root}/items/{id}` | `Store.put` — 저장 때 `thumb`·`thumb2` 를 뗀다 |
| 썸네일 | `{root}/thumbs/{id}`, 뒷면은 `{id}_b` | `putThumb` / `getThumb` / `delThumb` |
| `{root}` | 공용은 `pucards`, 대표 개인 창고는 따로 | `Store._rootOf(id)` |

화면은 `it.thumb` 의 **세 가지 상태**로 갈린다(`renderList` 주석):

```
① 값이 있다      = 옛 자료(아직 안 옮김) 또는 이미 받아 둔 것 → 바로 그린다
② 빈 문자열      = 사진 없는 명함 → 첫 글자만, 받으러 가지 않는다
③ 아예 없다      = 옮겨진 자료 → 화면에 들어올 때 받는다
```

옮기고 나면 ①이 ③이 된다 — 화면 쪽은 **고칠 것이 없다.**

## 만들 것

### 1. 대상 세기 (`countInlineThumbs`)

`state.items` 를 훑어 `thumb` 또는 `thumb2` 에 값이 있는 명함을 센다. 개수와 대략의
크기(글자 수 합)를 돌려준다. **아무 것도 저장하지 않는다.**

### 2. 옮기기 (`migrateInlineThumbs`)

**한 장을 옮기는 것은 한 번의 원자적 쓰기로 한다.** 썸네일을 새 자리에 넣는 것과
옛 자리를 비우는 것을 **같은 `update()`** 에 담는다:

```
upd['thumbs/<id>']        = <그림>
upd['items/<id>/thumb']   = null
```

이러면 둘 다 되거나 둘 다 안 된다 — **그림이 사라지는 중간 상태가 없다.** 「먼저 쓰고
나중에 지운다」보다 안전하다(그 방식은 사이에서 끊기면 어느 쪽인지 알 수 없다).

⚠ **`items/<id>` 를 통째로 다시 쓰지 않는다.** `thumb` 칸만 `null` 로 지운다 — 통째
쓰기는 그 사이 남이 고친 이름·전화를 되돌린다(2026-08-11 실제 사고와 같은 종류).

**묶어서 보낸다.** 한 장씩 보내면 수백 번의 쓰기가 몰려 서버가 막힌다(2026-08-16 에
자동 폴더 배정이 한 장씩 저장해 폭주한 전례가 있다). 한 번에 **50장씩** 묶고, 묶음
사이에 숨을 돌린다. 각 묶음은 그 자체로 원자적이다.

**뿌리(root)별로 나눈다.** 공용(`pucards`)과 대표 개인 창고는 다른 뿌리라 한 `update()`
에 섞을 수 없다. `Store._rootOf(id)` 로 갈라 각각 묶는다.

**옮긴 것은 `thumbCache` 에 넣는다** — 지금 보고 있는 화면이 방금 옮긴 그림을 다시
받으러 가지 않게. 화면 새로고침 없이도 그대로 보인다.

### 3. 누르는 자리

⚙️ 환경설정 안에 넣는다. **대표만 보인다**(`state.isAdmin`).

누르면 **먼저 세어서 알려주고 확인을 받는다**:

```
옛 명함 124장에 그림이 박혀 있습니다 (약 2.4MB).
밖으로 옮기면 명함첩을 열 때 그만큼 덜 받습니다.
그림은 그대로 보입니다 — 자리만 옮깁니다.

[옮기기]  [취소]
```

옮기는 동안 진행 상황을 보이고, 끝나면 몇 장을 옮겼는지 알린다.

## 안 하기로 한 것

- **자동으로 안 돌린다.** 화면을 열었다는 이유만으로 수백 건이 저장되면 안 된다 —
  사람이 누를 때만 움직인다.
- **원본 사진(`photos/`)은 안 건드린다.** 이번 대상은 목록용 작은 그림뿐이다.
- **`Store.put`·`getThumb`·`renderList` 는 안 고친다.** 이미 옳게 되어 있다.
- **되돌리는 단추는 안 만든다.** 옮긴 그림은 `thumbs/` 에 그대로 있고 화면도 그대로
  보이므로 되돌릴 이유가 없다. 정말 필요하면 명함을 한 번 저장하면 된다.

## 에러 처리

- 클라우드가 아니면(`Store.mode!=='firebase'`) 안내만 하고 아무 것도 안 한다.
- 대표가 아니면 단추가 안 보이고, 함수에서도 한 번 더 막는다.
- 묶음 하나가 실패하면 **거기서 멈추고** 몇 장까지 옮겼는지 알린다 — 이미 옮긴 것은
  원자적으로 끝났으므로 안전하고, 다시 눌러 이어서 하면 된다(남은 것만 다시 센다).
- 그림이 빈 문자열(`''`)인 명함은 **건드리지 않는다** — 「사진 없음」을 뜻하는 상태(②)라
  지우면 화면이 매번 받으러 간다.

## 기대 효과

`items` 4.92MB → **약 2.4MB**. 기업정보함·명함첩을 열 때마다 그만큼 덜 받는다.
직원 열 명이 하루 다섯 번 열면 하루 약 125MB 를 덜 내려받는다.

## 검사

- `countInlineThumbs` — 값 있는 것만 센다(빈 문자열·없는 칸은 안 센다), 앞면·뒷면 둘 다.
- `thumbMigrationPlan(items, root, 50)` 같은 **순수 함수**로 「무엇을 어느 경로에 쓸지」를
  만들고 그것을 검사한다:
  - `thumbs/<id>` 와 `items/<id>/thumb: null` 이 **같은 묶음**에 들어간다
  - `items/<id>` 를 통째로 쓰는 경로가 **하나도 없다**
  - 묶음 크기가 50을 안 넘는다
  - 빈 문자열 썸네일은 계획에 안 들어간다
  - 뒷면(`thumb2`)은 `thumbs/<id>_b` 로 간다
  - 뿌리가 다른 것은 다른 묶음으로 간다
- 대표가 아니면 아무 것도 안 쓴다.
- 뮤테이션으로 위 검사들이 실제로 잡는지 확인한다.
