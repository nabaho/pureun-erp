# 푸른이알피 부팅 내려받기 줄이기 — 설계서

- 날짜: 2026-08-16
- 대표 지시: "계속 비용이 올라가는 부분을 어떻게 해결해야할지 검토하고 있다. 다시검토해달라."
- 앞선 작업: PR #263(잃어버린 자료 찾기), PR #265(대시보드 🔄), PR #266(접속자 심장박동)
- 대표 결정: **「안전한 것만 — 기록 구조는 그대로」**, 방안 **A+B 함께**

## 1. 무엇이 문제인가 (실측)

이번 달 요금(8/1~8/16, `billing/current`):

| 항목 | 금액 | 비중 |
|---|---|---|
| 실시간DB | ₩74,799 | 95% |
| 사진 창고 | ₩0.12 | 0% |
| 서버·메일 | ₩0 | 0% |

사진첩은 무죄임을 증거로 확인했다 — 직원 6명 전원의 `puphotos/u/*/blobs`·`thumbs`
가 모두 `null`(본문·미리보기 0건, 전부 창고).

푸른이알피는 켤 때 `data` 노드를 통째로 `once('value')` 로 받는다. **실측 2.83MB**:

| 열쇠 | 크기 | 비중 |
|---|---|---|
| finance_income | 958KB | 33% |
| payroll_monthly | 373KB | 13% |
| companies | 281KB | 10% |
| cms_ledger | 240KB | 8% |
| contracts | 178KB | 6% |
| ledger_batches | 134KB | 5% |
| payroll_audit_log | 133KB | 5% |
| contract_forms | 123KB | 4% |
| co_merge_log | 89KB | 3% |

### 요금보다 먼저인 것 — 자료보호

`uid_roles` 실측: **계정 10개 중 재무 권한(`fin`)은 2개뿐이다.**

즉 **8명이 볼 수 없는 자료를 매번 내려받고 있다.** 전 직원 급여
(`payroll_monthly` 373KB)와 수입 내역(`finance_income` 958KB)이 권한 없는
직원의 브라우저(localStorage)에 그대로 깔린다. 화면에서 메뉴만 가려져 있다.

**이 설계의 첫째 목적은 요금이 아니라 이것을 막는 것이다.**

## 2. 하지 않기로 한 것

**큰 표를 해별로 쪼개거나 옛 자료를 보관소로 옮기는 것은 하지 않는다.**

`finance_income` 은 `dbGet('finance_income', [])` 로 **30곳 넘게 동기(sync)로**
읽힌다. 게으른 로딩으로 바꾸면 그 전부를 비동기로 고쳐야 하고, 하나라도 놓치면
**재무 화면이 조용히 일부만 보여준다** — 돈 계산에서 가장 위험한 실패다.
남은 금액(월 ₩3,000~11,000 추정)이 그 위험을 정당화하지 못한다.

`cold_storage` 라는 칸이 이미 있으나 **실제 보관이 아니라 시뮬레이션 껍데기**다
(`showToast('콜드 이전 완료 (시뮬레이션)')`). 따라야 할 기존 패턴이 아니다.

## 3. 설계

### 3.1 뼈대 — 통째 읽기에서 열쇠별 읽기로

`fbInitialSync()` 의 `fbDb.ref('data').once('value')` 를 **열쇠별 읽기**로 바꾼다.
새로 만드는 것이 아니라 **이미 있는 `_fbInitialSyncPerKey()` 를 승격**한다 —
보안규칙이 통째 읽기를 거부할 때 쓰려고 만들어 둔, 같은 보호(`_fbApplyRecord`)를
통과하는 경로다.

읽을 열쇠는 세 무리로 가른다.

```
BOOT_KEYS   = 화면이 켜지자마자 필요한 것          → 늘 받는다
FIN_KEYS    = 재무·급여 (FB_FIN_KEYS 그대로)      → fin 권한일 때만 받는다
COLD_KEYS   = 로그·감사·병합기록                  → 부팅에 안 받는다
```

`COLD_KEYS` (방안 B) — 부팅에 안 받는다:

| 열쇠 | 크기 | 왜 빼도 되나 |
|---|---|---|
| payroll_audit_log | 133KB | 급여 감사 로그. 감사 화면을 열 때만 본다 |
| co_merge_log | 89KB | 업체 병합 기록. **이미 `FB_EXCLUDE` 라 올리지도 않는다**(내려받기만 했다) |
| closed_archive | 54KB | 종료 보관분 |
| audit_log · error_log · backup_history · integrity_results · cert_log | 8KB | 진단용 |

합계 약 284KB. 이것들을 보는 화면은 열 때 그 열쇠만 따로 읽는다(3.4).

### 3.2 권한을 어떻게 아는가 — 닭과 달걀

지금 `hasFin` 은 `user_accounts`·`security_perms` 를 **로컬에서** 읽어 계산한다.
그런데 새 기기에는 그것이 아직 없다. 「무엇을 받을지 정하려면 권한을 알아야 하고,
권한은 받아 봐야 안다」가 된다.

**해결**: `uid_roles/{uid}` 를 서버에서 직접 한 번 읽는다.
- 아주 작은 칸이다(계정당 수십 바이트).
- **Firebase 규칙이 판단 근거로 쓰는 바로 그 값**이다(`pu-erp.html` 의 `fin:` 주석
  "규칙이 이 값을 봄"). 화면과 서버가 같은 것을 보게 된다.

### 3.3 모르면 다 받는다 (fail-open)

권한 조회가 **실패하거나·늦거나·값이 없으면 예전처럼 전부 받는다.**

재무 담당자가 빈 화면을 보는 것보다 요금을 조금 더 내는 쪽이 낫다.
돈 계산에서 「조용히 일부만 보이는 것」이 가장 위험하다.

구체적으로 `fin` 이 **명시적으로 `false` 일 때만** 재무 열쇠를 건너뛴다.
`undefined`·조회 실패·`uid_roles` 자체가 없음 → 전부 받는다.

### 3.4 안 받은 것이 필요해지면

재무 화면·감사 화면을 열 때 그 열쇠를 그 자리에서 읽는다.

```
ensureKeys(['finance_income', 'payroll_monthly'])   // 이미 있으면 아무것도 안 한다
```

- 이미 로컬에 있으면 곧바로 끝난다(두 번 안 받는다).
- 실시간 구독(`.on('child_changed')`)은 지금 그대로 둔다 — 한 번 받은 뒤에는
  구독이 최신을 밀어 준다.
- 권한이 없어 거부되면 조용히 건너뛴다(지금 `_fbInitialSyncPerKey` 와 같다).

### 3.5 빠뜨림 방지 — 이 설계의 가장 큰 위험

「목록에 있는 것만 받기」는 **새 열쇠가 조용히 영영 안 받아지는** 함정이 있다.
실제로 지금 서버 `data` 에는 `FB_ALL_SYNC_KEYS`(72개)에 없는 열쇠가 **87개**
있다(250KB). 그중 222KB 는 마침 빼려는 로그 둘이지만, 나머지에는 **이사 완료
표시**(`*_v1_done`, `mig_*`)가 섞여 있다 — 이것이 안 받아지면 **이미 끝난 이사가
다시 돈다.**

그래서 두 가지를 함께 둔다.

1. **`BOOT_KEYS` 에 지금 서버에 있는 열쇠를 모두 넣는다** — `COLD_KEYS` 와
   `FIN_KEYS` 로 뺀 것만 빼고. 즉 **기본은 「받는다」이고, 빼는 것만 이름을 적는다**
   (denylist 사고). 새 열쇠가 생겨도 다음 항목이 잡는다.
2. **표류 점검기**를 둔다. 관리자 콘솔에서 `erpAuditSyncKeys()` 를 부르면 서버
   `data` 의 실제 열쇠와 목록을 대조해 **목록에 없는 열쇠를 보고**한다.
   부팅 때 자동으로 돌리지 않는다 — 그 자체가 통째 읽기라 지금 고치려는 바로
   그 비용이다(PR #263 의 교훈: 「검사 화면이 자동으로 큰 것을 받게 두지 말 것」).

| 대상 | 지금 | 뒤 | 줄어드는 양 |
|---|---|---|---|
| 재무 권한 없는 8명 | 2.83MB | 약 1.46MB | **48%↓** |

## 5. 검사 방법

이 저장소가 오늘 두 번 데인 함정을 피한다: **「글자가 있나」식 검사는 쓰지 않는다.**
(오늘 "fbInitialSync() 를 바로 부르지 않는다"라는 **설명 주석 자체**가 「직접
부른다」로 잡혔다.)

가짜 db 로 **실제로 돌려서 무엇을 몇 번 읽는지 센다.**

1. `fin:false` → 재무 열쇠를 **한 번도 안 읽는다**(읽은 경로 목록으로 확인)
2. `fin:true` → 재무 열쇠를 읽는다
3. `uid_roles` 조회 실패 → **전부 읽는다**(fail-open)
4. `fin` 이 `undefined` → 전부 읽는다
5. `COLD_KEYS` 는 어느 경우에도 부팅에서 안 읽는다
6. `ensureKeys()` 를 두 번 불러도 **두 번 안 읽는다**
7. 권한 거부(reject)가 나도 나머지 열쇠는 계속 읽는다
8. `BOOT_KEYS ∪ FIN_KEYS ∪ COLD_KEYS` 가 현재 서버 열쇠를 **하나도 안 빠뜨린다**
   (실측 열쇠 목록을 고정값으로 박아 두고 대조)

뮤테이션으로 확인할 것:
- 권한 검사 제거 → 1번 실패
- fail-open 을 fail-closed 로 → 3·4번 실패
- `ensureKeys` 의 「이미 있으면 건너뛰기」 제거 → 6번 실패

---

## 6. 하지 않는 것 (범위 밖)

- 큰 표 쪼개기·옛 자료 보관 (2절)
- Firebase 규칙 배포 — 규칙은 콘솔이 진짜이고, 잘못 올리면 사진첩·성과확인이
  막힌 전례가 있다. 이 설계는 **화면 쪽만** 고친다.
- 실시간 구독(`.on`) 구조 — 지금 그대로 둔다
- 권한 없는 직원 기기에 **이미 깔린** 자료 지우기 — 별건으로 다룬다

---

## 7. 되돌리기

한 줄로 끈다: `BOOT_KEYS` 계산에서 권한·COLD 가르기를 건너뛰고 예전처럼
`data` 통째 읽기로 돌아가는 스위치를 남긴다(`window.erpBootFullSync = true`).
문제가 생기면 콘솔에서 켜고 새로고침하면 곧바로 예전 동작이다.

## 8. 구현 반영 (2026-08-16, 구현하며 설계와 달라진 점)

1. **`BOOT_KEYS` 굳은 목록 대신 서버의 지금 명단(shallow)** — 3.5절의 표류 문제를
   목록+점검기가 아니라 뿌리에서 없앴다. 부팅 때 REST `shallow=true`(이름만, 몇 KB)로
   실제 열쇠 명단을 받아, 빼는 것(FB_COLD_KEYS·fbShouldSync·재무 가르기)만 걸러낸다.
   새 열쇠·이사 완료 표시는 저절로 포함된다. 점검기(`erpAuditSyncKeys`)는 보고용으로만 남겼다.
2. **가장 큰 발견 — 부팅 이중 다운로드**: 통째 `once('value')`(2.83MB) **뒤에**
   `data.on(child_added)` 를 붙여 서버가 **같은 것을 한 번 더** 보냈다(주석에 "no-op"
   이라 적혀 있던 그 발화 — CPU 만 공짜였지 내려받기는 통째 한 벌). 켤 때마다 5.7MB.
   열쇠별 `on('value')` 은 **첫 값이 곧 초기 동기화**이고 그대로 실시간 구독으로
   남아 한 번만 받는다. 복귀 재동기화·수동 새로고침도 이미 붙은 구독은 안 다시
   붙이므로 사실상 공짜가 됐다.
3. **`FB_FIN_GATED` ≠ `FB_FIN_KEYS`**: `funds`(기금 **업무** 목록)·`mgr_rates` 는
   전 직원 업무 화면이 써서 가르기에서 **뺐고**(작은 돈 아끼려고 업무 화면을 깨지
   않는다), 목록이 만들어진 뒤 생긴 재무 키(`cms_ledger` 240KB·`ledger_batches`
   134KB·`bank_processed`·`ledger_held`·`payer_aliases`)를 **더했다**.
4. **COLD 는 `payroll_audit_log`(133KB) 하나만**: `closed_archive`·`audit_log` 등은
   합쳐 60KB 라 읽기-덧붙이기-쓰기 경로를 전부 지키는 위험을 무릅쓸 값어치가 없다.
   `co_merge_log`(89KB)는 `FB_EXCLUDE` 라 자동으로 빠진다 — **읽는 곳이 한 곳도
   없는데 매번 내려오고 있었다.** `payroll_audit_log` 는 덧붙이기 전에 반드시
   서버 것을 먼저 받는 가드를 넣었다(`addPayrollAudit`) — 안 받은 채 덧붙이면
   이 기기의 낡은 사본이 서버 최신 기록을 덮는다.
5. 세션 수신량 계기(`erpBytesIn()`)를 콘솔에 뒀다 — "열어두면 얼마나 받나"를
   이제 재서 답할 수 있다.
