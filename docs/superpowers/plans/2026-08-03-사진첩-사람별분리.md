# 사진첩 사람별 분리 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 직원은 자기가 올린 사진만 보고, 총괄 관리자만 전체를 본다. **화면에서 가리는 것이 아니라 서버 규칙으로 막는다.**

**Architecture:** 실시간DB는 규칙으로 목록을 걸러 주지 못한다 — 어떤 노드를 읽으려면 그 노드에 읽기 권한이 있어야 하고, 권한이 있으면 그 아래 전부가 열린다. 그래서 **사진을 사람별 자리로 나눠 담는 것 말고는 방법이 없다.** 경로를 `puphotos/u/{계정}/…` 로 바꾸고, 관리자가 사람 목록을 훑을 수 있도록 가벼운 명단(`puphotos/owners`)을 따로 둔다.

**Tech Stack:** Firebase RTDB compat · 빌드 없음 · `node --test`

## 왜 이 결정을 다시 적어 두는가

2026-08-02 설계는 **전 직원 공유 + 개인잠금**이었다. 근거는 "사업장 담당자가 남이 찍은 현장사진을 가져가야 한다"였다. 2026-08-03 대표 지시로 **사람별 완전 분리**로 뒤집혔다.

**그래서 잃는 것을 명확히 적는다:** 다른 사람이 찍은 현장사진을 사업장 담당자가 가져갈 수 없다. 나중에 그 공유가 필요해지면 "함께 볼 사람" 목록을 사진마다 두는 방식으로 다시 열어야 한다(그때는 또 규칙을 고쳐야 한다).

## 새 데이터 자리

```
puphotos/owners/{계정} = { name, lastAt }            ← 가벼운 명단. 관리자가 사람을 훑는 용도
puphotos/u/{계정}/items/{연도}/{id}   = 정보(+read)
puphotos/u/{계정}/blobs/{연도}/{id}   = 본문
puphotos/u/{계정}/thumbs/{연도}/{id}  = 미리보기
```

**옛 자리** `puphotos/items|blobs|thumbs/{연도}/{id}` 는 이사가 끝날 때까지 그대로 둔다. **자동으로 지우지 않는다.**

## 규칙 (대표님이 게시)

```json
"puphotos": {
  "owners": {
    ".read": "root.child('uid_roles').child(auth.uid).child('isAdmin').val() == true",
    "$uid": {
      ".read": "auth.uid === $uid",
      ".write": "auth.uid === $uid && auth.token.firebase.sign_in_provider === 'password'"
    }
  },
  "u": {
    "$uid": {
      ".read": "auth.token.firebase.sign_in_provider === 'password' && (auth.uid === $uid || root.child('uid_roles').child(auth.uid).child('isAdmin').val() == true)",
      ".write": "auth.token.firebase.sign_in_provider === 'password' && (auth.uid === $uid || root.child('uid_roles').child(auth.uid).child('isAdmin').val() == true)"
    }
  },
  ".read": "auth.token.firebase.sign_in_provider === 'password'",
  ".write": "auth.token.firebase.sign_in_provider === 'password'"
}
```

- `u` 자체에는 `.read` 를 주지 않는다 — 주면 관리자가 실수로 전 직원 사진 본문을 통째로 내려받게 된다. 관리자는 `owners` 로 사람을 알고 `u/{계정}/items/{연도}` 만 골라 읽는다.
- 최상위 `.read/.write` 는 **옛 자리를 읽고 이사하기 위해 한동안 남긴다.** 이사가 끝나고 옛 자리를 지운 뒤 **반드시 지운다**(그때까지는 옛 자리가 전 직원에게 열려 있다 — 이 사실을 대표님께 분명히 알린다).

## 이사 절차 (순서를 지켜야 사진을 잃지 않는다)

- [ ] **1. 새 자리로 담는 코드를 먼저 배포한다.** 이때부터 새 사진은 새 자리로 간다. 옛 자리는 읽기만 한다.
- [ ] **2. 대표님이 규칙을 게시한다.** (위 규칙. 최상위 `.read/.write` 포함 — 아직 지우지 않는다)
- [ ] **3. 설정의 「사진 옮기기」를 누른다.** 옛 자리 사진을 `meta.by`(올린 사람)를 보고 그 사람 자리로 **복사**한다. 옛 것은 그대로 둔다.
- [ ] **4. 옮긴 결과를 눈으로 확인한다.** 사진 수가 맞는지, 열어서 보이는지.
- [ ] **5. 「옛 자리 지우기」를 누른다.** 3·4가 끝난 뒤에만 나타나는 단추.
- [ ] **6. 대표님이 규칙에서 최상위 `.read/.write` 두 줄을 지우고 다시 게시한다.** 이 단계까지 해야 분리가 완성된다.

**`meta.by` 가 없는 옛 사진**은 누구 것인지 알 수 없다 → **관리자 자리로 옮기고 그 수를 알린다.** 조용히 버리지 않는다.

## Task 2: 이사 도구
