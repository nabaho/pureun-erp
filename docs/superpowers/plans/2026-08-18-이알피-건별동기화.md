# 푸른이알피 — 「칸 전체」 대신 「바뀐 건만」 주고받기 (요금)

**Goal:** 실시간DB 내려받기를 **수십 배** 줄인다. 지금은 계약 한 건을 고쳐도 계약 115건 전부가 접속 중인 20대 모두에게 오간다.

**Architecture:** 읽기·쓰기 모두 `data/{칸}` **통째**에서 `data/{칸}/v/{건id}` **건별**로 내린다. 화면·저장 형식(로컬 배열)은 그대로 두고, **주고받는 단위만** 바꾼다.

**Tech Stack:** 빌드 없는 단일 파일 HTML(`pu-erp.html`) · Firebase RTDB compat · 검사는 `node --test` + `node:vm`(가짜 DB)

## 왜 그렇게 나가나

자료 모양이 이렇다:

```
data/{칸} = { u: 바뀐시각, v: { 건id: {…}, 건id: {…}, … } }
```

- **읽기**: `data` 아래를 «칸 단위»로 구독한다. 한 건이 바뀌면 **그 칸의 v 전체**가 20대 모두에게 내려간다.
- **쓰기**: 저장할 때마다 `ref('data/'+k).set({v: 전체, u: 시각})` — **칸 전체를 올린다.**
- 게다가 일부 경로는 `transaction(...)` 이라 **쓰기 전에 칸 전체를 한 번 더 받는다.**

칸 크기 예: 계약 115건 · 급여 485건 · 업체 371건 · 근태 359건.

⚠ **읽기만 고치면 소용없다.** 쓰기가 칸 전체를 올리면 서버는 「이 칸이 통째로 바뀌었다」고 보고 그대로 통째로 내려보낸다. **읽기·쓰기를 같이 바꿔야 한다.**

## Global Constraints

- **빌드 과정이 없다.** `pu-erp.html` 안에서 고친다.
- **주석은 한국어.** 「무엇을」이 아니라 **「왜」**를 적는다.
- **검사 판정은 종료코드로:** `node --test tests/*.test.js` 가 `0`.
- **커밋은 경로를 지정한다.** `git add -A` 금지(공용 작업트리).
- **실시간DB 규칙은 콘솔이 진짜다.** 규칙이 필요하면 **붙여넣을 조각을 대표께 드린다.**
- ⚠ **자료가 안 맞아 보이는 사고는 요금보다 나쁘다.** 급여·계약이 걸려 있다. 단계마다 되돌릴 수 있게 한다.

## 지켜야 하는 것 (깨지면 안 되는 장치)

| 장치 | 지금 하는 일 | 건별로 바꿀 때 |
|---|---|---|
| 급감 차단(`_handleShrinkSync`) | 칸의 항목 수가 절반 아래로 줄면 사람에게 묻는다 | 건별 삭제는 한 건씩 오므로 **창 안에서 세어** 판단해야 한다 |
| `u` 시각 비교 | 옛 값이 새 값을 덮지 않게 막는다 | **건별 `u`** 가 필요하다 |
| 오프라인 큐(`pu-resilience.js`) | 끊겼을 때 쓰기를 모아 뒀다 다시 보낸다 | 경로가 바뀌므로 함께 봐야 한다 |
| 백업(`serverBackups`) | `data` 를 통째로 읽어 저장 | 형식이 그대로면 안 건드려도 된다 |
| 형식 정규화(`normalizeFbValue`) | 객체 ↔ 배열 | 건별 적용에도 같은 규칙을 써야 한다 |

## 1단계 — 읽기를 건별로 (되돌리기 쉬움)

### Task 1: 건별 구독

**Files:** Modify `pu-erp.html`, Create `tests/erp-record-sync.test.js`

- [ ] **Step 1: 실패하는 검사부터** — 가짜 DB에 구독을 붙이고 **무엇을 구독하는지** 본다
  - `data/{칸}/v` 에 `child_added`·`child_changed`·`child_removed` 를 붙인다
  - `data/{칸}` 에 값 구독(`on('value')`)을 **안 붙인다**
  - ⚠ 「글자가 있나」가 아니라 **붙인 경로 목록**을 모아 견준다(`#321` 검사와 같은 방식)

- [ ] **Step 2: 초기 적재를 child_added 가 맡게 한다**

  `child_added` 는 붙일 때 **있는 건 전부**에 대해 발화한다 — 그것이 곧 초기 적재다.
  그러니 **따로 하는 초기 동기화를 없앤다.** 남겨 두면 또 「두 번 받기」가 된다(이미 두 번 겪었다).

  ⚠ 「다 받았다」는 신호가 없다. 화면이 그것을 기다리고 있으면 **잠깐 빈 화면**이 된다.
  → `data/{칸}/u` **하나만** 먼저 읽어(수십 바이트) 「이 칸은 받을 것이 있다」를 알고,
    건이 다 들어오면 그리게 한다. 이 값은 이미 있다.

- [ ] **Step 3: 건별 적용 경로** — `_fbApplyRecord`(칸 전체) 옆에 `_fbApplyOne(k, id, v)` 를 만든다
  - 로컬 배열에서 그 id 를 찾아 갈아 끼우고, 없으면 더한다
  - 삭제는 빼낸다
  - ⚠ 급감 차단을 **건별로 옮긴다**: 짧은 창(예: 3초) 안에 삭제가 절반을 넘으면 그때 묻는다

**Verification:** 켠 뒤 한 건을 고쳤을 때 **그 건만** 오는지 — 가짜 DB가 받은 경로·크기로 확인.

## 2단계 — 쓰기를 건별로 (여기서 값이 준다)

### Task 2: 건별 저장

- [ ] **Step 1: 검사부터** — 한 건을 고쳤을 때 **`data/{칸}/v/{id}` 만** 쓰는지, 칸 전체를 안 쓰는지
- [ ] **Step 2:** `dbSet(k, 배열)` 을 「무엇이 바뀌었는지 견주어 바뀐 건만 쓰기」로 바꾼다
  - 바뀐 건: `data/{칸}/v/{id}` 에 set
  - 지운 건: 같은 경로에 null
  - 칸 시각: `data/{칸}/u` 갱신 (한 번의 `update()` 로 함께)
- [ ] **Step 3: 건별 `u`** 를 넣는다 — 옛 값이 새 값을 덮는 것을 건 단위로도 막아야 한다
- [ ] **Step 4: `transaction` 쓰는 자리**(3638·3989·4075)를 본다 — 통째 읽기가 남아 있으면 그 자리가 그대로 비용이다

⚠ **쓰기 규칙**: 지금 규칙이 `data/{칸}` 통째 쓰기를 전제로 하면 건별 쓰기가 막힐 수 있다.
막히면 **콘솔에 붙여넣을 조각을 대표께 드린다**(규칙은 콘솔이 진짜).
