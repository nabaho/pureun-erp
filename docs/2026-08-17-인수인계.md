## 0. 가장 먼저 알아야 할 것 — 여러 세션이 동시에 이 저장소를 고친다

이번 작업 중 **같은 문제를 다른 세션이 이미 고쳐 배포한 일이 세 번** 있었다.
세 번 모두 내가 설계·구현·리뷰까지 끝낸 뒤에 알았다. **이것이 이 저장소에서 가장
많은 시간을 버리게 하는 함정이다.**

- **이알피 동기화 비용 고침** — 다 만들고 리뷰까지 끝낸 뒤 main 에 더 나은 구현
  (`8b8ac3a`)이 이미 있는 것을 발견. 내 브랜치는 버렸다.
- **폰 기업 상세** — 다른 세션이 내 브랜치의 **중간(버그 있는) 버전**을 main 에 병합해
  버려서, 반쯤 죽은 기능이 실제로 배포돼 있었다(폴더·태그가 폰에서 영영 안 뜨고
  단추가 먹통). 뒤에 고쳐 배포했다.
- **폰 메일 화면** — 아래 고정 바 + 메일 홈 + 폰용 간단 쓰기를 다 만들고 리뷰 두 번을
  돌린 뒤, main 에 `483a1ab 메일함을 폰에서도 쓸 수 있게` 가 이미 있는 것을 발견.
  **그쪽이 더 낫다** — `renderMailPage()` 자체가 PC/폰을 가르고(한 곳), 폰에서도
  **PC 쓰기 화면을 그대로 써서** 참조·숨은참조·예약시각이 다 된다. 내 「간단 쓰기」는
  그 칸들을 담을 수 없어 「고쳐 쓰기가 참조·예약시각을 잃는」 자료 유실 문제를 만들었고,
  그것을 막으려 「PC에서 고치세요」로 거절하는 코드를 넣어야 했다. 전부 버렸다(§6 참고).

**그래서 반드시**:
1. 작업 시작 전 `git fetch origin && git log --oneline -25 origin/main` 으로 무엇이
   들어와 있는지 본다. **커밋 제목만 읽어도 세 번 다 막을 수 있었다.**
2. 새 기능을 만들기 전에 **그 기능이 이미 있는지 grep 한다.** 특히 「폰에서 X 를 쓰게」
   같은 것은 `function render<X>Mobile` / `document.body.classList.contains('pc')` 로 찾는다.
3. **긴 작업은 중간에도 다시 fetch 한다.** 설계 → 계획 → 구현 → 리뷰가 몇 시간이면
   그 사이 main 이 움직인다.
4. 배포는 항상 `git fetch` → `git rebase origin/main` → 전체 검사 → push.
   push 가 거부되면 그 사이 남이 올린 것이다 — 다시 rebase.
5. **rebase 충돌이 같은 기능 자리에서 나면 중복을 의심하라.** 그냥 풀지 말고
   `git show origin/main:파일` 로 그쪽이 무엇을 했는지 먼저 읽어라.

## 1. 이 저장소에서 지켜야 하는 규칙 (어기면 사고가 난다)

- **Bash 도구가 고장나 있다.** 환경변수만 쏟아낸다. **PowerShell 도구**를 쓸 것.
- **파일 수정은 Edit/Write 도구만.** PowerShell `Get-Content`/`Set-Content`/`Out-File`
  왕복은 한글 UTF-8 을 깨뜨린다(실제 사고 있었음).
- `pu-cards.html` 은 약 11,800줄, CRLF. **통째로 읽지 말 것** — Grep 으로 찾고 좁게 Read.
- **레코드를 통째로 `set` 하지 않는다.** 필요한 칸만 쓴다. 통째 쓰기가 남이 그 사이
  고친 이름을 되돌린 사고가 있었다(2026-08-11).
- **여러 줄이 바뀌면 한 번의 `update()` 로 묶는다.** 한 건씩 보내다 서버 폭주를 낸 적
  있다(2026-08-16 자동 폴더 배정).
- **`onclick` 에 들어가는 사용자 자료는 `esc()` «앞에서» 따옴표를 벗긴다** —
  `esc(String(x).replace(/'/g,"\\'"))`. `esc()` 가 `'` 를 `&#39;` 로 바꾸고 브라우저가
  실행 전에 되돌리므로, **`esc()` 뒤에 replace 하면 죽은 코드**다.
- **`state.tab` 에 `'co'` 를 절대 넣지 않는다.** `state.tab` 은 `'card'|'biz'` 두 값뿐이고
  75곳이 그렇게 믿는다. 기업 상세는 «갈래»가 아니라 «화면» — `state.view==='co'`.
  (대표 지시 2026-08-12, `tests/cards-co-info.test.js` 가 지킴)
- **검사에서 `slice(at, at + 숫자)` 같은 고정 길이 자르기를 쓰지 말 것.** 근처 코드가
  조금만 길어지면 엉뚱하게 터진다 — 이번에 두 번 터졌다. 이름 있는 표식으로 자른다
  (예: `$('pcSide').innerHTML = h; return;`).
- 작업 방식: 설계 → 계획 → 과제별 구현 → **뮤테이션 테스트** → 리뷰 → 배포.
  뮤테이션(일부러 되돌려 검사가 실패하는지 확인)을 빼면 «검사는 통과하는데 기능은
  고장난» 것이 그대로 나간다 — 실제로 이번에 그런 일이 있었다.

## 3. 아직 안 끝난 것 (다음 사람이 할 일)

### ★ 3-1. 「왜 느린가」 — 아직 결론 안 났다

**측정값(대표 기기, 기업 상세 화면 콘솔):**
```
명함 6,616장 · items 크기 4.92MB · 회사조립 64ms · 회사 4,138곳 · 페이지열기 548ms
thumb 2.48MB · companyAddr 0.12MB · id 0.10MB · email 0.09MB · …
```

- **계산은 문제가 아니다** — 회사 4,138곳 조립에 64ms.
- 느린 것은 열 때마다 `pucards/items` 를 **통째로 4.92MB** 받기 때문이다.

**⚠ 다만 「2.48MB 가 썸네일」은 과장일 수 있다.** 화면에 한 번 보인 명함은 그림을
메모리에 **되꽂아** 둔다(`renderList` → `getThumb` → `it.thumb = t`). 그래서 위 측정의
`thumb` 에는 **이미 밖으로 옮겨진 것도 섞여 있다.**

- 진짜 안 옮긴 것만 세는 판별식: `it.thumb` 이 있고 **`Store.thumbCache[id]` 에 없는 것**.
  (`countInlineThumbs` 가 이제 이 규칙을 쓴다)
- **다음 사람이 할 일**: 대표께 ⚙️ 환경설정 → 계정·AI 의 「옛 명함 그림 밖으로 빼기」를
  눌러 보시게 하고, **거기 나오는 숫자**를 확인할 것. 그것이 진짜 남은 양이다.
  - 숫자가 크면 → 옮기면 그만큼 빨라진다. 끝.
  - 숫자가 작으면 → **느린 원인이 다른 데 있다.** 4.92MB 중 무엇이 실제로 서버에서
    오는지 다시 재야 한다(메모리가 아니라 **네트워크**를 재야 한다 — 개발자도구
    Network 탭에서 firebase 응답 크기를 보거나, `items` 구독이 처음 받은 스냅샷
    크기를 재는 계측을 잠깐 넣는다).

**참고**: 푸른이알피는 같은 문제를 이미 고쳤다(부팅 5.7MB → 권한별로 갈라 받기).
`8b8ac3a` 커밋과 `docs/superpowers/specs/2026-08-16-부팅-받기-줄이기-design.md` 를
그대로 본으로 삼으면 된다. 계기도 있다 — 콘솔에서 `erpBytesIn()`.

### 3-2. 노란 폴더로 「거래처」 만들기 — 대표가 원했으나 안 함

대표 지시: 「거래처만」 184곳을 **노란 폴더**로 만들어 달라. **184곳 전부 새 폴더로
옮기기**로 결정하셨다(기존 폴더에 있던 것도 옮김 — 회사는 폴더 하나에만 든다).

- 폴더에 **색을 넣는 기능이 아직 없다.** 만들어야 한다.
- 나는 파이어베이스에 직접 못 쓴다 → **대표가 한 번 누르면 184곳이 담기는 단추**로
  만들기로 했다.
- 「거래처만」 필터는 **이미 지웠으므로**, 이제 「이알피 거래처인 회사」를 고르는 길이
  화면에 없다. 단추를 만들 때 `o.erp` 가 있는 회사를 골라 담으면 된다
  (`coList()` 의 각 회사에 `erp` 가 있다).

### 3-3. 검사 하나가 곧 터진다 (아직 안 고침)

`tests/cards-co-tag-hide.test.js` 는 이제 이름 있는 표식으로 자르도록 고쳤다.
**다른 고정 길이 자르기가 더 있는지** 한 번 훑어볼 것:
`Select-String -Path tests\*.test.js -Pattern "slice\(at, at \+ \d+\)"`

### 3-4. 리뷰가 남긴 작은 것들 (급하지 않음)

- `moveFolderOrder`(⋮ 메뉴의 위/아래) 는 아직 **레코드 통째 `set`** 을 두 번 한다 —
  1번 규칙 위반이 그대로 남아 있다. 드래그 정렬은 안전하게 고쳤지만 이 옛 길은 안 고쳤다.
- `renderCoPage` 가 `#pcCo` 를 통째로 다시 그리면서 **스크롤 위치를 안 되돌린다** —
  체크상자를 누르면 목록이 맨 위로 튈 수 있다. 호출부가 10곳이 넘어 따로 다뤄야 한다.
- 폰(터치)에서는 드래그 정렬이 안 된다(HTML5 드래그가 터치에서 안 먹는다).
  기업 상세 폴더·메인 탭·＃탭은 폰에서 순서를 바꿀 길이 아예 없다.
- `#tabs .tab` CSS 가 아무것도 안 잡는다(단추에 그 클래스가 없다). 탭이 셋이 되어
  320px 폰에서 좁아질 수 있다 — `#tabs button` 으로 고치면 된다.

## 4. 대표가 확인해 주셔야 할 것 (배포는 됐지만 눈으로 안 봄)

이번 작업은 **브라우저에서 사람이 직접 눌러 본 확인이 거의 없다.** 검사는 전부
통과하지만(3,954개), 로그인이 필요해 자동으로는 못 봤다. 다음 사람이 대표께
아래를 부탁드릴 것:

1. **직원 계정에서 명함을 폴더로 끌어 넣기가 되는가** — 매일 쓰는 길인데 같은
   자리에 새 동작(순서 바꾸기·회사 옮기기)을 두 개 더 얹었다. **가장 중요.**
2. 대표 계정에서 폴더를 끌어 순서가 바뀌고 새로고침해도 남는가.
3. 기업 상세에서 회사를 여러 곳 골랐을 때 아래 도구줄이 보이는가.
4. ⚙️ 환경설정 → 계정·AI 의 썸네일 단추를 눌러 나오는 **숫자**(3-1 참고).
5. 폰에서 기업 상세를 열어 폴더·서류 탭이 실제로 보이는가.

## 6. 버린 작업 — 폰 아래 고정 바 + 메일 화면 (2026-08-17)

**무엇을 하려 했나**: 대표 지시로 폰에서 메일이 메인화면에서 안 들어가는 것을 고치려,
목업 세 안(A 상단바 ✉️ / B 탭 네 개 / C 아래 고정 바)을 보여드리고 **C안**을 고르셨다.
1단계로 아래 바 + 메일 홈 + 폰용 간단 쓰기를 만들었다(커밋 5개, 검사 4,033개 통과,
리뷰 두 번).

**왜 버렸나**: 배포 직전 rebase 충돌로 확인해 보니, 다른 세션이 이미
`483a1ab 메일함을 폰에서도 쓸 수 있게` 를 배포해 두었고 **그쪽이 더 낫다.**

| | main (남긴 것) | 내 것 (버린 것) |
|---|---|---|
| 폰/PC 가르기 | `renderMailPage()` **한 곳**에서 가른다 | `renderMailAny()` 를 새로 만들고 호출부 6곳을 바꿈 |
| 폰 쓰기 | **PC 쓰기 화면을 그대로** — 참조·숨은참조·예약시각 다 됨 | 간단 쓰기 — 그 칸들을 **담지 못함** |
| 메일 진입 | ☰ 맨 위 (2번 누름) | 아래 고정 바 (1번 누름) |

특히 내 「간단 쓰기」가 참조·예약시각을 담지 못해 **「고쳐 쓰기」가 그 값들을 잃는
자료 유실**을 만들었고, 그것을 막으려 「PC에서 고쳐 주세요」로 거절하는 코드까지
넣어야 했다. main 방식은 그 문제가 **애초에 생기지 않는다.**

**아래 고정 바는 대표 결정으로 하지 않는다** — ☰ 맨 위로 2번 누르면 되니 충분하고,
위 탭 줄을 없애는 것은 화면 구조를 바꾸는 큰 변경이라 새 버그 위험이 있다.
**나중에 폰에서 실제로 불편하다고 하시면 그때 다시 꺼내면 된다.**

> **다시 꺼낸다면 설계부터 새로 해야 한다.** 위 표에 「무엇을 왜 버렸나」가 남아 있으니
> 그것이 유일한 재료다.
>
> ⚠ 남길 교훈 하나 더 — **「브랜치에 남아 있다」고 적을 때는 그 가지를 밀어 두어야 한다.**
> 안 밀면 세션이 끝나는 순간 사라지고, 이 문서만 「있다」고 말하게 된다.
> 실제로 찾아보기 전까지 한 달 가까이 있는 줄 알았다.

**남길 교훈**: 「폰에서 X 를 쓰게 해달라」류의 일은 **만들기 전에** 다른 세션이 이미
했는지 반드시 확인해야 한다. 이번엔 설계·구현·리뷰 두 번을 다 한 뒤에 알았다.
