# 사진첩(pu-photos.html) — 창고(Storage) 이전 콘솔 작업

2026-08-13 작성 · 비용 조사(8/1~8/11 실시간DB 내려받기 ₩28,833) 뒤 대표 결정.
관련 코드: `js/pu-photo-store.js` (창고 저장·읽기·지우기·이사 도구, 검사 131개 통과)

> **지금 코드를 배포해도 아무것도 안 바뀝니다.** 저장 방식은 `js/pu-photo-store.js`
> 맨 위 `var mode = 'rtdb';` 한 줄이 정합니다 — 지금은 그대로 `'rtdb'` 입니다.
> 아래 콘솔 작업을 다 마친 뒤에야, 이 한 줄을 `'storage'` 로 바꿔야 실제로 창고를
> 쓰기 시작합니다. 그 전까지는 사진첩이 지금과 똑같이 움직입니다.

---

## ⚠ 먼저 — 오늘 작성된 다른 문서와 헷갈리지 마십시오

오늘(2026-08-13) 급여데이터함 작업을 위해 `docs/firebase-storage-급여데이터함-포함(붙여넣기용).txt` 도
같이 만들어졌습니다. 그 파일 12~16번째 줄에 `puphotos/u/{uid}` 라는 칸이 있는데,
**이번 사진첩 창고 이전과는 다른 것입니다** — 이름도 다르고(`puphotos` vs 실제 코드의
`pu_photos`), 대상 버킷도 다릅니다(기본 창고 vs 이번에 새로 만드는 서울 버킷).
그 문서가 작성될 때는 오늘 사진첩을 **새 버킷으로 따로 뺀다**는 이번 결정을 몰랐던
것으로 보입니다. **그 문서의 `puphotos` 칸은 쓰지 마시고, 이 문서의 규칙만 쓰십시오.**
(두 작업 담당자가 같은 날 각자 진행해서 생긴 어긋남입니다 — 급여데이터함 쪽에도
한 번 확인을 부탁해 주시면 좋겠습니다.)

## 1. 새 창고(버킷) 만들기 — 서울 리전

명함첩(`pu-cards.html`)이 쓰는 `pureun-erp-photos` 와 같은 이유로, 사진첩도 **따로**
새 버킷을 만듭니다. 명함첩과 **같은 버킷을 안 쓰는 이유**: 명함첩은 고객사 임직원
정보, 사진첩은 우리 근로자 정보 — 대상이 다르면 접근 규칙이 갈리는데, 한 버킷에
같이 있으면 그 구분이 섞입니다.

1. 콘솔 → `Storage` → 버킷 추가(왼쪽 위, 버킷 이름 옆의 `+` 또는 「버킷 추가」)
2. 버킷 이름: **`pureun-erp-hrphotos`** (코드에 이미 이 이름으로 넣어 두었습니다 —
   다른 이름으로 만드시면 `pu-photos.html`·`gov-consulting.html` 두 파일의
   `storageBucket` 값을 그 이름으로 바꿔야 합니다)
3. 리전: **`asia-northeast3` (서울)** — 명함첩 버킷과 같은 리전
4. 기본 설정(Standard 저장 등급)으로 만들면 됩니다

## 2. 창고 규칙 붙여넣기

1. `docs/firebase-storage-사진첩-새창고(붙여넣기용).txt` 파일을 엽니다
2. **전체를 복사**합니다 (`rules_version` 부터 마지막 `}` 까지)
3. 콘솔 → `Storage` → 방금 만든 `pureun-erp-hrphotos` 버킷을 선택 → `Rules` 탭
   (⚠ 다른 버킷의 Rules 탭에 붙여넣지 않도록, 위쪽 버킷 이름을 한 번 더 확인해 주십시오)
4. **전체를 지우고 붙여넣습니다** (이 버킷은 새로 만든 것이라 지금은 빈 규칙입니다 —
   기존 규칙을 지울 걱정은 없습니다)
5. `게시`

이 규칙이 하는 일: 사람은 **자기 자리(`pu_photos/u/{uid}`)만** 읽고 쓸 수 있습니다.
사진이 아닌 파일이나 10MB 넘는 파일은 거절합니다. 그 밖의 모든 자리는 막혀 있습니다.

**⚠ 한 가지 한계 — 알아 두실 것.** 창고 규칙은 실시간DB(`uid_roles`)를 읽을 방법이
없어서, "이 사람이 총괄 관리자인가"를 창고 쪽에서 판정할 수 없습니다. 그래서
**관리자가 자기 것이 아닌 다른 직원의 사진을 창고로 옮기는 것(이사 도구를 그 직원
몫에 돌릴 때)은 이 규칙만으로는 안 됩니다** — 시도하면 그 직원 몫만 실패(failed)로
잡히고, 사진은 실시간DB에 그대로 남습니다(잃지 않습니다). 관리자가 **자기 자신의**
사진을 옮기는 것은 됩니다. 여러 직원 것을 관리자가 한꺼번에 옮기려면 서버
(Cloud Functions, Admin SDK)로 옮기는 도구를 별도로 만들어야 하는데, 이번 작업
범위에는 없습니다 — 필요해지면 그때 말씀해 주십시오.

## 3. 연결 확인(점검)

`js/pu-photo-store.js` 에는 `probe(stamp)` 라는 점검 함수가 이미 있습니다(작은 글자
하나를 올리고·주소를 받고·지우는 세 걸음을 실제로 해 봅니다). 브라우저 개발자 도구
콘솔에서 사진첩 화면을 연 채로 아래처럼 불러 확인할 수 있습니다.

```js
PuPhotoStore.probe(String(Date.now())).then(console.log)
```

`{ ok: true, step: 'done', ... }` 이 나오면 올리기·읽기·지우기가 다 됩니다.
`ok: false` 면 `message` 에 적힌 이유(대개 규칙 문제)를 보고 1~2 단계를 다시 확인합니다.

## 4. 실제로 켜기 — 이때는 되돌리기 어렵습니다(순서를 지켜야 함)

점검이 통과했으면, `js/pu-photo-store.js` 맨 위:

```js
var mode = 'rtdb';
```

를

```js
var mode = 'storage';
```

로 바꾸고 커밋·배포합니다. **이 시점부터 새로 찍는 사진은 창고에 담깁니다** —
실시간DB 내려받기 비용이 그때부터 줄어듭니다.

이미 실시간DB에 있는 옛 사진들은 자동으로 옮겨지지 않습니다. 총괄 관리자 계정으로
개발자 도구 콘솔에서 아래를 불러 옮길 수 있습니다(올리고 → 되읽어 확인하고 →
그제야 실시간DB에서 지우는 순서를 지킵니다 — 검사 131개 중 여럿이 이 순서를
못 박아 둡니다).

```js
PuPhotoStore.migrateToStorage(function (progress) {
  console.log('진행:', progress);   // { moved, skipped, failed }
}).then(function (result) {
  console.log('끝:', result);
});
```

**총괄 관리자 자기 자신의 사진만 확실히 옮겨집니다**(위 2번의 한계 참고). 여러
직원 사진을 한꺼번에 옮기고 싶으시면 먼저 알려 주십시오.

## 5. 다 하셨으면

알려 주십시오 — `mode` 를 바꾸고 배포하는 것까지는 코드 쪽에서 마무리해 드릴 수
있습니다. 그 전에 1~3 단계(버킷 만들기·규칙 붙여넣기·점검)는 콘솔 작업이라
대표님이 직접 하셔야 합니다.

---

## 붙임 — 규칙을 저장소 파일로 배포하지 않는 이유

이 저장소의 `docs/firebase-storage-*.txt` 파일들은 **참고용 사본**입니다. **진짜는
콘솔입니다.** 저장소 파일로 배포했다가 사진첩·성과확인이 막힌 일이 있었습니다 —
저장소 사본이 콘솔보다 낡아서, 배포가 최신 규칙을 덮어버렸기 때문입니다. 그래서
**콘솔에 직접 붙여넣는 방식만** 씁니다.
