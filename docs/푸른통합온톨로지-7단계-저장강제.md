# 푸른통합 온톨로지 7단계 — 바꾸면서도 깨지지 않는 저장 강제

## 결론

기존 원본은 계속 각 프로그램의 정본이다. 모든 자료를 `ontology/` 아래로 옮기지 않는다.
대신 모든 화면과 Cloud Functions 쓰기 앞에 같은 관문을 두고, 관계망 사본은 서버에서도
모양을 검사한다. 2026-09-06 현재 운영 앱은 **관찰**, 새 앱은 **강제**가 기본이다.

관찰을 먼저 두는 까닭은 옛 자료에 `entityType`·`revision` 등이 없는 상태에서 서버를
먼저 닫으면 정상 업무까지 한꺼번에 멈추기 때문이다. 관찰은 영구 유예가 아니다.
프로그램별 이관이 끝나면 `LEGACY_OBSERVE_PROGRAMS`에서 빼는 순간 강제로 바뀐다.

## 1~8단계 적용

| 단계 | 적용한 장치 | 현재 상태 |
|---|---|---|
| 1. 저장경로 전수조사 | `scripts/ontology-write-inventory.js`가 등록 프로그램·소유뿌리·관문·클라이언트/서버 쓰기 흔적을 매번 계산 | 완료 |
| 2. 자료별 저장계약 | `id`, `entityType`, `schemaVersion`, `contractVersion`, 생성/수정 시각, `revision`, 관계 ID·원본 ID 짝 검사 | 공통 계약 완료 |
| 3. 중앙 저장 관문 | `js/pu-ontology-write.js`가 Firebase `set/update/remove/push/transaction` 앞을 감싸고, 명시적 `createGateway`는 수정차수 트랜잭션 저장 제공 | 15개 앱 + Firebase 딸린 화면 3개 탑재 |
| 4. 기존자료 진단·보정 | `planMigration`이 원본을 바꾸지 않고 자동 보완 가능/사람 확인 필요를 분리 | 도구 완료·실자료 이관은 앱별 진행 |
| 5. 직접 저장 우회 차단 | 모든 등록 프로그램과 Firebase 딸린 화면이 초기화 전에 관문을 싣는지 배포검사. 새 앱은 `writeContracts` 없으면 실패 | 완료 |
| 6. 서버 이중 강제 | 관계망 개체·관계 필수 모양, 관리자 쓰기, 판 내부 불변, 알 수 없는 필드 거부 | 관계망 완료·원본뿌리는 이관 후 순차 적용 |
| 7. 삭제·동시접속 보호 | `tombstone`과 `revision` 기반 트랜잭션 저장. 관리자 SDK는 별도 서버 관문으로 관찰 | 공용 장치 완료·앱별 교체 진행 |
| 8. 단계적 적용 | 기존 앱만 명시적 관찰 유예, 새 프로그램은 `data-mode="observe"`를 써도 기본 강제 | 안전한 전환 시작 |

## 전수조사 결과

- 등록 프로그램: 15개
- 공용 클라이언트 관문 탑재: 15개
- Firebase를 여는 딸린 화면 관문 탑재: 3개(취업규칙 작성기·전자위임장 제출·이음센터 보기)
- 기존 프로그램 관찰 모드: 15개
- 새 프로그램 기본값: 강제 모드
- Cloud Functions: `getDatabase()` 공용 관찰 관문 적용

2026-09-08 통합검사에서는 실제 Firebase Admin SDK 객체 래핑, 관계망 규칙의 살아 있는
콘솔 대비 삭제 0개, Firebase 규칙 문법 dry-run을 통과한 뒤 관계망 규칙을 배포했다.
기존 원본 자료 이관은 별도 단계이며, 관찰 상태를 곧바로 “삭제·충돌이 완전히 차단됨”으로 해석하지 않는다.

쓰기 흔적 수는 `node scripts/ontology-write-inventory.js --markdown`로 다시 계산한다.
이 숫자에는 배열의 `push` 같은 동명이 섞일 수 있으므로 고정된 합격 숫자로 쓰지 않는다.

## 바뀌지 않는 최소 계약

```js
{
  id: 'case-123',
  entityType: 'Case',
  schemaVersion: 3,
  contractVersion: 1,
  createdAt: 1788680000000,
  updatedAt: 1788683600000,
  createdBy: 'P-001',
  updatedBy: 'P-002',
  revision: 12,
  companyId: 'company-77'
}
```

업무별 선택 칸은 자유롭게 늘릴 수 있다. 업체명·사람 이름은 표시값일 뿐 관계 열쇠가
아니다. 원본 관계가 있으면 `sourceKind`와 `sourceId`를 반드시 함께 둔다.

## 구조를 바꾸는 순서

1. 공통 사전과 새 계약 판을 먼저 추가한다.
2. 읽기는 현재 판과 바로 전 판을 함께 허용한다.
3. 새 코드는 현재 판으로만 쓴다.
4. `planMigration`으로 막힌 자료를 가른다.
5. 백업 후 명시적 이관을 실행한다.
6. 건수·관계·표본 화면을 대조한다.
7. 해당 프로그램을 관찰 유예 목록에서 뺀다.
8. 마지막에 원본 Firebase 규칙의 필수 모양을 닫는다.

## 삭제와 충돌

물리 삭제는 다음 레코드 저장으로 바꾼다.

```js
{ _deleted:true, deletedAt:1788683600000, deletedBy:'P-002', revision:13 }
```

수정자는 화면을 열었을 때의 `revision`을 `expectedRevision`으로 보낸다. 서버의 최신 값이
다르면 트랜잭션을 중단하고 최신 자료를 다시 열게 한다. 마지막 저장자가 조용히 이기는
방식은 강제 전환 대상 프로그램에서 허용하지 않는다.

## 다음 전환 단위

한 번에 15개를 닫지 않는다. `푸른ERP의 companies → contracts → cases`처럼 자료 한 종류씩
`관찰 위반 0 → 이관 계획 막힘 0 → 백업 → 트랜잭션 저장 → 서버 규칙`을 모두 통과한 뒤
강제로 올린다. 화면 개발은 그동안 계속할 수 있다.
