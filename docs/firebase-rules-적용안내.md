## 1순위 — 익명 접근 차단 ✅ 2026-07-30 게시 완료·검증 완료

**파일**: `docs/firebase-rules-1순위-익명차단.json`

이메일(비밀번호)로 로그인한 사람만 접근하도록 45곳을 바꿨습니다.
`data/$other` 등 기존 규칙에서 이미 쓰던 검증된 방식과 동일합니다.

### 익명을 그대로 둔 곳 (막으면 기능이 깨짐)

| 노드 | 이유 |
|---|---|
| `esign` | 외부 근로자가 링크로 접속해 서명 (`sign.html`) |
| `ieum_public` | 외부 공개 명단 보기 (`ieum-view.html`) — 쓰기는 이미 로그인 필요 |
| `appBuild` | 버전 확인용, 데이터 없음 |

### 적용 후 달라지는 점

- **컨설팅 일정**을 포털 로그인 없이 주소로 바로 열면 데이터가 안 보입니다.
  → 포털에서 로그인 후 들어가면 정상입니다. (원래 이래야 맞습니다)
- 그 외 직원이 정상 로그인해 쓰는 흐름은 변화 없습니다.

### 적용 방법

1. Firebase 콘솔 → Realtime Database → **규칙** 탭
2. **현재 내용을 전부 복사해 따로 저장** (되돌릴 때 필요)
3. `firebase-rules-1순위-익명차단.json` 내용을 전부 붙여넣기 → **게시**
4. 확인: 포털 로그인 → 컨설팅 일정·기금관리·업무관리가 정상인지
5. 이상하면 2에서 저장해둔 내용을 다시 붙여넣어 즉시 원복

## 2순위 — 권한 자가 부여 차단 ✅ 2026-07-30 게시 완료·검증 완료

**문제**: 지금은 `uid_roles/{본인}`을 본인이 쓸 수 있습니다.
직원이 자기 권한에 `fin: true`를 써넣으면 급여·재무 전체가 열립니다.

**왜 바로 못 막나**: 앱이 로그인할 때 이 값을 스스로 기록하는 구조라,
그냥 막으면 **아무도 권한을 못 받아 로그인 후 화면이 비게 됩니다.**

> 실제로는 아래 사전등록 없이 진행했습니다. 콘솔 확인 결과 uid_roles 에 10명이 이미 등록돼 있어,in/isAdmin/isSubAdmin 세 필드만 `관리자만 올릴 수 있음` 으로 잠그는 방식(irebase-rules-2순위-권한잠금.json)을 썼습니다. 등록 10명 전원·미등록 3명 모두 로그인 통과를 시뮬레이션으로 확인한 뒤 게시했고, 게시 후 자가부여 시도가 401 로 차단되는 것까지 확인했습니다.

**운영 변화**: 직원 권한 변경은 이제 Firebase 콘솔에서 직접 해야 합니다(ERP 화면 변경은 규칙 판정에 반영되지 않음).

원래 계획했던 방식(참고용):

1. 대표님이 직원 13명의 권한을 콘솔에서 한 번 등록
   (`uid_roles/{uid}` = `{isAdmin, isSubAdmin, fin, hr, ...}`)
   - 각자의 uid는 Firebase 콘솔 → Authentication 에서 확인
2. 전원이 정상 로그인되는지 확인
3. 그 뒤에 규칙을 `관리자만 쓰기`로 잠금
4. 앱의 자가 기록은 실패해도 무시되도록 이미 `catch` 처리돼 있어 화면에 영향 없음

> 1~2를 건너뛰고 3만 하면 전 직원이 잠깁니다. 반드시 순서를 지켜야 합니다.

## 3순위 — 급여 확정 잠금 정상화 ✅ 2026-07-30 수정 완료 (게시는 급여 아웃소싱 운영 시작 전)

**파일**: `app/firebase.rules.json` (급여 아웃소싱용 초안)

확정(잠금)된 급여월은 관리자만 고치도록 `payroll_monthly/$ym`에 규칙이 있으나,
**Firebase는 상위 규칙이 하위를 덮어씁니다.** 상위 `clients/$site/.write`에서 이미
담당자 쓰기를 허용해 **잠금이 전혀 작동하지 않습니다.**

**고친 방법**: `clients/$site/.write` 를 관리자 전용으로 바꾸고, 담당자 쓰기를 항목별로 분리했습니다.`payroll_monthly/$ym` 은 `잠기지 않은 달만` 조건이 붙고, 나머지 섹션은 배정자가 자유롭게 씁니다.

시뮬레이션(7상황x5역할) 결과 잠긴 달의 수정·하위 필드 단독 수정·삭제가 모두 담당자에게 차단되고 관리자만 허용됩니다. 마감(locked=true)은 담당자도 할 수 있어 D4 마감 흐름은 그대로입니다.

⚠️ 아직 콘솔에 게시하지 않았습니다. 급여 아웃소싱 실운영을 시작할 때 게시하세요.

## 4순위 — 포털 개인 데이터·건의함·백업 권한 세분화 ✅ 2026-07-30 게시 완료·검증 완료

**파일**: `docs/firebase-rules-3순위-포털권한.json`

2026-07-30 추가 점검에서 다음 문제를 확인해 개정안을 준비했습니다.

- `data/$other` 때문에 건의 원문·상태·답변을 모든 로그인 사용자가 수정할 수 있음
- 포털 개인 설정과 해결 알림이 이메일 문자열 경로에 저장돼 본인 소유권 규칙을 만들기 어려움
- 서버 백업과 백업 인덱스를 일반 로그인 사용자도 쓸 수 있음
- `uid_roles`에서 `hr`, `isFullViewer`, `role`, `sid`, `status`가 충분히 잠기지 않음

개정안의 주요 변경:

1. 개인 설정을 `data/portal_prefs_uid/{uid}`로 전환하고 본인만 접근
2. 해결 알림을 `data/sg_resolved_uid/{uid}`로 전환
3. 건의 신규 등록은 작성자 UID가 일치할 때만 허용하고, 상태·답변 수정은 관리자만 허용
4. 서버 일간·수시 백업은 관리자·위임관리인만 읽기·쓰기
5. 나머지 권한성 `uid_roles` 필드의 자가부여 차단

새 `enter.html`을 먼저 배포해 기존 이메일 경로의 설정·알림을 UID 경로로 자동
이전하도록 한 뒤 게시했습니다. 게시 전 현재 운영 규칙을
`C:\tmp\pureun-erp-rules-backup-2026-07-30.json`에 백업했고, Firebase CLI의
서버 측 문법 검사를 통과했습니다.

게시 후 운영 규칙을 다시 내려받아 이 파일과 정확히 일치하는지 확인했습니다.
익명 접근 검사 결과 건의함·UID 개인 설정·백업 인덱스는 모두 401로 차단됐고,
공개 버전 확인용 `appBuild`만 200으로 허용됐습니다.
