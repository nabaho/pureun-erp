# 푸른통합 온톨로지 6단계 — 입력·저장 검증

## 순서와 현재 범위

1. **업체관리 → 계약 입력의 업체 연결 검증**: 이번 구현 범위.
2. 담당자 사번·계약·사건 참조 검증: 다음 적용 대상.
3. 자동 수집·일괄 가져오기·다른 프로그램 저장 경로 검증: 미적용.
4. 신규 프로그램 배포 계약 강화: 공통 사전·등록 검사에 입력 검증을 추가 예정.
5. 여러 담당자·자동 수집이 겹치는 동시접속 통합 시험: 별도 단계.

이번 구현은 ERP 계약 입력 모달과 계약관리의 건별 저장 경로를 대상으로 한다.
모든 프로그램의 서버 쓰기를 차단하는 전역 가드나 DB 외래키 제약은 아니다.
기존 계약 이관·자동 생성·일괄 가져오기 경로 전체가 검증되었다고 간주하지 않는다.

## 1번의 변경

- 회사명 검색은 후보만 제공한다. 계약 저장에서 이름으로 업체 ID를 자동 선택하지 않는다.
- 실제 업체 ID 존재 여부, 삭제·중복, 최상위/중첩 ID 충돌, 사업자번호 불일치를 검사한다.
- 업체 선택 시 회사명·사업자번호를 반영하고 ID를 두 위치에 일치시킨다.
- 회사명·사업자번호를 직접 변경하면 기존 연결을 풀고 다시 검증한다.
- 과거 계약·사건의 자체 ID를 업체 ID로 대입하지 않는다.
- 기존 업체정보 동기화는 선택된 ID 한 건에만 적용한다. 같은 이름의 다른 업체는 그대로 둔다.
- 계약 저장이 취소·실패하면 업체 동기화·임시작성본 삭제·사진 공유를 수행하지 않는다.
- 확인창이 열린 동안 업체 상태가 바뀔 수 있으므로 건별 저장 직전과 업체 동기화 직전에 다시 검사한다.

## 연결 상태

| 값 | 의미 | 업체 마스터 동기화 |
|---|---|---|
| `linked` | 명시적 업체 ID를 목록에서 검증함 | 그 ID 한 건만 |
| `pending` | 사용자가 신규·미확정 업체로 연결 보류를 선택함 | 하지 않음 |
| `not_required` | 업체 연결이 없는 근로자 단독 의뢰 | 하지 않음 |

연결 보류는 계약 자체를 폐기하지 않고 업무를 이어가기 위한 선택이다.
보류된 업체 관계는 확정 관계망에 들어가지 않으며, 이후 업체 등록·선택 및 재진단이 필요하다.
기존 자료는 일괄 수정하지 않는다. 기존의 잘못된 연결은 그 계약을 편집해 저장할 때 확인한다.

## 검증과 한계

동명이 업체, 삭제·없는·중복 ID, 내부 ID 충돌, 사업자번호 불일치,
근로자 의뢰, 연결 보류, 계약 저장 취소·예외, 과거 기록 ID 오대입을 실행 테스트한다.
전체 HTML 스크립트 구문검사와 기존 동시편집·덮어쓰기 보호 검사를 함께 유지한다.

이 검증은 현재 클라이언트가 읽은 업체 목록을 기준으로 한다.
Firebase 보안규칙이나 트랜잭션 경계를 변경하지 않았으며,
서버에서 동시 삭제·변경되는 모든 경쟁 상황을 원자적으로 차단한다는 보장은 아니다.
계약 저장의 성공 반환도 기존 로컬 저장·전송 대기열 수락 규칙을 따른다.
