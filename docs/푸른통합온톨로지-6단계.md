# 푸른통합 온톨로지 6단계 — 입력·저장 검증

## 순서와 현재 범위

1. **업체관리 → 계약 입력의 업체 연결 검증**: 구현 완료.
2. **담당자 사번·계약·사건 참조 검증**: 계약·사건 입력 및 건별 전체 저장에 적용.
3. 자동 수집·일괄 가져오기·다른 프로그램 저장 경로 검증: **3-A 사건 일괄 가져오기·계약 자동 이관, 3-B 은행·카드 문자 및 재무 파일 적용**, OCR·자료메일은 다음 범위.
4. 신규 프로그램 배포 계약 강화: **4-A 화면·저장 자리 등록 계약 적용**, 입력 검증 강제는 다음 범위.
5. 여러 담당자·자동 수집이 겹치는 동시접속 통합 시험: 별도 단계.

이번 구현은 ERP 계약·사건 입력 모달, 각 관리 화면의 건별 전체 저장,
사건 일괄 저장, 계약에서 업체·사건·컨설팅·기금·기타사업으로 이관하는 경로와
은행·카드 문자 및 재무 거래파일 수집 경로를 대상으로 한다.
모든 프로그램의 서버 쓰기를 차단하는 전역 가드나 DB 외래키 제약은 아니다.
기존 계약 이관·자동 생성·일괄 가져오기 경로 전체가 검증되었다고 간주하지 않는다.

## 1번의 변경

- 직접 입력·기업정보함·OCR로 들어온 정확한 10자리 사업자번호가 업체 명부의 한 곳과만 일치하면 계약 입력 중 업체 ID를 자동 연결한다. 입력한 회사명 표기는 덮어쓰지 않는다.
- 자동 연결이 끝나면 긴 검증 상자는 짧은 `업체 자동 확인` 표시로 접힌다. `변경`을 누르면 기존 검색·선택 화면을 다시 열 수 있다.
- 회사명 검색은 후보만 제공한다. 이름만 같거나 같은 사업자번호가 중복된 경우에는 업체 ID를 자동 선택하지 않고 사람이 확인한다.
- 실제 업체 ID 존재 여부, 삭제·중복, 최상위/중첩 ID 충돌, 사업자번호 불일치를 검사한다.
- 업체 선택 시 회사명·사업자번호를 반영하고 ID를 두 위치에 일치시킨다.
- 회사명·사업자번호를 직접 변경하면 기존 연결을 풀고 다시 검증한다.
- 과거 계약·사건의 자체 ID를 업체 ID로 대입하지 않는다.
- 기존 업체정보 동기화는 선택된 ID 한 건에만 적용한다. 같은 이름의 다른 업체는 그대로 둔다.
- 계약 저장이 취소·실패하면 업체 동기화·임시작성본 삭제·사진 공유를 수행하지 않는다.
- 확인창이 열린 동안 업체 상태가 바뀔 수 있으므로 건별 저장 직전과 업체 동기화 직전에 다시 검사한다.

## 연결 상태

| 값 | 의미 | 업체 마스터 동기화 |
|---|---|---|
| `linked` | 명시적 업체 ID를 목록에서 검증함 | 그 ID 한 건만 |
| `pending` | 사용자가 신규·미확정 업체로 연결 보류를 선택함 | 하지 않음 |
| `not_required` | 업체 연결이 없는 근로자 단독 의뢰 | 하지 않음 |

연결 보류는 계약 자체를 폐기하지 않고 업무를 이어가기 위한 선택이다.
보류된 업체 관계는 확정 관계망에 들어가지 않으며, 이후 업체 등록·선택 및 재진단이 필요하다.
기존 자료는 일괄 수정하지 않는다. 기존의 잘못된 연결은 그 계약을 편집해 저장할 때 확인한다.

## 검증과 한계

### 2번의 변경 — 담당자·원본 업무 참조

- 현재 `user_dir`와 `user_accounts`의 실제 사번으로 검증한다. 이름이나 초기 seed를 SID로 변환하지 않는다.
- 계약 담당자 드롭다운의 기존 이름 기반 선택값을 SID로 고쳤다. 계약·사건 선택 목록은 이름과 사번을 함께 표시해 동명이인을 구분한다. 명부에 없는 기존 값은 별도 옵션으로 유지한다.
- 신규 주담당·부담당은 사번 존재·중복·퇴직·삭제·잠금·배제·휴직 여부를 확인한다. 같은 사번의 계정 상태가 공개 명부보다 우선한다.
- 변경하지 않은 과거 담당자와 끊어진 원본 참조는 경고로 남겨 일반 내용 수정을 허용한다. 이는 새 연결의 유효성 승인이 아니며 원본을 자동 정리하지 않는다.
- 계약 담당자 탭과 사건 편집 화면에 원본 계약·사건 검색/선택을 추가했다. 선택할 때만 draft에 실제 ID를 넣으며, 명시적 연결 해제도 저장 전까지 원본에 반영하지 않는다.
- `sourceKind`·`sourceId`, `sourceContractId`는 원본 존재·삭제·중복·자기참조·상충 여부를 확인한다. `sourceContractNo` 단독 기록은 기존 값을 경고로 보존하고 신규 번호 단독 연결은 막는다.
- 계약·사건의 명시적이며 유일한 원본 ID만 `derivedFrom` 관계로 진단한다. 번호로 ID를 추정하지 않으며 끊어진/모순된 참조는 검증센터에서 확인한다.
- 입력 시점뿐 아니라 `persistOne`·`caseUpsert` 저장 직전에도 검증한다. 검증 모듈이 로드되지 않으면 해당 저장을 막는다.

`tests/ontology-work-references.test.js`는 순수 검증 함수, 실제 입력 패널과 최종 저장 함수 실행을 검사한다.
실데이터를 삭제·변경하는 테스트는 하지 않는다.

### 3-A의 변경 — 사건 일괄 입력·계약 자동 이관

- 사건 가져오기는 이름을 SID로 추정하지 않는다. 미리보기에서 주담당·부담당을 이름+사번 목록으로 직접 선택하며 원본 행 배열은 직접 변경하지 않는다.
- 사건유형·상태·의뢰인·번호를 확인하고, 빈 사건번호는 같은 배치 안에서 겹치지 않게 생성한다. 기존 번호 또는 입력 목록 내 중복 번호는 보류한다.
- `validateWorkBatch`가 전 행의 ID, 담당자, 원본 참조를 검사한다. 신규 입력의 기존 ID 덮기·삭제 ID 재생성·중복 ID를 차단한다. 한 행이라도 실패하면 해당 배치를 저장하지 않는다.
- 저장 함수가 실패하면 미리보기를 닫거나 성공 알림을 띄우지 않는다. 원본 파일은 읽기만 하고 삭제하지 않는다. 사건 번호 일괄 변경도 검증과 저장 성공 후에만 완료를 알린다.
- 계약 이관 전 원본 계약 ID와 변경 시각, 신규 담당자 배정, 업체 연결을 다시 확인한다. 미확정 업체와 같은 이름/사업자번호 후보가 이미 있으면 자동 선택하거나 새로 만들지 않고 명시적 선택을 요청한다.
- 업체·사건·컨설팅·기금·기타사업 생성에 `sourceContractId`, `sourceKind:'contract'`, `sourceId`를 남긴다. 사건·프로젝트의 업체 ID도 검증된 계약의 ID만 승계한다.
- 새 레코드의 개체 종류와 생성·갱신 시각을 기록한다. 명시적 원본 ID 관계는 `derivedFrom`으로 진단하며 번호만으로 색인을 만들지 않는다.
- 이관 실패 정리에서 기존 업체에 이어 붙인 `linked` 결과는 삭제하지 않는다. 이미 반영한 기존 업체의 빈칸 보완/메모는 보존되므로 사람이 확인한다. 여러 저장을 하나의 서버 트랜잭션으로 바꾼 것은 아니다.
- 재이관/완료 판단은 명시적 원본 ID를 우선한다. 번호만 남은 과거 연결·상충 ID·일부 업무만 존재하는 이관 흔적은 자동 완료 처리하지 않고 검토를 요청한다.

`tests/ontology-intake.test.js`는 실제 미리보기 선택·일괄 저장·계약 이관·재이관 함수를 가짜 저장소에서 실행한다.
정상/불량 행 혼합, 저장 실패 후 재시도, 동명이인, 중복 번호, 원본 변경,
기존 업체 보존, 신규 생성분만 정리, 부분 이관 완료 방지를 검사한다.

### 3-B의 변경 — 은행·카드 문자 및 재무 거래파일

- 문자 수집 원본은 `originSystem:'hana-sms'`와 64자리 `originId`를 거래 행에 보존한다. 카드 취소(`cancel`)도 초안·묶음·중복 판별 과정에서 유지한다.
- `validateHanaSourceBatch`가 원본 ID, 중복 ID, 실제 달력 일시, 안전한 양의 정수 금액, 입출금 종류, 은행·카드 출처, 취소값을 전 행 검사한다. 한 행이라도 실패하면 배치 전체를 저장·수신완료하지 않아 원본 대기함에 남긴다.
- 클라이언트 저장 함수의 성공만 믿지 않는다. 인증된 Firebase REST 조회로 묶음의 실제 서버 사본과 원본 행이 모두 일치하는지 확인한 뒤에만 문자 서비스에 `ack`를 보낸다. 인증·네트워크·서버 확인 실패 시 원본 문자는 다음 가져오기에서 재시도된다.
- 금액 일치는 후보 표시만 할 수 있으며 사건·계약·컨설팅 등 업무 ID를 자동 선택하지 않는다. 기존에 사람이 선택한 연결만 행 열쇠가 바뀔 때 이어간다.
- 거래파일 묶음 저장 실패를 성공으로 처리하지 않는다. 다른 재무 가져오기 화면에서도 금액 단독 ID 대입을 제거했다.
- 테스트는 합성 데이터와 가짜 서버만 사용한다. 실제 문자 대기함, Firebase 운영 데이터, 보안규칙을 변경하지 않는다.

`tests/ontology-hana-source.test.js`는 잘못된 원본 혼합 배치의 전부 보류,
행별 서버 사본 대조, 취소·출처 보존, 저장 확인 전 수신완료 금지와 금액 단독 연결 금지를 검사한다.

**다음 범위(미적용):** OCR·자료메일 자동 수집, 아직 점검하지 않은 다른 프로그램의 가져오기,
역이관·부분 패치, 기존 이름→SID 부팅 정규화, 사건의 기존 업체정보 자동 보완/업체 연결.
전체 프로그램의 저장 경로 검증 및 모든 업무 간 순환 참조 검사는 별도 확장 대상이다.

배치 전 행 검증은 서버의 원자적 커밋 보장이 아니다. 오프라인 전송 대기열, 서버 승인 실패,
다른 기기의 동시 번호 생성·참조 삭제, 부분 이관의 자동 재개/중복 방지는 별도의 통합 시험과 서버 경계 개선이 필요하다.

동명이 업체, 삭제·없는·중복 ID, 내부 ID 충돌, 사업자번호 불일치,
근로자 의뢰, 연결 보류, 계약 저장 취소·예외, 과거 기록 ID 오대입을 실행 테스트한다.
전체 HTML 스크립트 구문검사와 기존 동시편집·덮어쓰기 보호 검사를 함께 유지한다.

이 검증은 현재 클라이언트가 읽은 업체·담당자·업무 목록을 기준으로 한다.
Firebase 보안규칙이나 트랜잭션 경계를 변경하지 않았으며,
서버에서 동시 삭제·변경되는 모든 경쟁 상황을 원자적으로 차단한다는 보장은 아니다.
계약 저장의 성공 반환도 기존 로컬 저장·전송 대기열 수락 규칙을 따른다.

## 4-A 의 변경 — 화면·저장 자리 등록 계약 (2026-09-03)

예전 등록 검사는 **포털 타일 목록만** 봤다. 그래서 타일 없이 주소로 들어가는 화면 넷과
주인 없는 저장 자리 스물넷이 검사를 통째로 안 지났다. 온톨로지가 그 자료를 영영 못 본다는 뜻이다.

### 등록부에 새로 밝힌 것

- **딸린 화면(`SATELLITES`) 4개**: 이음센터 근무일정 보기(이알피)·취업규칙 작성기(취업규칙 관리)·
  푸른카메라(사진첩)·전자위임장 제출(문서관리). 딸린 화면은 **자기 저장 자리를 갖지 않는다** —
  자기 자리를 가지면 딸린 화면이 아니라 프로그램이므로 `PROGRAMS` 에 넣는다.
- **등록 제외(`EXCLUDED_SCREENS`) 2개**: 설치 안내·기금관리 실험 화면. 사유를 함께 적는다.
- **소유 저장 자리 보강**: 이알피(`improve_requests`·`hanaSmsBridge`·`ieum_public`),
  취업규칙 관리(`rules_mgmt`), 경력관리(`kcareer_inbox`·`kcareer_pub`), 뉴스레터 관리(`ilabor`).
- **밑바탕 자리(`INFRA_ROOTS`) 17곳**: 권한·접속·백업·요금 같은 살림은 업무 개체가 아니다.
  개체로 만들지 않지만 적어 두지 않으면 「주인 없는 자리」로 걸린다.
- **미루는 관계어(`PREDICATES_PLANNED`) 5개**: 사전에 적었지만 아직 만들지 않는 관계어에
  **왜 미루는지**를 함께 적는다. 사전에 말만 늘어나는 것을 막는다.

### 규칙이 바뀐 곳

포털 타일 수와 등록부 수가 **같은가**를 보던 검사를 버렸다. 그러면 타일 없는 프로그램
(근로자 전용·공개 화면)을 하나 넣는 순간 검사가 깨져 **등록을 안 하는 쪽이 쉬워진다.**
새 규칙은 두 줄이다 — 타일은 모두 등록돼 있어야 하고, 타일 없는 등록 프로그램은
`portal:false` 로 **타일이 없음을 밝혀야** 한다.

소유는 **경로**로 본다. 맨 앞 토막만 보면 기금관리(`data/funds`)와 푸른 메일(`pucards/mailbox`)이
「주인이 둘」로 걸린다. 그것은 곁방이고, 주인이 둘이라고 볼 것은 똑같은 경로뿐이다.

### 화면

검증센터에 **「등록·계약」** 칸이 늘었다. 소유 자리 없음·주인이 둘·딸린 화면 주인 없음·
아직 안 읽는 자리·미루는 관계어를 한 건씩 검토한다. 등록부 진단은 원본을 읽지도 쓰지도 않는다
(`readOnly:true`, `sourceMutation:'never'`).

머리줄은 「등록 프로그램 14개 · 딸린 화면 4개 · 등록 제외 2개 · 밑바탕 자리 17곳」을 말한다.

### 아직 안 읽는 자리 — 숨기지 않는다

소유는 밝혔지만 통합 진단이 아직 읽지 않는 자리가 있다(`improve_requests`·`hanaSmsBridge`·
`ieum_public`·`kcareer_inbox`·`kcareer_pub`). 「소유했으니 됐다」가 아니라 **「관계망이 아직 이걸 못 본다」**
로 화면에 남긴다. 읽기 어댑터를 넣거나, 통합 화면에서 읽지 않을 자료면 앱 내부로 선언한다.

### 미적용 범위

모든 프로그램의 저장 경로 입력 검증(6-3 나머지), 새 프로그램이 **입력 검증까지** 쓰게 하는 강제,
동시접속 통합 시험(6-5)은 이번 범위가 아니다.

`tests/ontology-registry.test.js` 가 이 계약을 기계로 지킨다. 되돌림 시험 10가지를 실제로 돌려
새 화면·빠진 소유·주인 둘·사유 없는 관계어가 모두 걸리는 것을 확인했다.

## 4-B — 인사·급여 기록을 «사람»에게 잇는다 (2026-09-04, 대표 판단 「1」)

### ★ 먼저: 앞선 목업의 전제가 틀렸다

`docs/mockups/ontology-next-steps.html` 3번은 「근로계약 38건이 사업장에 붙는다」로 그렸다.
구현하려고 자료 모양을 열어 보니 **그 넷은 고객 사업장 자료가 아니었다.**

```
employment_contracts   id:'ec-'+사번   { sid, name }      ← 푸른 직원 근로계약서
attendance_records                     { sid, date, ... }  ← 푸른 직원 근태
payroll_monthly        id:'pay-'+사번+'-'+연월 { empSid }   ← 푸른 직원 급여
leave_of_absence                       같은 갈래           ← 푸른 직원 휴가·휴직
```

`companyId` 칸이 아예 없고, 있을 수도 없다. **고객 사업장 근로자는 사건(`cases`)의
`workers` 안에** 있고, 그 사건은 이미 `concerns` 로 업체에 붙어 있다.

⚠ 목업대로 사업장에 붙였다면 **우리 직원의 급여·근태가 고객 업체 관계망에 들어갔다.**

### 한 것

- 사전에 관계어 하나를 더했다 — `recordedFor:['Employment|PayrollRecord','Person']`.
  둘로 가르지 않는다(사전에 말만 늘고 쓰는 자리는 같다).
- 네 갈래를 **사번**으로 사람에게 잇는다. 신뢰도 1.0 — 이름으로 맞추지 않는다.
- 사번이 비었거나 모르는 사번이면 **안 잇고 알린다**(`missing_person_sid`·`orphan_person`).
- ⚠ **사번 칸 이름이 갈래마다 다르다** — 급여만 `empSid`, 나머지는 `sid`.
  한쪽만 보면 급여가 통째로 안 붙는다.

### 함께 잡은 흠 — 급여를 `p.sid` 로 찾던 두 곳

급여 기록은 쓰는 자리 전부가 `empSid` 로 적는데, 읽는 자리 **둘**이 `p.sid` 로 찾고 있어
**늘 빈 손**이었다.

| 어디 | 무슨 일이 났나 |
|---|---|
| 퇴직정산 평균임금 | 최근 3개월 급여를 못 찾아 **평균임금 기초가 0** 이 됐다 |
| 직원 카드 급여 이력 | 이력이 **늘 비어** 보였다 |

옛 기록이 `sid` 로 적혔을 수 있어 `(p.empSid||p.sid)` 로 둘 다 본다.

### 권한

`Employment` 은 `personal`, `PayrollRecord` 는 `financial` 이다. 관계는 양 끝 중 **높은 쪽**을
따르므로(`edgeVisibility`) 이 관계들은 모두 **관리자만** 보는 칸에 들어간다.
검사가 그것을 실제로 스냅샷을 만들어 확인한다.

### 안 한 것

**사업장 재직 관계(`belongsToOrganization`)는 여전히 미룬 것으로 남는다** —
사업장 근로자에게 영구 번호가 없다(대표 판단 ①, 2026-09-03).
이번 일로 그것이 「된 것」처럼 지워지지 않도록 검사가 지킨다.

`tests/ontology-person-records.test.js` (6). 되돌림 시험 셋(급여 사번 칸 무시·모르는 사번
그냥 잇기·사업장에도 붙이기)이 모두 걸리는 것을 확인했다.

## 4-C — 무거운 자리는 «켤 때만» 읽는다 (2026-09-04)

### ★ 어긋난 안내가 먼저 있었다

어댑터 주석이 「두 자리 모두 «가벼운 자료»다. 사진 원본·판독 글자·급여 금액은 여기 없다」
라고 적혀 있었다. **틀린 말이었다.** `pucards/coInfo` 한 칸에는 `pu-cards.html` 의
`CO_FIELDS` 서른 칸이 들어 있고, 그 안에

- **계좌번호**(대표 결정으로 «온전히» 담긴다) · **예금주**
- **직전년도 매출액** · **생년월일**

이 있다. 진단을 한 번 돌릴 때마다 그것이 **4,158곳어치** 브라우저 메모리로 내려왔다.
CLAUDE.md 「관계 진단은 경량 메타데이터만 읽는다」와 어긋난다.

⚠ 읽은 사람이 안심하고 틀리는 자리였다 — **어긋난 안내는 없는 것보다 나쁘다.**

### 무엇이 문제이고 무엇이 아닌가

| | |
|---|---|
| **문제** | «내려받는 것» — 요금이 붙고, 계좌·매출액이 화면 메모리에 올라온다 |
| **문제 아님** | «저장되는 것» — `putEntity` 는 `label` 만 담는다. 관계망에 그 칸들은 안 들어간다 |

검사가 실제로 스냅샷을 만들어 계좌번호·예금주·매출액·생년월일이 **안 들어가는 것**을 확인한다.

### 한 것

- 어댑터에 **무겁다고 밝혔다** — 무엇이 함께 내려오는지(`heavy`), 관계에 실제로 쓰는 칸
  셋(`uses:['erpCoId','company','docs']`), 켜면 무엇이 나오는지(`gives`).
  `uses` 는 나중에 «얇은 거울»을 만들 때 그대로 명세가 된다.
- `getReadPlan(context)` 이 `context.heavy!==true` 면 그 자리에 `skip` 을 단다.
  ⚠ **목록에서 빼지는 않는다** — 빼면 무엇을 안 읽었는지 화면이 말할 수 없다.
- 검증센터에 스위치 「기업 상세도 함께 읽기」. **기본은 끔.**
- 안 읽었으면 **낮은 등급 알림**(`source_skipped_heavy`)으로 남긴다.
  ⚠ **「안 읽음」과 「못 읽음(권한)」을 섞지 않는다** — 섞으면 없는 권한 문제를 찾게 된다.
  프로그램 딱지도 「일부 연결(안 읽은 자리 있음)」로 말한다.

### 남은 것 — 이 걸음이 «절반»인 까닭

켜면 여전히 4,158곳 전문을 받는다. 실시간DB 는 칸을 골라 줄 수 없기 때문이다.
완전히 없애려면 **얇은 거울**이 필요하다 —
`pucards/ontIdx/{회사} = {c:회사명, e:erpCoId, d:{서류키:{n,k}}}`.

거울을 누가 유지하는가가 남은 결정이다.

| 길 | 좋은 점 | 걸리는 점 |
|---|---|---|
| 기업정보함이 쓸 때마다 갱신 | 지금 바로 가능 | 쓰는 자리가 여럿이라 하나 놓치면 **조용히 낡는다** |
| Cloud Function 트리거 | 놓칠 수 없다 | `firebase deploy --only functions` 가 아직 안 돌았다 |

`tests/ontology-heavy-read.test.js` (7). 되돌림 시험 셋(기본으로 읽기·건너뛴 것 조용히
넘기기·화면에서 skip 무시하고 받기)이 모두 걸리는 것을 확인했다.

## ㉡ — 관계망을 올린다 (2026-09-04)

지금까지 확정 관계망은 **파일 내려받기뿐**이었다. 볼 때마다 처음부터 다시 훑어야 했고,
다른 프로그램은 관계망을 아예 몰랐다. 서버에 쓰는 코드가 한 줄도 없었다.

### 자리 모양

```
ontology/v1/gen/{판번호}/meta                     판 하나의 머리
ontology/v1/gen/{판번호}/internal/entities|edges  업체·계약·사건·사업·일정  → 재직 직원
ontology/v1/gen/{판번호}/source/…                 서류·사진·메일·규정·제출  → 재직 직원
ontology/v1/gen/{판번호}/personal/…               사람·근로계약·근태·휴가   → 관리자만
ontology/v1/gen/{판번호}/financial/…              급여·수입·지출·청구서     → 관리자만
ontology/v1/current                              지금 볼 판 번호
```

칸을 **권한으로** 가른다. 관계망에 이름·금액·연락처는 안 담기지만,
「누가 무엇과 이어져 있는가」 자체가 알려 주는 것이 있다 —
CLAUDE.md 「원본보다 넓은 권한으로 공개하지 않는다」를 **자리 모양으로 못 박은 것**이다.

### 지키는 것 — 전부 검사가 기계로 본다

| | 왜 |
|---|---|
| 모든 경로가 `ontology/` 로 시작한다 | 원본을 향해 한 글자도 안 쓴다 |
| **`current` 는 맨 마지막** | 먼저 바꾸면 반쯤 올라간 판을 남이 읽는다 |
| 새 판은 옛 판을 **안 덮는다** | 올리다 끊겨도 보던 판이 그대로 산다 — 그것이 「직전 판 보관」이다 |
| 확정(1.0)만 올린다 | 추정 후보는 사람이 확정하기 전까지 저장 대상이 아니다 |
| 값에 이름·금액·연락처가 없다 | 색인은 원본 payload 를 복제하지 않는다 |
| 400칸씩 쪼개 쓴다 | 실시간DB 는 한 번에 16MB 까지다 — 기금에서 실제로 맞았다 |
| 화면이 먼저 묻는다 | 무엇이 올라가고 무엇이 빠지는지 말하고, 그만둘 수 있다 |

⚠ `uploadPlan` 은 **쓰지 않는다** — 무엇을 어디에 쓸지 «적어서 돌려줄» 뿐이다.
서버에 닿는 일은 화면이 한다. 그래야 검사가 파이어베이스 없이 전부 재어 본다.

`tests/ontology-upload.test.js` (8). 되돌림 넷(current 먼저 쓰기·안 쪼개기·
personal 을 직원에게 열기·이름표 싣기)이 모두 걸리는 것을 확인했다.

### ⚠ 규칙은 아직 «안 올라갔다»

이 원격 작업방에는 firebase CLI 가 없어 `scripts/rules-deploy.js --deploy` 가 못 돈다.
`docs/rules-paste.json` 을 만들어 두었다 — 대표가 콘솔에 붙여넣어야 산다.

마지막 콘솔 원본(2026-09-03)과 견주어 **사라질 규칙은 0건**이고 더해지는 것만 16개다
(온톨로지 13 + `data/co_no_seq` 3 — 뒤엣것은 다른 방의 「고유번호 머리+몸통」 작업이
만들개에는 들어갔으나 콘솔에는 아직 안 올라간 것이다).

⚠ 다만 **살아 있는 콘솔과 견주지는 못했다.** 그 사이 누가 콘솔을 손으로 고쳤다면
이 붙여넣기가 그것을 지운다. 대표 PC 에서 `node scripts/rules-deploy.js --deploy` 를
돌리면 그 확인까지 자동으로 한다 — 그 길이 있으면 그쪽이 낫다.

## 4-D — 얇은 거울 (2026-09-05, 대표 지시 「모두 진행」)

4-C 는 절반이었다. 무거운 자리를 끄면 서류 관계가 통째로 빠지고, **켜면 여전히**
기업 상세 4,158곳 **전문**을 받았다(계좌번호·예금주·매출액·생년월일이 함께).

### ★ 누가 거울을 유지하는가 — 「읽는 쪽」으로 정했다

설계안의 두 길 중 어느 쪽도 안 골랐다.

| 길 | 왜 안 골랐나 |
|---|---|
| 기업정보함이 «쓸 때마다» 갱신 | 쓰는 자리가 `pu-cards.html`·`js/pu-doc-file.js` 두 파일에 흩어져 있다. **하나만 놓쳐도 조용히 낡는다** |
| Cloud Function 트리거 | 놓칠 수 없지만 `firebase deploy --only functions` 가 아직 안 돌았다 |

**셋째 길**: 무거운 자리를 **한 번 읽은 김에** 거울을 떠 둔다.
쓰는 자리를 하나도 안 건드리므로 **놓칠 자리가 없다.**

⚠ 대신 거울은 **낡을 수 있다.** 숨기지 않는다 — 화면이 「마지막으로 뜬 때」를 말하고,
새로 뜨려면 무거운 자리를 켜서 한 번 읽으면 된다.

### 자리

```
pucards/ontIdx/{회사} = { c:회사명, e:확정 업체열쇠, d:{서류키:{n:이름, k:갈래}} }
pucards/ontIdxMeta    = { at:뜬 때, n:곳 수 }
```

**규칙은 손댈 것이 없다** — `pucards/$k` 가 이미 열려 있다(`sentDocs` 와 같은 자리).

### 지키는 것

| | 왜 |
|---|---|
| 관계에 쓰는 **셋만** 담는다 | 계좌·예금주·매출액·생년월일은 **담길 자리 자체가 없다** |
| 거울로 읽어도 **같은 관계** | 켰다 껐다 할 때 관계망이 흔들리면 안 된다 — 검사가 두 길의 관계를 **견준다** |
| 「언제 뜬 것인가」는 **맨 마지막** | 반쯤 뜬 거울을 새것으로 읽으면 안 된다 |
| 200곳씩 모아 쓴다 | 2026-08-16 대량 쓰기 사고 |
| 못 쓸 열쇠는 **건너뛴다** | 점(`.`)이 든 이름 하나에 4,158곳이 통째로 멎지 않게 |
| 안 읽었으면 **못 뜬다** | 빈 거울이 서버에 올라가면 서류 관계가 통째로 사라진다 |

`tests/ontology-mirror.test.js` (8). 되돌림 넷(민감한 칸 담기·머리줄 먼저 쓰기·
거울 파서가 다른 관계 내기·안 읽고도 뜨기)이 모두 걸린다.
