# 푸른통합 온톨로지 6단계 — 입력·저장 검증

## 순서와 현재 범위

1. **업체관리 → 계약 입력의 업체 연결 검증**: 구현 완료.
2. **담당자 사번·계약·사건 참조 검증**: 계약·사건 입력 및 건별 전체 저장에 적용.
3. 자동 수집·일괄 가져오기·다른 프로그램 저장 경로 검증: **3-A 사건 일괄 가져오기·계약 자동 이관 적용**, 나머지는 다음 범위.
4. 신규 프로그램 배포 계약 강화: 공통 사전·등록 검사에 입력 검증을 추가 예정.
5. 여러 담당자·자동 수집이 겹치는 동시접속 통합 시험: 별도 단계.

이번 구현은 ERP 계약·사건 입력 모달, 각 관리 화면의 건별 전체 저장,
사건 일괄 저장 및 계약에서 업체·사건·컨설팅·기금·기타사업으로 이관하는 경로를 대상으로 한다.
모든 프로그램의 서버 쓰기를 차단하는 전역 가드나 DB 외래키 제약은 아니다.
기존 계약 이관·자동 생성·일괄 가져오기 경로 전체가 검증되었다고 간주하지 않는다.

## 1번의 변경

- 회사명 검색은 후보만 제공한다. 계약 저장에서 이름으로 업체 ID를 자동 선택하지 않는다.
- 실제 업체 ID 존재 여부, 삭제·중복, 최상위/중첩 ID 충돌, 사업자번호 불일치를 검사한다.
- 업체 선택 시 회사명·사업자번호를 반영하고 ID를 두 위치에 일치시킨다.
- 회사명·사업자번호를 직접 변경하면 기존 연결을 풀고 다시 검증한다.
- 과거 계약·사건의 자체 ID를 업체 ID로 대입하지 않는다.
- 기존 업체정보 동기화는 선택된 ID 한 건에만 적용한다. 같은 이름의 다른 업체는 그대로 둔다.
- 계약 저장이 취소·실패하면 업체 동기화·임시작성본 삭제·사진 공유를 수행하지 않는다.
- 확인창이 열린 동안 업체 상태가 바뀔 수 있으므로 건별 저장 직전과 업체 동기화 직전에 다시 검사한다.

## 연결 상태

| 값 | 의미 | 업체 마스터 동기화 |
|---|---|---|
| `linked` | 명시적 업체 ID를 목록에서 검증함 | 그 ID 한 건만 |
| `pending` | 사용자가 신규·미확정 업체로 연결 보류를 선택함 | 하지 않음 |
| `not_required` | 업체 연결이 없는 근로자 단독 의뢰 | 하지 않음 |

연결 보류는 계약 자체를 폐기하지 않고 업무를 이어가기 위한 선택이다.
보류된 업체 관계는 확정 관계망에 들어가지 않으며, 이후 업체 등록·선택 및 재진단이 필요하다.
기존 자료는 일괄 수정하지 않는다. 기존의 잘못된 연결은 그 계약을 편집해 저장할 때 확인한다.

## 검증과 한계

### 2번의 변경 — 담당자·원본 업무 참조

- 현재 `user_dir`와 `user_accounts`의 실제 사번으로 검증한다. 이름이나 초기 seed를 SID로 변환하지 않는다.
- 계약 담당자 드롭다운의 기존 이름 기반 선택값을 SID로 고쳤다. 계약·사건 선택 목록은 이름과 사번을 함께 표시해 동명이인을 구분한다. 명부에 없는 기존 값은 별도 옵션으로 유지한다.
- 신규 주담당·부담당은 사번 존재·중복·퇴직·삭제·잠금·배제·휴직 여부를 확인한다. 같은 사번의 계정 상태가 공개 명부보다 우선한다.
- 변경하지 않은 과거 담당자와 끊어진 원본 참조는 경고로 남겨 일반 내용 수정을 허용한다. 이는 새 연결의 유효성 승인이 아니며 원본을 자동 정리하지 않는다.
- 계약 담당자 탭과 사건 편집 화면에 원본 계약·사건 검색/선택을 추가했다. 선택할 때만 draft에 실제 ID를 넣으며, 명시적 연결 해제도 저장 전까지 원본에 반영하지 않는다.
- `sourceKind`·`sourceId`, `sourceContractId`는 원본 존재·삭제·중복·자기참조·상충 여부를 확인한다. `sourceContractNo` 단독 기록은 기존 값을 경고로 보존하고 신규 번호 단독 연결은 막는다.
- 계약·사건의 명시적이며 유일한 원본 ID만 `derivedFrom` 관계로 진단한다. 번호로 ID를 추정하지 않으며 끊어진/모순된 참조는 검증센터에서 확인한다.
- 입력 시점뿐 아니라 `persistOne`·`caseUpsert` 저장 직전에도 검증한다. 검증 모듈이 로드되지 않으면 해당 저장을 막는다.

`tests/ontology-work-references.test.js`는 순수 검증 함수, 실제 입력 패널과 최종 저장 함수 실행을 검사한다.
실데이터를 삭제·변경하는 테스트는 하지 않는다.

### 3-A의 변경 — 사건 일괄 입력·계약 자동 이관

- 사건 가져오기는 이름을 SID로 추정하지 않는다. 미리보기에서 주담당·부담당을 이름+사번 목록으로 직접 선택하며 원본 행 배열은 직접 변경하지 않는다.
- 사건유형·상태·의뢰인·번호를 확인하고, 빈 사건번호는 같은 배치 안에서 겹치지 않게 생성한다. 기존 번호 또는 입력 목록 내 중복 번호는 보류한다.
- `validateWorkBatch`가 전 행의 ID, 담당자, 원본 참조를 검사한다. 신규 입력의 기존 ID 덮기·삭제 ID 재생성·중복 ID를 차단한다. 한 행이라도 실패하면 해당 배치를 저장하지 않는다.
- 저장 함수가 실패하면 미리보기를 닫거나 성공 알림을 띄우지 않는다. 원본 파일은 읽기만 하고 삭제하지 않는다. 사건 번호 일괄 변경도 검증과 저장 성공 후에만 완료를 알린다.
- 계약 이관 전 원본 계약 ID와 변경 시각, 신규 담당자 배정, 업체 연결을 다시 확인한다. 미확정 업체와 같은 이름/사업자번호 후보가 이미 있으면 자동 선택하거나 새로 만들지 않고 명시적 선택을 요청한다.
- 업체·사건·컨설팅·기금·기타사업 생성에 `sourceContractId`, `sourceKind:'contract'`, `sourceId`를 남긴다. 사건·프로젝트의 업체 ID도 검증된 계약의 ID만 승계한다.
- 새 레코드의 개체 종류와 생성·갱신 시각을 기록한다. 명시적 원본 ID 관계는 `derivedFrom`으로 진단하며 번호만으로 색인을 만들지 않는다.
- 이관 실패 정리에서 기존 업체에 이어 붙인 `linked` 결과는 삭제하지 않는다. 이미 반영한 기존 업체의 빈칸 보완/메모는 보존되므로 사람이 확인한다. 여러 저장을 하나의 서버 트랜잭션으로 바꾼 것은 아니다.
- 재이관/완료 판단은 명시적 원본 ID를 우선한다. 번호만 남은 과거 연결·상충 ID·일부 업무만 존재하는 이관 흔적은 자동 완료 처리하지 않고 검토를 요청한다.

`tests/ontology-intake.test.js`는 실제 미리보기 선택·일괄 저장·계약 이관·재이관 함수를 가짜 저장소에서 실행한다.
정상/불량 행 혼합, 저장 실패 후 재시도, 동명이인, 중복 번호, 원본 변경,
기존 업체 보존, 신규 생성분만 정리, 부분 이관 완료 방지를 검사한다.

**다음 범위(미적용):** 은행/SMS·OCR·자료메일 자동 수집, 다른 프로그램의 가져오기,
역이관·부분 패치, 기존 이름→SID 부팅 정규화, 사건의 기존 업체정보 자동 보완/업체 연결.
전체 프로그램의 저장 경로 검증 및 모든 업무 간 순환 참조 검사는 별도 확장 대상이다.

배치 전 행 검증은 서버의 원자적 커밋 보장이 아니다. 오프라인 전송 대기열, 서버 승인 실패,
다른 기기의 동시 번호 생성·참조 삭제, 부분 이관의 자동 재개/중복 방지는 별도의 통합 시험과 서버 경계 개선이 필요하다.

동명이 업체, 삭제·없는·중복 ID, 내부 ID 충돌, 사업자번호 불일치,
근로자 의뢰, 연결 보류, 계약 저장 취소·예외, 과거 기록 ID 오대입을 실행 테스트한다.
전체 HTML 스크립트 구문검사와 기존 동시편집·덮어쓰기 보호 검사를 함께 유지한다.

이 검증은 현재 클라이언트가 읽은 업체·담당자·업무 목록을 기준으로 한다.
Firebase 보안규칙이나 트랜잭션 경계를 변경하지 않았으며,
서버에서 동시 삭제·변경되는 모든 경쟁 상황을 원자적으로 차단한다는 보장은 아니다.
계약 저장의 성공 반환도 기존 로컬 저장·전송 대기열 수락 규칙을 따른다.
