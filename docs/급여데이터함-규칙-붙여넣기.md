# 급여데이터함 — 콘솔에 붙여넣을 규칙

2026-08-13 작성 · 대상: 새 앱 `pu-paydata.html`
설계서: `docs/superpowers/specs/2026-08-13-급여데이터함-design.md`

> **대표님이 하실 일은 두 번의 붙여넣기입니다.**
> ① 실시간DB 규칙에 `paydata` 블록 끼워 넣기 → ② 창고 규칙에 `pu_paydata` 줄 더하기
>
> **이걸 하기 전에는 앱의 첫 저장이 반드시 「권한 거부」로 막힙니다.** 규칙 문제인데
> 코드 문제로 오진하지 않도록 이 문서를 먼저 둡니다.

---

## 0. 먼저 확인할 것 — 창고 주소

앱마다 창고 주소가 셋으로 갈려 있습니다. **셋이 다 살아 있을 수는 없습니다.**

| 앱 | 지금 설정된 창고 |
|---|---|
| 사진첩 · 기금 · 컨설팅 · 업무관리 | `pureun-erp.firebasestorage.app` |
| 명함첩 | `pureun-erp-photos` |
| 급여관리 | `pureun-erp.appspot.com` |

**확인 방법:** 파이어베이스 콘솔 → 왼쪽 메뉴 `Storage` → 화면 위쪽에 적힌 버킷 이름.

**확인 결과를 여기 적어 주십시오:**

```
실재하는 버킷 이름:  (여기 적기)
확인한 날:            (여기 적기)
```

급여데이터함은 **사진첩과 같은 창고**(`pureun-erp.firebasestorage.app`)를 쓰도록 코드에 적어 두었습니다. 확인한 이름이 이것과 다르면 알려 주십시오 — 코드 한 줄을 바꿉니다. 다르다는 것을 모르고 진행하면 파일이 엉뚱한 곳에 쌓입니다.

## 1. 실시간DB 규칙 — `paydata` 블록 끼워 넣기

**⚠ 전체를 덮어쓰지 마십시오.** 현재 규칙에는 최상위 열쇠가 40개 가까이 있습니다
(`data` · `pucards` · `puphotos` · `payroll_os` · `fund_erp` …). 덮으면 그 앱들이 전부 막힙니다.

**넣는 자리:** 콘솔 → `Realtime Database` → `규칙` 탭 → `"rules": {` 안쪽,
기존 열쇠들과 같은 층에 아래를 **추가**합니다. 앞뒤 열쇠 사이에 쉼표(`,`)가 빠지지 않게 봐 주십시오.

```json
"paydata": {
  "u": {
    "$owner": {
      ".read": "auth != null",
      ".write": "auth != null && ($owner === auth.uid || root.child('paydata/u/'+$owner+'/deputy/'+auth.uid+'/to').val() >= now)"
    }
  },
  "pending_shared": {
    ".read": "auth != null",
    ".write": "auth != null"
  },
  "owners": {
    ".read": "auth != null",
    "$uid": {
      ".write": "auth != null && $uid === auth.uid"
    }
  },
  "arrivals": {
    ".read": "auth != null",
    ".write": "auth != null"
  },
  "access_log": {
    ".read": "auth != null && root.child('uid_roles/'+auth.uid+'/isAdmin').val() === true",
    "$id": {
      ".write": "auth != null && !data.exists()"
    }
  },
  "handoff_log": {
    ".read": "auth != null && root.child('uid_roles/'+auth.uid+'/isAdmin').val() === true",
    "$id": {
      ".write": "auth != null && !data.exists()"
    }
  }
}
```

### 이 규칙이 하는 일 (읽어 보실 부분)

**`u/$owner` — 사람별 자리.** 급여데이터함은 자료를 사람마다 따로 담습니다.

- **쓰기**: 자기 자리이거나(`$owner === auth.uid`), **휴가 대리로 맡은 자리**일 때만 열립니다.
- 뒷부분 `deputy/{내 계정}/to` 가 지금(`now`)보다 뒤일 때만 통과합니다 —
  **기간이 지나면 규칙이 저절로 닫습니다.** 돌아와서 회수를 잊어도 열려 있지 않습니다.
  사람이 거둬야 닫히는 권한은 반드시 열린 채로 남습니다. 이것이 이 규칙의 핵심입니다.
- **읽기**: 로그인한 직원은 남의 자리를 읽을 수 있습니다(2026-08-13 대표 결정 —
  전 직원 열람 가능, 단 **사유를 적어야** 함). 사유 받기와 기록 남기기는 앱이 합니다.

**`arrivals` — 도착 칸.** 급여관리 수신함이 「어느 업체가 이번 달 자료를 보냈나」를
한 화면에서 보려면 이 칸이 필요합니다. **업체·귀속월·종류·시각만** 들어갑니다 —
자료 본문도, 값도, 파일 이름도 넣지 않습니다(파일 이름에는 근로자 성명이 흔히 들어 있습니다).

**`access_log` · `handoff_log` — 기록.** 관리자만 읽고, **한 번 쓰면 못 고칩니다**
(`!data.exists()`). 지울 수 있는 기록은 기록이 아닙니다.

**`pending_shared` — 공용 대기 칸.** 나중에 메일 자동수신(5차)이 붙으면 서버가 받은
첨부가 여기 놓입니다. 서버는 사람이 아니라 「누구 자리」가 없기 때문입니다.
누구든 집어서 자기 자리로 내려보내고, 집은 사람이 기록에 남습니다.

### 넣은 뒤 확인

콘솔 규칙 화면에서 **「게시」**를 누르고, 오류 없이 게시되는지 봅니다.
문법 오류가 나면 쉼표 빠짐이 거의 대부분입니다.

## 2. 창고 규칙 — `pu_paydata` 줄 더하기

**넣는 자리:** 콘솔 → `Storage` → `Rules` 탭.
기존 `match /b/{bucket}/o {` 안쪽에 아래 블록을 **추가**합니다(다른 `match` 줄은 그대로 둡니다).

```
match /pu_paydata/{uid}/{allPaths=**} {
  allow read: if request.auth != null;
  allow write: if request.auth != null && request.auth.uid == uid;
}
```

### 왜 이렇게 생겼는가 — 그리고 한계

**⚠ 창고 규칙은 실시간DB를 볼 수 없습니다.** (파이어베이스 창고 규칙은 Firestore만
참조할 수 있습니다.) 그래서 **대리인 판정을 창고에서 할 수 없습니다.**

그래서 이렇게 우회했습니다.

- 파일은 **항상 올린 사람 자리**에 놓입니다(주인 자리가 아닙니다).
- 「누구 자리 소속인가」는 **실시간DB 정보**가 정합니다. 대리인이 올린 파일도 DB상
  주인 자리에 매입니다.
- 지우기는 **DB 정보를 휴지통으로 옮기는 것**으로 합니다. 창고 파일 실삭제는 30일 뒤
  사람이 확인해서 합니다(자동 삭제 없음).

**남는 한계 — 대표님께 알려 두는 것:**

창고 **읽기가 로그인한 직원 전체로 열립니다.** 앱을 거치지 않고 파일 주소를 직접 아는
경우 열람 기록이 남지 않습니다. 서명 주소(signed URL)로 막을 수 있지만 서버 작업이
커서 1차 범위에서 뺐습니다. **이 상태로 진행하는 것을 알고 계신 채로** 갑니다.

## 붙임 — 규칙을 저장소 파일로 배포하지 않는 이유

이 저장소에는 규칙 JSON 파일들이 있습니다(`docs/firebase-rules-*.json`). 그것들은
**참고용 사본**입니다. **진짜는 콘솔입니다.**

저장소 파일로 배포했다가 사진첩과 성과확인이 막힌 일이 있었습니다 — 저장소 사본이
콘솔보다 낡아서, 배포가 최신 규칙을 덮어버렸기 때문입니다. 그래서 **콘솔에 직접
붙여넣는 방식만** 씁니다.
