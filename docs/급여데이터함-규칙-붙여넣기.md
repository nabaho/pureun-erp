# 급여데이터함 — 콘솔에 붙여넣을 규칙

2026-08-13 작성 · 대상: 새 앱 `pu-paydata.html`
설계서: `docs/superpowers/specs/2026-08-13-급여데이터함-design.md`

> **대표님이 하실 일은 두 번의 붙여넣기입니다.**
> ① 실시간DB 규칙에 `paydata` 블록 끼워 넣기 → ② 창고 규칙에 `pu_paydata` 줄 더하기
>
> **이걸 하기 전에는 앱의 첫 저장이 반드시 「권한 거부」로 막힙니다.** 규칙 문제인데
> 코드 문제로 오진하지 않도록 이 문서를 먼저 둡니다.

> **2026-08-13 갱신 — 「폴더」 칸이 하나 늘었습니다.**
> 사진첩의 「내 폴더」(분류와 다른 축 — "어느 일인가")를 급여데이터함에도 넣기로
> 하면서, `paydata/u/$owner` 아래에 `folders` 칸을 하나 더했습니다. **실시간DB
> 규칙을 이미 넣어 두셨더라도 아래 1장을 다시 통째로 붙여넣어 주셔야 합니다**
> (조각만 더하지 마십시오 — 이 문서 1장에 그 이유가 있습니다). 창고 규칙(2장)은
> 안 바뀌었으니 다시 안 하셔도 됩니다.

> **2026-08-14 갱신 — 「공유」 칸이 새로 생겼습니다.**
> 좌측 사람별 대시보드에서 "내 업체를 다른 담당자와 공유"하는 기능을 위해
> `paydata` 아래 최상위로 `shares` 칸을 새로 더했습니다 — `arrivals`·`pending_shared`와
> 같은 **자리 밖 열린 칸**(전 직원이 읽고 쓸 수 있음, 이 앱을 쓰는 사람끼리 공유 표시만
> 남기는 용도라 이 정도 개방으로 충분합니다). **이번에도 아래 1장을 통째로 다시
> 붙여넣어 주셔야 합니다.** 창고 규칙(2장)은 이번에도 안 바뀌었습니다.
>
> ⚠ 이 파일은 2026-08-13에 콘솔과 글자 단위로 맞춰 본 버전 위에 `shares` 블록만
> 더한 것입니다(레포에 커밋된 시점 기준 diff는 그 한 칸 추가뿐임을 확인했습니다).
> 다만 그 사이 다른 작업에서 콘솔을 직접 고쳤을 수 있으니, **붙여넣기 전에 지금
> 콘솔에 떠 있는 규칙과 이 파일의 `paydata` 앞부분이 크게 다르지 않은지 한 번
> 훑어봐 주십시오.** 다르면 붙여넣지 말고 먼저 알려 주세요 — 다시 맞춰 드립니다.

## 0. 먼저 확인할 것 — 창고 주소

앱마다 창고 주소가 셋으로 갈려 있습니다. **셋이 다 살아 있을 수는 없습니다.**

| 앱 | 지금 설정된 창고 |
|---|---|

| 명함첩 | `pureun-erp-photos` |
| 급여관리 | `pureun-erp.appspot.com` |

## 1. 실시간DB 규칙 — **전체 파일을 통째로 붙여넣으십시오**

> **⚠ 이 아래의 `paydata` 블록만 따로 붙여넣지 마십시오.** 그것은 전체 규칙의 **한 조각**입니다.
> 조각만 붙여넣으면 지금까지의 규칙 전체가 사라지고 `Line 1: Expected '{'` 오류가 납니다.
> (2026-08-13 실제로 그렇게 됐습니다. 오류 덕에 게시가 막혀 사고는 없었습니다 —
> 그때는 **「게시」가 아니라 옆의 「삭제」**를 눌러 원래대로 되돌립니다.)

**이렇게 하십시오.**

1. `docs/firebase-rules-급여데이터함-포함(붙여넣기용).json` 파일을 엽니다
2. **전체를 복사**합니다 (`{` 부터 마지막 `}` 까지)
3. 콘솔 → `Realtime Database` → `규칙` 탭에서 **전체를 지우고 붙여넣습니다**
4. `게시`

그 파일은 **대표님이 지금 쓰고 계신 규칙 그대로**에 `paydata` 한 칸만 더한 것입니다.
`paydata` 를 뺀 나머지가 현재 규칙과 **글자 하나까지 같은 것을 기계로 확인**했습니다
(최상위 40칸, `paydata` 는 `puphotos` 다음 21번째).

### 아래는 무엇이 더해졌는지 보시기 위한 것입니다 (붙여넣지 마십시오)

```json
"paydata": {
  "u": {
    "$owner": {
      ".read": "auth != null && auth.token.firebase.sign_in_provider === 'password'",
      "deputy": {
        ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password' && $owner === auth.uid",
        "$deputy": {
          "from": { ".validate": "newData.isNumber()" },
          "to": { ".validate": "newData.isNumber()" }
        }
      },
      "items": {
        ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password' && ($owner === auth.uid || root.child('paydata/u/' + $owner + '/deputy/' + auth.uid + '/to').val() >= now)"
      },
      "pending": {
        ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password' && ($owner === auth.uid || root.child('paydata/u/' + $owner + '/deputy/' + auth.uid + '/to').val() >= now)"
      },
      "values": {
        ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password' && ($owner === auth.uid || root.child('paydata/u/' + $owner + '/deputy/' + auth.uid + '/to').val() >= now)"
      },
      "thumbs": {
        ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password' && ($owner === auth.uid || root.child('paydata/u/' + $owner + '/deputy/' + auth.uid + '/to').val() >= now)"
      },
      "trash": {
        ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password' && ($owner === auth.uid || root.child('paydata/u/' + $owner + '/deputy/' + auth.uid + '/to').val() >= now)"
      }
    }
  },
  "pending_shared": {
    ".read": "auth != null && auth.token.firebase.sign_in_provider === 'password'",
    ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password'"
  },
  "owners": {
    ".read": "auth != null && auth.token.firebase.sign_in_provider === 'password'",
    "$uid": {
      ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password' && $uid === auth.uid"
    }
  },
  "arrivals": {
    ".read": "auth != null && auth.token.firebase.sign_in_provider === 'password'",
    ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password'"
  },
  "shares": {
    ".read": "auth != null && auth.token.firebase.sign_in_provider === 'password'",
    ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password'"
  },
  "access_log": {
    ".read": "auth != null && root.child('uid_roles').child(auth.uid).child('isAdmin').val() == true",
    "$id": {
      ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password' && !data.exists()"
    }
  },
  "handoff_log": {
    ".read": "auth != null && root.child('uid_roles').child(auth.uid).child('isAdmin').val() == true",
    "$id": {
      ".write": "auth != null && auth.token.firebase.sign_in_provider === 'password' && !data.exists()"
    }
  }
}
```

### 실물 규칙을 보고 두 가지를 고쳤습니다 (2026-08-13)

**① 익명 로그인이 뚫려 있었습니다.** 현재 규칙은 거의 모든 칸에
`auth.token.firebase.sign_in_provider === 'password'` 를 붙여 **아이디·비밀번호로 들어온
사람만** 통과시킵니다(익명 차단, 2026-08-04 작업). 제 초안은 `auth != null` 만 있어서
익명 계정도 급여자료를 읽을 수 있었습니다. **모든 줄에 붙였습니다.**

**② 대리인이 스스로 기간을 늘릴 수 있었습니다.** 이게 더 중요합니다.
초안은 `u/$owner` 한 곳에 쓰기를 열어 뒀는데, 그러면 **맡은 사람이 그 아래
`deputy/{자기 계정}/to` 를 직접 늘려 영구화**할 수 있었습니다. 「기간이 지나면 저절로
닫힌다」가 무너집니다.

파이어베이스 규칙은 **위에서 한 번 허락하면 아래에서 되돌릴 수 없습니다.**
그래서 `u/$owner` 에 쓰기를 열지 않고, 그 아래 **칸마다 따로** 열었습니다.

| 칸 | 누가 쓸 수 있나 |
|---|---|
| `deputy` | **주인만** — 맡기고 거두는 것은 주인의 권한이다 |
| `items` · `pending` · `values` · `thumbs` · `trash` · `folders` | 주인 **또는 기간 안의 대리인** |

같은 조건이 여섯 번 되풀이돼 길어 보이지만, 규칙에는 변수가 없어서 이게 유일한 방법입니다.
(현재 규칙의 `perf_confirm` 도 같은 이유로 칸마다 되풀이합니다.)

**`folders` — 사진첩의 「내 폴더」와 같은 것입니다(2026-08-13 추가).** 종류 탭이
「무엇인가」(근태·급여대장…)라면 폴더는 「어느 일인가」(예: 「2026 정기감사」)입니다.
내가 정리하는 방식이라 대리인이 맡은 기간에는 함께 쓸 수 있게 했고, 그 밖에는
전 직원이 **보기만** 됩니다(`$owner` 의 `.read` 를 그대로 물려받습니다).

### 이 규칙이 하는 일 (읽어 보실 부분)

**`u/$owner` — 사람별 자리.** 급여데이터함은 자료를 사람마다 따로 담습니다.

- **쓰기**: 자기 자리이거나(`$owner === auth.uid`), **휴가 대리로 맡은 자리**일 때만 열립니다.
- 뒷부분 `deputy/{내 계정}/to` 가 지금(`now`)보다 뒤일 때만 통과합니다 —
  **기간이 지나면 규칙이 저절로 닫습니다.** 돌아와서 회수를 잊어도 열려 있지 않습니다.
  사람이 거둬야 닫히는 권한은 반드시 열린 채로 남습니다. 이것이 이 규칙의 핵심입니다.
- **읽기**: 로그인한 직원은 남의 자리를 읽을 수 있습니다(2026-08-13 대표 결정 —
  전 직원 열람 가능, 단 **사유를 적어야** 함). 사유 받기와 기록 남기기는 앱이 합니다.

> **⚠ 사진첩과 여기가 다릅니다 — 일부러 다릅니다.**
> 현재 규칙의 `puphotos/u/$uid` 는 읽기를 **본인 또는 관리자**로 묶어 두었습니다
> (2026-08-03 지시). 급여데이터함은 **전 직원이 이름을 골라 읽을 수 있게** 열어 둡니다
> (2026-08-13 결정). 급여자료가 사진보다 더 민감한데 더 넓게 여는 것이라, 「실수로 넓힌
> 것」으로 보이지 않게 여기 적어 둡니다. 좁히려면 `.read` 를 사진첩과 같은 꼴로 바꾸면
> 되고, 그러면 「같은 사업장 담당자끼리만」이 아니라 「본인·관리자만」이 됩니다.

**`arrivals` — 도착 칸.** 급여관리 수신함이 「어느 업체가 이번 달 자료를 보냈나」를
한 화면에서 보려면 이 칸이 필요합니다. **업체·귀속월·종류·시각만** 들어갑니다 —
자료 본문도, 값도, 파일 이름도 넣지 않습니다(파일 이름에는 근로자 성명이 흔히 들어 있습니다).

**`access_log` · `handoff_log` — 기록.** 관리자만 읽고, **한 번 쓰면 못 고칩니다**
(`!data.exists()`). 지울 수 있는 기록은 기록이 아닙니다.

**`pending_shared` — 공용 대기 칸.** 나중에 메일 자동수신(5차)이 붙으면 서버가 받은
첨부가 여기 놓입니다. 서버는 사람이 아니라 「누구 자리」가 없기 때문입니다.
누구든 집어서 자기 자리로 내려보내고, 집은 사람이 기록에 남습니다.

**`shares` — 업체 공유(2026-08-14 추가).** 좌측 사람별 대시보드에서 내 업체를
다른 담당자에게 "이거 봐 주세요"로 알리는 칸입니다. `arrivals`·`pending_shared`와
같은 이유로 자리(`u/$owner`) **밖**에 둡니다 — 받는 사람의 자리 안에 쓰려면
그 사람 것이 아닌데도 쓸 수 있어야 하는데, `u/$owner`는 주인·대리인만 쓸 수
있게 일부러 막아 뒀기 때문입니다. 권한을 주는 칸이 아니라 **표시(알림)만
남기는** 칸이라 — 실제 서류를 보는 권한은 지금처럼 이름을 골라 보는 방식
그대로입니다 — 전 직원에게 열어도 위험이 크지 않습니다.

### 넣은 뒤 확인

콘솔 규칙 화면에서 **「게시」**를 누르고, 오류 없이 게시되는지 봅니다.
문법 오류가 나면 쉼표 빠짐이 거의 대부분입니다.

## 2. 창고 규칙 — **전체 파일을 통째로 붙여넣으십시오**

실시간DB와 똑같습니다. **조각만 붙여넣지 마십시오.**

1. `docs/firebase-storage-급여데이터함-포함(붙여넣기용).txt` 파일을 엽니다
2. **전체를 복사**합니다
3. 콘솔 → `Storage` → `Rules` 에서 **전체를 지우고 붙여넣습니다**
4. `게시`

그 파일은 **2026-08-13 대표님이 주신 현재 창고 규칙 그대로**에 `pu_paydata` 칸과
`okPayFile()` 함수만 더한 것입니다. **지운 줄이 하나도 없는 것을 기계로 확인**했습니다
(더한 줄 20줄, 그중 규칙 9줄·주석 11줄).

더해진 것은 이 두 덩이입니다(무엇이 들어갔는지 보시기 위한 것 — 붙여넣지 마십시오).

```
match /pu_paydata/{uid}/{allPaths=**} {
  allow read:   if isStaff();
  allow write:  if signedIn() && request.auth.uid == uid && okPayFile();
  allow delete: if signedIn() && request.auth.uid == uid;
}

function okPayFile() {
  return request.resource != null
      && request.resource.size < 25 * 1024 * 1024;
}
```

### 사진첩과 두 군데가 다릅니다 — 둘 다 일부러입니다

| | 사진첩 (`puphotos`) | 급여데이터함 (`pu_paydata`) |
|---|---|---|
| 읽기 | **본인만** | **전 직원** (이름 골라 보기 — 대표 결정 2026-08-13) |
| 파일 종류 | 사진만 (`okImage`) | **묶지 않음** — 엑셀·PDF를 받아야 한다 |
| 크기 | 10MB | 25MB |

**종류를 왜 안 묶는가:** 한글 파일(`hwp`)은 브라우저가 종류를 안 알려주는 일이 흔해서,
종류로 묶으면 통째로 막힙니다. 엉뚱한 종류(`exe`·`js`·`html`)는 **앱이 올리기 전에
거절**합니다 — 계획서 Task 10에 그 검사가 들어 있습니다.

### 대리인 판정을 창고에서 못 하는 것 — 그리고 한계

**⚠ 창고 규칙은 실시간DB를 볼 수 없습니다.** (파이어베이스 창고 규칙은 Firestore만
참조할 수 있습니다.) 그래서 **대리인 판정을 창고에서 할 수 없습니다.**

그래서 이렇게 우회했습니다.

- 파일은 **항상 올린 사람 자리**에 놓입니다(주인 자리가 아닙니다).
- 「누구 자리 소속인가」는 **실시간DB 정보**가 정합니다. 대리인이 올린 파일도 DB상
  주인 자리에 매입니다.
- 지우기는 **DB 정보를 휴지통으로 옮기는 것**으로 합니다. 창고 파일 실삭제는 30일 뒤
  사람이 확인해서 합니다(자동 삭제 없음).

**남는 한계 — 대표님께 알려 두는 것:**

## 붙임 — 규칙을 저장소 파일로 배포하지 않는 이유

이 저장소에는 규칙 JSON 파일들이 있습니다(`docs/firebase-rules-*.json`). 그것들은
**참고용 사본**입니다. **진짜는 콘솔입니다.**

저장소 파일로 배포했다가 사진첩과 성과확인이 막힌 일이 있었습니다 — 저장소 사본이
콘솔보다 낡아서, 배포가 최신 규칙을 덮어버렸기 때문입니다. 그래서 **콘솔에 직접
붙여넣는 방식만** 씁니다.
