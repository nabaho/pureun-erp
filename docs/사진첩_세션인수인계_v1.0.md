## 1. 한 줄 요약

폰으로 찍은 사진이 **그 기기에만** 남아 PC에서 안 보인다.

## 2. 확정된 것 · 철회된 것

### 확정

| 항목 | 결정 |
|---|---|
| 사진 보관 | 별도 앱 「푸른 사진첩」 (`pu-photos.html` 가칭) |
| 저장 방식 | 실시간DB에 base64 (푸른카메라와 동일). **Storage 쓰지 말 것** |
| 각 앱 연결 | `js/` 공용 조각 하나 → 앱마다 한 줄 |
| 사진 배정 | 자동 안 함. **담당자가 날짜를 골라** 체크해서 넣음 |
| 안 쓴 사진 | **안 지움.** 무조건 보관 |
| 공개 범위 | 올린 사람 + 관리자만 |
| 도장 시각 | 실제 찍은 시각을 기본값으로, 고칠 수 있게 |
| 소유 | 컨설팅이 **복사해 갖는다.** 사진첩을 가리키기만 하지 않음 |

### 철회 — 다시 제안하지 말 것

| 안 | 왜 뺐나 |
|---|---|
| Firebase Storage | 이 저장소의 **어떤 앱도 실제로 안 쓴다.** `pu-cards.html`은 SDK만 로드하고 사진은 실시간DB에 넣는다. 검증된 적 없음 |
| 컨설팅 앱 안에서 촬영 | 현장에서 앱을 만져야 함 |
| 찍은 날짜로 자동 배정 | 하루에 두 사업장을 가면 안 갈림. 추천까지만, 넣는 건 사람이 |
| 컨설팅 앱 안에 보관함 | 앱이 커지고(이미 500KB) 다른 앱이 못 씀 |

## 3. 확인된 사실 (직접 조사한 것)

### 3-1. 이 시스템의 구조

- 앱 15개가 **`js/` 공용 파일 4개**를 함께 로드한다:
  `pu-resilience.js` · `pu-health.js` · `pu-version.js` · `pu-backup.js`
  → 당겨오기를 여기 하나 더 넣으면 앱마다 `<script src>` 한 줄이면 된다
- 포털 `enter.html` 에 앱 목록이 **배열 리터럴**로 있다(약 571행부터).
  `{ key, name, desc, icon, url, roles, row }` 한 줄 추가하면 타일이 생긴다
- 빌드 없음. 단일 HTML 파일 + `js/` 몇 개. 각 앱은 자기완결형

### 3-2. 검증된 선례 — `pu-camera.html` (28KB)

폰 전용으로 찍어 명함첩에 넣는 앱. **이걸 본떠 만들면 된다.**

- Firebase compat SDK 10.12.0 (app / database / auth / app-check)
- 실시간DB `pureun-erp-default-rtdb.asia-southeast1`
- App Check reCAPTCHA v3 활성
- 데이터 루트 `pucards`, 저장은 `db.ref(DB_ROOT+'/items/'+id).set(it)`
- 사진은 **base64 dataURL 그대로** 노드에 넣는다 (`toDataURL('image/jpeg', .65~.95)`)
- 공용 파일 3개 로드 (`pu-backup.js`는 안 씀)

### 3-3. 지금 컨설팅 앱의 사진 (`gov-consulting.html`, 500KB)

| 무엇 | 어디 |
|---|---|
| 저장소 | 브라우저 IndexedDB `pureun_photos` / 스토어 `photos` — **기기 전용, 클라우드 동기화 없음** |
| 키 형식 | `<일정id>_c<n>` = 도장 찍힌 것, `<일정id>_o<n>` = 원본 |
| 메모리 캐시 | 전역 `PHOTOS[일정id][키]` (canvas 객체) |
| 저장 함수 | `savePhotoToDB(sid, key, dataUrl)` — ⚠ 트랜잭션 완료를 안 기다린다 |
| 불러오기 | `loadPhotosFromDB()` |
| 삭제 | `deletePhotoFromDB(sid)` / `deleteOnePhotoFromDB(sid, key)` |
| 도장 그리기 | `drawStamp` · `drawStampText` · `simpleStampCanvas` — **1080×1080 정사각**, 품질 `.92` |
| 도장 시각 | `applyTimes(slot)` — 지금은 직접 입력하거나 **오전/오후 범위에서 임의 생성**. 실제 촬영 시각을 안 씀 |
| 칸 개수 | `totalSlotCount(sc)` · `photoSlotDefs(sc)` — 일정/컨설팅마다 다름(최대 12) |
| 사진 있나 | `schedHasPhoto(sid)` |
| 파일 입력 | `photoFi` · `mEditExtraFi` — `accept="image/*"`, **`multiple` 없음**(한 장씩) |

### 3-4. Firebase 현황 (중요)

- 2026-07-30 규칙 개편으로 **익명 로그인 차단**됨. 이메일 로그인 계정만 읽고 쓴다
- 그래서 **localhost에서는 데이터가 안 읽힌다**(익명으로 붙기 때문). 정상이다
- 컨설팅 앱의 `signInAnonymously` 폴백은 더 이상 데이터를 못 읽는다
- 새 노드를 쓰려면 **콘솔에서 규칙에 경로를 추가**해야 한다.
  기존 패턴: `.read/.write: "auth != null && auth.token.firebase.sign_in_provider === 'password'"`

## 4. 반드시 지킬 규칙

### 4-1. 실데이터 사고 방지 (제일 중요)

2026-07에 브라우저 테스트가 `setCos`/`setScheds`를 불러 **실제 사업장 26곳·일정 53건을 테스트 데이터로 덮어썼다.** 백업에서 복구했다.

- 브라우저에서 테스트하기 전에 **반드시 `fbPush`를 스텁으로 갈아끼운다**
  ```js
  window.__origFbPush = fbPush;
  window.fbPush = function(){ (window.__pushed=window.__pushed||[]).push(1); return Promise.resolve(); };
  ```
- 끝나고 `window.__pushed.length === 0` 을 확인해 보고한다
- 테스트 데이터는 `localStorage.setItem` 으로 직접 넣고, 끝나면 지운다
- 사진은 **한 장씩 추가만.** 배열·객체를 통째로 덮어쓰지 않는다

### 4-2. 검증

빌드가 없으므로 **스크립트를 뽑아 문법 검사 → 브라우저에서 동작 확인** 순서.

```powershell
$h=[System.IO.File]::ReadAllText("gov-consulting.html",[System.Text.Encoding]::UTF8)
$m=[regex]::Matches($h,'(?s)<script(?![^>]*\ssrc=)[^>]*>(.*?)</script>')
$js=($m|ForEach-Object{$_.Groups[1].Value}) -join "`n;`n"
[System.IO.File]::WriteAllText("$env:TEMP\chk.js",$js,(New-Object System.Text.UTF8Encoding($false)))
node --check "$env:TEMP\chk.js"
```

⚠ `Get-Content -Raw` 로 읽으면 한글이 깨진다. 반드시 `ReadAllText` + UTF8.

### 4-3. 배포 — 작업트리를 여러 세션이 공유한다

같은 폴더를 여러 AI 세션이 동시에 쓴다. 브랜치가 예고 없이 바뀐다.

- `git stash pop` **금지**. `git add .` **금지** — 건드린 파일만 지정해 add
- `git pull --rebase` 하다 남의 파일에서 충돌나면 **즉시 `git rebase --abort`**
- main 배포는 임시 작업트리로:
  ```bash
  git fetch origin main
  git worktree add --detach <임시경로> origin/main
  git -C <임시경로> cherry-pick <커밋>
  git -C <임시경로> push origin HEAD:main
  git worktree remove --force <임시경로>
  ```

### 4-4. UI

- 화면을 바꾸기 전에 **목업을 먼저 보여주고 승인**받는다
- 설명은 짧고 쉽게. 파일 경로·함수 이름은 대표님이 직접 입력할 때만 노출

## 5. 작업 순서

| 덩이 | 내용 | 예상 | 이것까지 하면 |
|---|---|---|---|
| **A** | 사진첩 앱 껍데기 + 포털 등록 | 반나절 | 앱이 열림 |
| **B** | 사진 클라우드 저장(실시간DB, **연도별 분리**) | 반나절 | 폰↔PC 사진 공유됨 |
| **C** | 사진첩 화면(올리기·날짜별 보기·날짜 고치기) | 반나절 | 앨범에서 몰아 올리기 됨 |
| **D** | 당겨오기 창(공용 조각) + 컨설팅 연결 | 반나절 | **대표님 요구 완성** |
| **E** | 연말 백업(ZIP) | 반나절 | 해마다 안전하게 남음 (12월 전) |

**A~C 는 새 파일이라 기존 앱에 영향이 없다.**
**D 에서 처음으로 `gov-consulting.html` 을 건드린다** — 4-3 규칙 주의.

### 설계 시 지킬 것
- 사진은 **볼 때만 한 장씩** 받아온다. 앱 열 때 통째로 받으면 느려진다
- **연도별로 노드를 나눈다.** 올해 것만 평소에 불러온다
- 올릴 때 긴 변 1600px로 축소(약 300KB). **원본은 클라우드에 안 올린다**
- 통신 실패 시 기기에 먼저 저장 → 연결되면 자동 재시도
- 찍은 시각은 EXIF에서 읽고, 없으면 파일 날짜, 그것도 없으면 직접 지정

## 6. 착수 전 확인할 것

1. **사진첩 앱을 이 세션이 만드는지** — 대표님께 확인. 다른 경로로 만들어지는 중일 수 있다
2. 이미 만들어져 있다면 **사진을 어디에 어떤 형태로 저장하는지** 먼저 읽는다. D는 그걸 읽어야 한다
3. 새 실시간DB 노드를 쓰면 **콘솔 규칙 추가가 필요**하다 (대표님만 가능)
